# 2단계 설계 — 화면

`design-system.md`의 토큰·컴포넌트만으로 기술한다. 코드는 없다.

---

## 0. 전제

### 0.1 화면 구조 — 통합 좌우 분할 (소유자 확정)

소유자가 확정한 구조는 다음 셋이다. 이 문서 전체가 이 위에 선다.

1. **좌우 분할.** 왼쪽 입력, 오른쪽 결과, 실시간 반영.
2. **갱신 시점.** 필수 항목이 모두 채워지면 그때부터 결과가 나온다. 그전에는 "무엇을 더 입력하면 결과가 나오는지"를 보여준다. 타이핑 중 매 글자 갱신하지 않는다.
3. **결과 제시.** 기본안 + 대안 1~2개 비교. 단일 최적안만 내지 않는다 — 헌장의 "결과는 선택지 비교로 제시한다"를 화면 구조로 구현한 것이다.

이 구조는 요구사항의 4화면 분리와 어긋난다. `open_questions`에 올렸다. 이 문서는 통합 구조를 다음과 같이 요구사항의 화면 목록에 대응시킨다.

| requirements.md 4절 화면 | 이 문서에서의 실체 |
|---|---|
| 랜딩 화면 | 통합 작업 화면의 헤더 + 결과 패널의 입력 부족 상태. 첫 진입 시 보이는 것이 곧 랜딩이다 |
| 입력 화면 | 통합 작업 화면의 좌측 패널(데스크톱) / 상단 영역(모바일). 3절 |
| 결과 화면 | 통합 작업 화면의 우측 패널(데스크톱) / 하단 시트(모바일). 4절 |
| 오류·안내 화면 | 결과 패널의 계산 불가 상태(인라인). 별도 페이지를 만들지 않는다. 8.4절 |

**별도 페이지를 하나도 만들지 않는다.** 헌장이 "금액을 표시할 때 산정 기준·적용 대상·조건을 같은 화면에서 함께 표시한다"고 정했으므로, 근거·가정·한계를 다른 페이지로 옮기는 순간 위반이다.

### 0.2 엔진 결과 — 가정에서 계약으로

**초판은 `engine-interface.md`가 없어 아래를 가정으로 세웠다. 게이트 2에서 대조를 마쳤고 전부 계약으로 확정됐다.** 표는 화면이 어떤 값에 기대고 있는지를 한눈에 보기 위해 남긴다. 정본은 `engine-interface.md`다.

| 가정 | 화면에서 쓰는 곳 |
|---|---|
| G1. 결과는 **배분안 배열**이며 각 안이 `이름`, `계좌별 배분액(월/연)`, `계좌별 잔여 한도`, `미배분 잔액`, `예상 절감세액`을 갖는다 → 계약의 `Plan` | 4절 전체, C-3 비교 |
| G2. 첫 원소가 기본안이고 나머지 1~2개가 대안이다. 개수는 입력에 따라 변할 수 있다 → 계약도 `plans` 1~3개 | 4.4절, 안이 1개일 때의 처리 포함 |
| G3. 각 시나리오가 **적용한 규칙 목록**을 갖고, 각 규칙이 `id`, `source.law`(문자열), `source.url`, `기준 과세연도`, 선택적 `bill_stage`를 갖는다 | `LawChip`, `BasisBlock`, `ProposedBadge` |
| G4. 엔진이 **가정 목록**(다른 소득공제 미반영, 단일 과세연도 등)을 문자열 배열로 함께 준다 | `AssumptionBlock` |
| G5. 계산 불가 상태는 예외가 아니라 **사유 코드 + 관련 규칙**을 담은 결과로 돌아온다(예: 최소 가입 연령 미달) | 8.4절 오류 상태 |
| G6. 절감세액은 **국세 + 개인지방소득세**를 합한 값이며, 그 사실이 결과에 표기 가능한 형태로 온다 | `AmountCard` 조건 캡션 |
| G7. 모든 계산이 브라우저 안에서 끝나고 네트워크 요청이 없다 | 로딩 상태를 "네트워크 대기"가 아니라 "계산 중"으로 설계한 근거. 8.3절 |

G7 때문에 로딩은 대부분 100ms 미만이다. 그럼에도 로딩 상태를 설계하는 이유는 첫 진입 시 룰셋(JSON) 로드가 한 번 있고, 저사양 기기에서 시나리오 3개 계산이 눈에 띄게 걸릴 수 있기 때문이다.

**계약 확정으로 이름이 바뀐 것.** 화면 문서의 "시나리오"는 계약의 `ScenarioResult`(확정 룰셋 / 개정예고 룰셋), "배분안"은 계약의 `Plan`이다. 이 문서에서 `[4-C]` C-3가 비교하는 대상은 **한 시나리오 안의 `plans`**다. 4.4절에서 정리했다.

**계약이 추가로 준 것 (게이트 2 D10).** `Plan.warnings`(중도 불이익), `ScenarioResult.fund_use_horizon_boundaries`(선택지 라벨에 넣을 실제 연수), `comparison_note_codes`. 3.4절과 4.7절에서 다룬다.

### 0.3 화면에 쓰는 가명칭

서비스 명칭 미정이므로 `[가칭] 납입배분 계산기`를 쓴다. 헌장이 금지한 "세무·택스·절세·컨설팅·환급·상담·자문·대행" 계열을 피했고, 안전 계열(계좌·납입·배분·계산)로 조합했다.

## 1. 공통 골격

### 1.1 데스크톱 (≥1024px)

```
┌────────────────────────────────────────────────────────────────────────────────────┐
│  [가칭] 납입배분 계산기                    2026 과세연도 기준       [ ? 이용 안내 ] │  헤더 56px, sticky
├──────────────────────────────────┬─────────────────────────────────────────────────┤
│                                  │                                                 │
│   입력 패널                       │   결과 패널                                      │
│   5/12 열                         │   7/12 열                                       │
│   min 400 / max 520px            │   sticky top: 헤더+24px                          │
│   독립 스크롤                      │   자체 스크롤(길어지면)                            │
│                                  │                                                 │
│   3절                             │   4절                                           │
│                                  │                                                 │
├──────────────────────────────────┴─────────────────────────────────────────────────┤
│  푸터 — 제공자 표기 · 현재 제휴·광고 없음 · 룰셋 기준일                                  │  고지 아님(보조)
└────────────────────────────────────────────────────────────────────────────────────┘
```

- 두 패널 사이 `space-7`(48px) 거터, 그 가운데 1px `border-subtle` 세로선.
- 입력 패널이 결과 패널보다 길어지면 결과 패널이 sticky로 따라붙는다. 반대로 결과가 더 길면 각자 스크롤한다.
- 헤더의 `2026 과세연도 기준`은 장식이 아니라 **고지 ③의 상시 노출분**이다. 결과가 없어도 항상 보인다.

### 1.2 모바일 (<768px)

```
┌──────────────────────────────┐
│ [가칭] 납입배분 계산기   [ ? ] │  헤더 52px
├──────────────────────────────┤
│ 이 계산기는 무엇을 하는가 (2줄) │  진입 안내, 결과 생성 후 접힘
├──────────────────────────────┤
│                              │
│  입력 (세로 1열)               │
│  3절과 동일한 그룹 순서          │
│                              │
├──────────────────────────────┤
│                              │
│  결과 (입력 아래로 이어짐)       │
│  4절과 동일한 순서              │
│                              │
├──────────────────────────────┤
│ [ 남은 항목 3개 ]  또는          │  StickySummaryBar 56px
│ [ 절감세액 {금액} · 결과 보기 ]   │  화면 하단 고정
└──────────────────────────────┘
```

- **결과를 위로 올리지 않는다.** 입력이 먼저 오고 결과가 아래에 이어진다. 대신 하단 고정 바가 결과로 가는 지름길이다.
- 하단 바를 탭하면 결과가 **바텀시트로 전체 높이의 92%까지** 올라온다. 시트 안에서 스크롤하며 결과 전체를 본다. 시트 상단에 `입력 수정` 버튼이 있어 다시 내려갈 수 있다.
- 시트를 쓰지 않고 그냥 스크롤해도 같은 결과에 도달한다. **시트는 지름길이지 유일한 경로가 아니다.**

### 1.3 태블릿 (768~1023px)

단일 열을 유지하되 폭이 넓으므로 입력 필드를 2열로 배치한다(같은 그룹 내에서만). 결과는 입력 아래. 하단 고정 바 유지.

좌우 분할을 1024px 미만에서 시도하지 않는 이유: 결과 패널 폭이 480px 아래로 내려가면 시나리오 3개 비교가 성립하지 않는다(5.5절에 측정 근거를 적었다).

## 2. 헤더 · 진입 안내

### 2.1 헤더

좌측 가명칭(`type-title-s`), 중앙 또는 우측에 `2026 과세연도 기준`(`type-caption`, `text-secondary`), 우측 끝 `이용 안내` 버튼(`text` 변형).

`이용 안내`는 모달로 열리며 고지 ①②⑤의 전문을 담는다. **결과 화면의 고지를 대신하지 않는다** — 결과 패널의 고지는 별도로 항상 표시된다. 이 모달은 결과가 없는 상태에서도 서비스 성격을 확인할 수 있게 하는 보조 경로다.

### 2.2 진입 안내 (첫 화면의 카피)

결과 패널 상단(데스크톱) / 헤더 아래(모바일)에 두 문장.

```
왼쪽에 값을 넣으면 ISA · IRP · 연금저축에 각각 얼마씩 넣는 배분을
세법 규칙으로 계산해 오른쪽에 보여줍니다.
계산은 이 브라우저 안에서만 이루어지고 입력값은 어디로도 전송되지 않습니다.
```

- 두 번째 문장이 헌장 제품 원칙 4의 화면 표현이자, 사용자가 소득을 입력하기 전에 알아야 할 정보다. 결과가 나온 뒤에는 접히고 아이콘 + `브라우저 내 계산` 한 줄로 축약된다.
- 명령형("시작하세요")을 쓰지 않는다. 주어는 계산기이고 서술은 기능이다.

### 3.2 규약

- **"계산하기" 버튼이 없다.** 필수 항목이 다 채워지면 결과가 자동으로 나오므로 제출 버튼이 필요 없다. 요구사항 AC의 "모든 필수 항목이 유효하면 계산하기 버튼이 활성화된다"는 이 구조에서 **"모든 필수 항목이 유효하면 결과 패널이 결과 상태로 전환된다"**로 대응한다. 모바일에서는 하단 고정 바가 그 역할을 겸한다(`남은 항목 n개` → `결과 보기`).
- **조건부 노출의 조건은 다른 필드의 값에서 추론하지 않고 사용자에게 직접 묻는다.** 게이트 2 판정으로 확정된 원칙이다 — **명시적 진술이 다른 필드로부터의 추론보다 낫다.** ISA 관련 항목의 노출 조건은 `ISA 누적 납입액 > 0`이 아니라 `ISA 계좌가 있나요 = 예`다(`requirements.md` 2절의 `ISA 계좌 보유 여부`). 근거 셋: ① 금액 필드에서 의도를 추론하면 사용자가 값을 지우거나 고치는 동안 항목이 깜빡여 자기가 잘못한 것으로 읽힌다 ② "계좌는 있는데 아직 안 넣은" 상태가 실재하고, 그 사용자는 게이트 1 D3이 범위에 넣은 전환 기능을 통째로 못 본다 ③ 비용이 비대칭이다 — 잘못 보여주면 `아니오` 한 번이고, 잘못 숨기면 기능 상실이다.
- **`fund_use_horizon`에는 미리 선택된 값이 없다.** 엔진이 기본값을 만들지 않는다고 계약에 못박았으므로(`engine-interface.md` 3.1절) 화면도 만들지 않는다. `아직 모르겠다`는 **비어 있음이 아니라 사용자가 고른 답**이며 계약의 `"unknown"`으로 보낸다. 3.4절.
- 그룹 ③의 세 필드는 기본값이 비어 있지 않고 **`0`으로 미리 채워져 있다.** 요구사항 AC가 "입력하지 않으면 0으로 간주하고 진행을 막지 않는다"이므로, 빈칸으로 두고 0으로 해석하는 것보다 0을 보여주는 편이 정직하다. 사용자가 무엇이 계산에 들어갔는지 화면에서 확인할 수 있다.
- 오류는 **필드 옆 즉시 표시**한다(요구사항 3절 유저플로우 3). 오류가 있는 동안 결과 패널은 계산하지 않고 직전 결과를 유지한 채 상단에 오류 요약을 띄운다(8.4절).
- `초기화`는 확인 모달을 거친다. 누른 뒤 되돌릴 수 없으므로.
- 각 필드의 `[ ? ]`는 `HelpPopover`다. "이 값을 어디서 확인하나요"만 담는다. 계산 근거는 담지 않는다 — 근거는 결과 패널의 `BasisBlock` 소관이다.

### 3.3 기준연도가 다른 소득 (게이트 1 최종 판정 대응)

게이트 1 최종 판정이 "2단계 입력·화면 설계에서 정면으로 다뤄야 한다"고 지목한 사항이다. ISA 서민형은 **직전** 과세기간 소득, 연금계좌 세액공제율은 **해당** 과세기간 소득으로 판정한다.

설계 결론: **필드를 두 개로 늘리지 않고, 체크박스 한 개로 분기한다.**

- 기본 상태: `총급여액(2026년)` 하나만 묻는다.
- 체크박스 `직전 과세기간(2025년) 총급여액이 다릅니다`를 체크하면 아래에 `총급여액(2025년)` 필드가 나타난다.
- **체크하지 않으면 화면은 직전 연도 값으로 `null`을 보낸다.** 초판은 "같다고 간주"로 설계했으나 계약이 이를 금지한다 — `engine-interface.md` 3.1절은 `prior_year_total_salary_krw`가 null이면 "교차확인을 건너뛰고 `prior_year_income_missing` notice를 낸다. **해당 연도 값으로 대체하지 않는다**"고 못박았다. 화면이 임의로 값을 채워 보내면 엔진이 확인 없이 구간을 판정하게 되고, 그것은 근거 없는 숫자를 계산에 밀어 넣는 일이다.
- 그 결과 `[4-E]` `AssumptionBlock`에 notice가 항목으로 뜬다: `직전 과세기간 총급여액을 받지 않아 ISA 비과세 한도 구간의 교차확인을 하지 않았습니다.` 체크박스 라벨 옆에 이 사실을 미리 알리는 캡션을 둔다 — 체크하면 결과가 더 정확해진다는 것을 입력 시점에 알 수 있어야 한다.

근거: 두 필드를 모두 필수로 만들면 입력 항목이 하나 더 늘어 이탈이 커지고, "왜 두 번 묻지" 하는 혼란이 생긴다. 반대로 하나만 묻고 조용히 같은 값을 쓰면 가정을 숨기는 설계가 된다. 체크박스 분기는 대부분의 사용자에게 필드를 하나로 유지하면서, 묻지 않았다는 사실을 결과에 드러낸다.

**보류 슬롯 — `ISA 가입경과연수`.** `engine-interface.md`가 `accounts.isa.years_since_opening`을 선택 필드로 두었고, null이면 `fund_use_horizon_boundaries.isa_lock_in_years_remaining`을 **보수적으로 전체 기간**으로 잡는다(계약 5.9절). 즉 이 필드가 없어도 화면은 성립하되 남은 의무가입기간이 실제보다 길게 나온다. requirements.md 2절 입력 항목 표에 없는 항목이라 이번에도 필드를 그리지 않고, 그룹 ③의 `ISA 계좌 유형` 아래 자리만 유지한다. 대신 `[4-E]`에 `ISA 가입 시기를 받지 않아 남은 의무가입기간을 최대로 잡았습니다`가 항목으로 뜬다.

### 3.4 `fund_use_horizon` — 선택지 라벨 문제 (게이트 2 D10)

**엔진이 화면에 넘긴 문제.** 선택지 값 이름에 연수가 없다. 의도된 설계다 — 값 이름에 숫자를 넣으면 룰셋 수치가 계약에 복사되고 세법이 바뀌면 이름이 거짓말이 된다. 실제 연수는 엔진이 `ScenarioResult.fund_use_horizon_boundaries`로 룰셋에서 읽어 내보낸다. **그런데 사용자는 이 선택지를 입력 시점에, 즉 엔진 결과가 나오기 전에 봐야 한다.**

#### 결론: 라벨은 수치 없는 서술로 완결하고, 실제 연수는 보조 캡션으로 나중에 붙인다

두 층으로 나눈다.

| 층 | 내용 | 출처 | 없을 수 있나 |
|---|---|---|---|
| **라벨**(필수) | 수치 없는 서술. 예: `ISA 의무가입기간 안에 해지할 가능성이 있다` | 화면이 직접 쓴 문장. **숫자가 없으므로 세법 수치가 아니다** | 아니오. 항상 있다 |
| **보조 캡션**(선택) | `남은 의무가입기간 {n}년` / `그 나이까지 {m}년` | `fund_use_horizon_boundaries` | 예. 아직 없으면 캡션 줄 자체를 그리지 않는다 |

**왜 라벨에 숫자를 넣지 않는가.**

1. **금지 사항이다.** 라벨에 연수를 하드코딩하는 것은 룰셋 수치를 화면 코드에 복사하는 것이고, 제품 원칙 1을 정면으로 어긴다. 룰셋이 바뀌면 라벨이 조용히 틀린 값을 말하게 된다.
2. **숫자가 있다가 없어지는 라벨은 더 나쁘다.** 데이터가 있으면 숫자를 넣고 없으면 빼는 라벨은 사용자마다·순간마다 문장 길이와 의미가 흔들린다. 라벨은 언제나 같은 문장이어야 하고, 그 자체로 선택이 가능해야 한다.
3. **경계값 없이도 선택은 가능하다.** 사용자가 실제로 아는 것은 "이 돈을 언제 쓸 것 같은가"이지 "의무가입기간이 몇 년인가"가 아니다. `ISA를 의무가입기간 안에 해지할 가능성이 있다`는 서술만으로 자기 사정에 대입할 수 있다. 연수는 판단을 **돕는** 정보이지 판단의 **전제**가 아니다.

#### 경계값을 언제 얻는가 — `computeFundUseHorizonBoundaries`

`fund_use_horizon`은 필수 항목 중 **마지막에 채워지도록 배치**했다(그룹 ②의 맨 아래). 따라서 이 선택지를 볼 시점에는 나이와 ISA 관련 입력이 이미 있다.

- 그 시점에 화면이 계약의 **경계값 전용 진입점 `computeFundUseHorizonBoundaries`**(계약 9절)를 부른다.
- 초판은 `compute`에 `fund_use_horizon: "unknown"`을 넣고 부산물을 꺼내 쓰는 프로브 방식을 설계했다. `calc-engine-dev`가 게이트 2 마감에서 전용 진입점을 추가해(`schema_version 2.1.0`) 그 우회가 필요 없어졌고, 계약이 "선택지 캡션처럼 경계 연수만 필요할 때는 이 진입점을 쓴다. `compute`의 부산물을 꺼내 쓰지 않는다"고 명시했다. **그 지시를 따른다.**
- 응답의 `boundaries`만 읽어 보조 캡션에 채운다. 계약이 두 진입점의 `boundaries`가 바이트 단위로 같음을 단위 테스트로 고정하므로 값이 갈릴 위험이 없다.
- **결과 패널에는 아무것도 표시하지 않는다.** 필수 항목이 다 채워져야 결과가 나온다는 확정 규칙(0.1절)을 지킨다.
- 캡션이 채워지는 순간 라벨은 그대로이고 캡션 줄만 나타난다. 레이아웃이 흔들리지 않도록 캡션 줄의 자리는 미리 비워 둔다.

#### 이 입력이 금액을 바꾸지 않는다는 사실을 어떻게 전달하는가

계약이 `echo.fund_use_horizon_affects`로 이 사실을 기계가 읽을 수 있게 실었다. 화면은 **세 곳에서** 사람에게 말한다.

1. **입력 옆**(선택지 그룹 바로 아래, 항상 표시): `이 선택은 계산되는 금액을 바꾸지 않습니다. 어떤 배분안을 먼저 보여줄지와 중도 인출 관련 안내만 달라집니다.`
2. **`[4-E]` `AssumptionBlock`**: `자금 사용 시점은 배분 금액과 세액공제액에 반영하지 않았습니다. 배분안의 순서와 안내에만 쓰였습니다.` (계약의 `fund_use_horizon_excluded_from_amounts` 가정 코드)
3. **선택을 바꿨을 때**: 재계산 후 금액이 하나도 안 바뀌면 `갱신 중` 인디케이터만 지나가고 아무 하이라이트가 없어 "먹통인가" 하는 인상을 준다. 그래서 **순서가 바뀐 배분안 행에 220ms 하이라이트를 주고**, C-3 위에 3초간 캡션을 띄운다: `금액은 그대로이고 배분안을 보여주는 순서가 바뀌었습니다.`

세 번째가 특히 중요하다. **화면이 아무 반응도 하지 않으면 사용자는 입력이 무시됐다고 읽는다.** 실제로는 무시된 것이 아니라 금액에 영향이 없는 것이고, 그 차이를 화면이 말해야 한다.

### 3.5 ISA 만기 전환 목적지 (게이트 1 D3 범위, 계약 `isa_transfer.destination`)

초판은 이 입력을 빠뜨렸다. 게이트 1 D3이 ISA 만기 자금의 연금계좌 전환을 범위에 넣었고 `requirements.md` 2절과 `engine-interface.md` 3.3절이 모두 목적지 필드를 요구하는데 화면에 없었다 — **범위 안의 기능인데 입력이 없으면 동작하지 않는다.**

| 항목 | 값 |
|---|---|
| 계약 필드 | `isa_transfer.destination` |
| 자료형 | `"retirement_pension"` \| `"annuity_savings"` \| `null` |
| 화면 라벨 | `전환한 자금을 받을 계좌` — 선택지 `IRP` / `연금저축` |
| 필수 여부 | 계약상 **선택**. `null`이면 엔진이 `"retirement_pension"`으로 본다 |
| 노출 조건 | `ISA 만기 전환 여부 = 예`일 때만 |

**설계 결정: 화면은 `null`을 보내지 않고 `IRP`를 미리 선택해 둔다.**

`fund_use_horizon`에서는 기본 선택을 두지 않았는데 여기서는 두는 이유가 다르다. 그 필드는 계약이 기본값 생성을 명시적으로 금지했고 `unknown`이라는 정직한 선택지가 있었다. 이 필드는 반대다 — **계약이 `null`을 `retirement_pension`으로 해석한다고 이미 정해 두었으므로, 비워 두는 것은 "고르지 않음"이 아니라 "IRP를 고름"이다.** 그렇다면 그 사실을 화면이 보이는 편이 정직하다. 숨은 기본값보다 보이는 기본값이 낫다.

- 목적지에 따라 결과가 달라지므로(연금저축이면 단독 한도 판정에 먼저 걸린다) 선택지 아래에 그 사실을 캡션으로 둔다: `받는 계좌에 따라 적용되는 한도가 달라 결과가 바뀝니다.`
- 사용자가 목적지를 한 번도 만지지 않았으면 `[4-E]`에 항목이 하나 뜬다: `전환한 자금을 받을 계좌를 IRP로 두고 계산했습니다.`
- 목적지를 바꾸면 **금액이 실제로 달라진다.** `fund_use_horizon`과 달리 3.4절의 "금액은 그대로" 캡션을 붙이지 않는다. 두 입력을 같은 방식으로 다루면 안 된다.

#### 조건부 입력과 `RequirementChecklist`

조건부로 나타나는 입력은 **필수 항목 개수에 상시로 반영하지 않는다.** 첫 진입 시 `n / 4`였다가 ISA 보유를 `예`로 바꾸는 순간 `n / 6`으로 늘어나면, 사용자는 진행 막대가 뒤로 가는 것을 본다. 이탈을 만드는 구조다.

대신 이렇게 다룬다.

- **분모는 무조건 필수인 네 항목으로 고정한다** — 나이 · 총급여액 · 월 납입 여력 · 자금 사용 시점.
- **기납입액은 체크리스트에 올리지 않는다.** 요구사항 AC가 "입력하지 않으면 0으로 간주하고 진행을 막지 않는다"이므로 애초에 진행을 막는 항목이 아니다. 초판은 이 항목을 분모에 넣고 "세 필드 중 하나라도 만졌으면 충족"으로 다뤘는데, 그것은 **사용자의 상호작용에서 확인 의사를 추론한 것**이고 위 원칙에 어긋난다. 대신 값이 전부 0인 채로 결과가 나오면 `[4-E]`에 항목이 뜬다(4.5절).
- 조건부 필수 항목(전환 금액)이 활성화되고 아직 비어 있으면, 체크리스트 **아래에 별도 줄**로 붙인다: `ISA 만기 전환을 선택하셔서 전환 금액이 추가로 필요합니다 → 입력하기`. 분자·분모를 건드리지 않고 진행 막대도 그대로 둔다.
- 전환 목적지와 ISA 계좌 유형은 기본 선택이 있으므로 체크리스트에 올라오지 않는다.
- 네 항목이 다 찼는데 조건부 필수가 비어 있으면 결과 패널은 **입력 부족 상태를 유지**한다(계산할 수 없으므로). 이때 화면은 `2 / 4`가 아니라 `4 / 4 · 추가 항목 1개`로 표시한다. **다 채웠는데 결과가 없는 상태를 설명 없이 두지 않는다.**

#### 조건부 입력이 나타나는 순간의 결과 처리

실시간 갱신 구조에서 입력이 도중에 늘어나는 것은 특수한 사건이다. 세 경우로 나눈다.

| 사건 | 결과 패널 |
|---|---|
| `ISA 계좌가 있나요`를 `예`로 바꿈 | ISA 납입액이 0으로 미리 채워져 있고 계좌 유형도 기본값이 있으므로 **즉시 재계산된다.** 잔여 한도가 늘어 배분이 달라지므로 변경된 금액에 하이라이트. 입력 부족으로 되돌아가지 않는다 |
| `ISA 계좌가 있나요`를 `아니오`로 되돌림 | ISA 관련 값(납입액·유형·전환 일체) 전부 초기화 후 즉시 재계산. 3초간 `ISA 관련 항목이 계산에서 제외되었습니다` |
| 전환 여부를 `예`로 바꿈 (전환 금액 비어 있음) | **직전 결과를 지우지 않고 유지**하되 상단에 `InlineAlert(info)`: `ISA 만기 전환을 선택하셨습니다. 전환 금액을 입력하면 추가 공제 한도를 반영해 다시 계산합니다.` 아래 결과에는 아직 전환이 반영되지 않았다는 표시를 함께 둔다 |
| 전환 금액까지 채움 | 정상 재계산. `[4-D]` 표에 전환 추가 한도 행이 새로 생기므로, 그 행에 220ms 하이라이트를 주어 **무엇이 늘었는지** 보이게 한다 |
| 전환 여부를 `아니오`로 되돌림 | 전환 관련 값 전부 0/null로 되돌리고 즉시 재계산. `ConditionalGroup` 규약(design-system 5.3절)대로 값을 남겨두지 않는다. 결과 패널에 3초간 `ISA 만기 전환 항목이 계산에서 제외되었습니다` |

첫 줄이 핵심이다. **조건부 입력이 나타났다고 결과를 비우면, 사용자는 자기가 무언가를 망가뜨렸다고 읽는다.** 직전 결과를 유지한 채 무엇이 더 필요한지 말하는 편이 낫고, 이는 8.4절 (a)의 처리와 같은 원칙이다.

### 4.2 고지 여섯 요소의 배치 — 확정 명세

`qa`가 게이트 4에서 검사할 대상이다. 각 요소가 **어디에, 어떤 컴포넌트로, 어떤 기본 상태로** 있는지 못박는다.

| # | 요소 | 위치 | 컴포넌트 | 기본 상태 | 접기 가능 |
|---|---|---|---|---|---|
| 1 | **성격** — 자동 계산 결과이며 세무대리가 아님 | 결과 패널 최상단 `[4-A]` | `DisclosureBanner` 1문장 | 항상 표시 | **불가** |
| 2 | **자격** — 제공자가 §6 등록 세무대리인이 아님 | 결과 패널 최상단 `[4-A]` 두 번째 문장 | 같은 배너 | 항상 표시 | **불가** |
| 3 | **근거** — 법령 조항 + 기준 과세연도 | 세 곳에 중복 배치: 헤더의 `2026 과세연도 기준`(상시) · `[4-D]` 각 행의 `LawChip` · `[4-F]` `BasisBlock` 전문 | `LawChip` + `BasisBlock` | `[4-F]` **펼침** | 접을 수 있으나 접힌 헤더에 `적용 조항 n건 · 2026 과세연도 기준` 잔존 |
| 4 | **가정** — 서비스가 세운 가정 | 두 곳: `[4-B]` 헤드라인 금액 바로 아래 한 줄 요약(24px 이내) · `[4-E]` `AssumptionBlock` 전체 목록 | `AmountCard` 슬롯3 + `AssumptionBlock` | `[4-E]` **펼침** | `[4-E]`만 접기 가능. `[4-B]`의 한 줄은 접기 불가 |
| 5 | **한계** — 개별 사정에 따라 다르며 자격자 확인 필요 | 결과 영역 하단 `[4-G]` | `LimitNote` | 항상 표시 | **불가** |
| 6 | **개정예고 구분** — `bill_stage` 표시 | 해당 시나리오에 4중 배치: 도넛 **상단면**의 사선 해칭 · 스택바 해당 **행 전체**의 해칭 + 좌측 배지 · 차트 아래 캡션 한 줄 · `[4-D]`·`[4-F]`의 해당 행 배지 | `ProposedBadge` + 해칭 패턴 | 해당 시나리오 선택 시 항상 표시 | **불가** |

**세 가지 구조적 방어.**

1. **요소 1·2·5는 접히지 않는다.** 접히면 접은 상태가 기본이 되고, 그것이 각주화의 첫 단계다.
2. **요소 3·4는 두 겹으로 둔다.** 금액 옆의 한 줄(요약)과 하단 블록(전문). 헌장이 요구하는 "금액을 표시할 때 같은 화면에서 조건을 함께"는 한 줄이 담당하고, 시행령 §33②2호가 요구하는 "산정 기준·적용 대상·조건의 명확한 표시"는 블록이 담당한다.
3. **요소 6은 배지 하나로 끝내지 않는다.** 색이 아니라 패턴으로 차트에도 새기고, 캡션 문장을 함께 붙인다. 배지만 두면 축소된 화면·흑백 인쇄·공유 이미지에서 소실된다.

**저장·공유 산출물에도 요소 1·2·3(요약)·5가 함께 담긴다.** 결과 이미지가 화면 밖으로 나가면 고지가 따라가지 않는 것이 이 제품의 가장 큰 노출 위험이다. 9절.

### 4.3 `[4-D]` 계좌별 상세 리스트

차트가 못 담는 정확한 값과 근거를 담는 표. **차트의 텍스트 대체 경로이기도 하다**(design-system 6.4절).

```
계좌         월 배분     연 환산    납입 잔여 한도 대비   적용 조항
──────────────────────────────────────────────────────────────────────────
연금저축     ●  350,000   4,200,000   ████░░ 82%     [소득세법 §59조의3 ①]
IRP         ●  250,000   3,000,000   ███░░░ 61%     [소득세법 §59조의3 ① 단서]
  └ 세액공제가 더 인정될 수 있는 금액 {금액} (연금저축·IRP 합산)      ← 5.10절
ISA         ●  200,000   2,400,000   ██░░░░ 24%     [조특법 §91조의18 ③5]
  └ 비과세 한도 {금액} — 계좌에서 생긴 수익에 적용. 절세액에 미포함  ← 5.11절
──────────────────────────────────────────────────────────────────────────
미배분              0           0                    월 납입 여력을 모두 배분함
```

배분 대상이 아닌 계좌가 있으면 그 행은 이렇게 된다(5.9절).

```
ISA         ○  배분 대상 아님
  └ 직전 3개 과세기간 중 금융소득종합과세 대상이었던 경우 ISA 과세특례가
    적용되지 않습니다. 그래서 이번 계산의 배분 대상이 아닙니다.
    [조특법 §129조의2 ①]
```

- 계좌명 앞의 `●`는 차트와 같은 색(`data-pension` / `data-irp` / `data-isa`). 차트와 표의 색이 어긋나면 둘 다 못 읽는다. 배분 대상이 아닌 계좌는 속을 채우지 않은 `○`로 두어 차트에 조각이 없는 것과 대응시킨다.
- 금액은 `tabular-nums`. 월과 연을 모두 보여준다 — 사용자는 월 단위로 생각하고, 세액공제는 연 단위로 계산되기 때문이다.
- `적용 조항` 열의 `LawChip`을 누르면 `[4-F]`의 해당 항목으로 스크롤 + 하이라이트.
- 미배분 잔액이 있으면 그 행이 `state-warning` 색으로 강조되고 사유가 붙는다: `세 계좌의 납입 잔여 한도를 모두 채우고 남은 금액입니다. 이 배분에 포함되지 않습니다.`
- ISA 만기 전환을 "예"로 입력했으면 표 아래에 별도 행이 추가된다: `ISA 전환에 따른 추가 공제 한도 {금액} — 위 연금저축·IRP 배분에 반영됨` + `LawChip`. 전환이 "아니오"면 이 행 자체를 그리지 않는다(요구사항 AC).

### 4.4 배분안(`Plan`)과 개수

- 계약의 `plans`는 1개 이상 3개 이하이고 **`plans[0]`이 기본안**이다. 어느 안이 기본안이 되는지는 `fund_use_horizon`이 정한다.
- 안이 3개면 스택바 3행, 2개면 2행, **1개면 스택바를 그리지 않고** 그 자리에 한 줄 캡션을 둔다: `입력한 조건에서는 비교할 다른 배분이 나오지 않았습니다.` 도넛과 한도 트랙 막대는 그대로 남는다.
- 배분안이 1개인 상태는 **오류가 아니다.** 결과는 정상이고 비교 대상만 없다. 오류 색을 쓰지 않고 `type-caption`으로 담담하게 적는다.
- 행 이름은 계약의 배분안 종류를 그대로 부른다: `세액공제액이 가장 큰 배분`(`max_tax_credit`) · `연금저축을 먼저 채우는 배분`(`annuity_savings_first`) · `ISA를 먼저 채우는 배분`(`isa_first`). **계산이 무엇을 우선했는지를 이름이 그대로 말한다.**
- 각 행에 절감세액과 **기본안 대비 차액**을 함께 적는다: `1,3XX,XXX원 (기본안 −1XX,XXX원)`. 차액이 있어야 비교가 성립한다.
- **"추천"·"최적"·"권장"을 행 라벨에 쓰지 않는다.** 기본안은 `기본` 표시만 단다.
- **`baseline_reordered_by_fund_use_horizon`이 오면 그 사실을 숨기지 않는다.** C-3 상단에 한 줄: `세액공제액이 가장 큰 배분이 기본안이 아닙니다. 자금 사용 시점 선택에 따라 순서가 바뀌었습니다.` 이 줄이 없으면 사용자는 기본안이 곧 최대 절세액이라고 읽는다.

### 4.5 `[4-E]` `AssumptionBlock` 항목 (고정 + 조건부)

항상 들어가는 항목:
- `2026 과세연도 하나만 계산했습니다. 다음 해 이후는 반영하지 않았습니다.`
- `연말정산의 다른 소득공제·세액공제(부양가족 등)는 반영하지 않았습니다.`
- `절세액은 국세와 개인지방소득세를 합한 금액입니다.`
- `입력한 값이 정확하다는 전제에서 계산했습니다. 이 계산기는 입력값을 검증하지 않습니다.`
- `투자 수익률과 계좌 운용 결과는 계산에 포함되지 않았습니다.`

- `자금 사용 시점은 배분 금액과 세액공제액에 반영하지 않았습니다. 배분안의 순서와 안내에만 쓰였습니다.` (계약 `fund_use_horizon_excluded_from_amounts`)

조건부로 붙는 항목 — **대부분 "묻지 않아서 생긴 것"이다.**

**항목을 목록으로 나열하지 않는다. 두 조각을 한 문장에 붙여 쓴다 — 무엇을 묻지 않았는가, 그래서 계산을 어떻게 했는가.** 관리자가 게이트 2에서 요구한 형태이며, "묻지 않았다"만 적으면 사용자는 그것이 자기 결과에 무슨 뜻인지 알 수 없다.

|---|---|---|
| 직전 과세기간 소득 체크박스를 켜지 않음 | `직전 과세기간 총급여액을 받지 않아, ISA 비과세 한도 구간을 해당 연도 소득만으로 판정하고 교차확인은 하지 않았습니다.` | `prior_year_income_missing` |
| 금융소득종합과세 여부를 묻지 않음 | `직전 3개 과세기간의 금융소득종합과세 대상 여부를 받지 않아, 해당자였다면 적용되는 ISA 과세특례 배제를 적용하지 않고 계산했습니다. 해당자라면 ISA 배분이 결과와 달라집니다.` | `financial_income_status_unknown` |
| 청년 우대 자기신고를 받지 않음 | `청년 우대 대상 여부를 받지 않아, 개정안 시나리오의 청년 우대를 적용하지 않고 계산했습니다. 대상자라면 세액공제액이 결과보다 커질 수 있습니다.` | `youth_status_not_declared` |
| ISA 가입 시기를 묻지 않음 | `ISA 가입 시기를 받지 않아, 남은 의무가입기간을 가장 길게 잡았습니다. 실제로는 이보다 짧을 수 있습니다.` | — (계약 5.9절 보수적 처리) |
| 남은 납입 개월수를 묻지 않음 | `과세연도 전체를 납입한다고 보고 연간 예산을 계산했습니다. 연중에 시작하면 실제 납입액은 이보다 적습니다.` | 계약 3.1절 기본값 |

| 전환 목적지를 만지지 않음 | `전환한 자금을 받을 계좌를 IRP로 두고 계산했습니다. 연금저축으로 받으면 적용되는 단독 한도가 달라 결과가 바뀝니다.` | — (3.5절) |
| 직전 과세기간 전환 적용액을 비워 둠 | `직전 과세기간에 받은 전환 추가공제를 0으로 보았습니다. 실제로 받은 금액이 있으면 추가 한도가 결과보다 줄어듭니다.` | `prior_transfer_credit_zero_assumed` |

| 개정예고 시나리오 | 고지 ⑥과 연결 | — |

**어느 방향으로 틀릴 수 있는지를 적는다.** `달라질 수 있습니다`로 끝내면 사용자는 무엇을 확인해야 할지 모른다. `커질 수 있습니다` / `줄어듭니다` / `이보다 짧을 수 있습니다`처럼 방향을 적으면, 자기 사정에 해당하는 항목만 골라 확인할 수 있다. **이것이 필수 입력을 늘리지 않으면서 정확도를 사용자에게 넘기는 방법이다.**

**"묻지 않았다"를 가정으로 적는 것이 이 블록의 핵심이다.** 서비스가 세운 가정 중 가장 흔한 것은 계산 방법의 가정이 아니라 **받지 않은 입력을 어떻게 처리했는가**이고, 그것이 결과를 바꾼다. 고지 ④가 요구하는 "입력값 외에 서비스가 세운 가정"에 정확히 해당한다.

**관리자 판정(게이트 2).** 엔진의 선택 입력 넷(`financial_income_taxpayer_last_3_years`·`declared_youth`·`months_remaining_in_tax_year`·`accounts.isa.years_since_opening`)을 입력 항목으로 늘리지 않고 이 블록에 드러내는 방식이 승인됐다. 근거는 판정 지표 1(계산 완료율)과 정직함을 동시에 지키는 것이다 — 입력이 길어지면 완료율이 떨어지고, 조용히 가정하면 정직함이 깨진다. **그 승인은 이 블록이 "무엇을 묻지 않았고 그래서 어떻게 계산했는가"로 쓰인다는 조건 위에 있다.** 항목이 단순 목록으로 퇴화하면 승인의 전제가 무너진다.

### 4.6 `[4-G]` `LimitNote` 문구

```
이 결과의 한계
· 개별 사정(다른 소득·공제 항목, 계좌 개설 시기, 금융기관별 조건 등)에 따라
  실제 결과는 달라질 수 있습니다.
· 실제 신고·납부는 세무사 등 자격을 갖춘 사람에게 확인하시기 바랍니다.
· 이 계산기는 특정 금융상품이나 금융회사를 다루지 않습니다.
  현재 제휴나 광고가 없습니다.
```

마지막 줄은 헌장 제품 원칙 8("지금 정하지 않은 것을 약속하지 않는다")에 따라 **현재 사실만** 적었다. "앞으로도 없습니다"라고 쓰지 않는다.

### 4.7 중도 불이익 안내 (`Plan.warnings`) — 게이트 2 D10

#### 설계의 요점: 겁주는 장치가 아니라 정보

경고가 사용자를 놀라게 하는 순간 두 가지가 동시에 무너진다. 첫째, 금액이 없는 경고는 과장으로만 남는다 — 인출 단계가 v2라 "얼마를 물게 되는지"를 우리는 모른다(계약 5.6절). 둘째, 겁을 주어 행동을 유도하는 화면은 "개인에게 맞춘 지시"에 가까워진다. 헌장이 금지한 쪽이다.

**그래서 이 안내의 문장은 전부 "이런 규칙이 있다"는 사실 서술이고, 주어는 사용자가 아니라 법령이다.** 각 안내에 `LawChip`이 붙는 것이 그 증거다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| "손해를 볼 수 있습니다" | "감면받은 세액을 추징하는 규칙이 있습니다" |
| "주의하세요" / "위험합니다" | (제목 없이 사실만) |
| "다른 계좌를 고려하세요" | (지시하지 않는다. 배분안 비교가 그 역할을 한다) |
| 느낌표, 붉은색, 경고 삼각형 큰 아이콘 | `state-warning` 좌측 3px 바 + 작은 아이콘 |

#### 배치 — 세 층위

**(a) 계좌별 안내** — `Plan.warnings[]`의 `account`에 붙는다. **두 곳에 같은 내용을 붙인다.**

1. **C-2 한도 트랙 막대의 캡션 아래** — 해당 계좌 막대 바로 아래 한 줄. `WarningNote`(design-system 5.22절).
2. **`[4-D]` 계좌별 상세 표의 해당 행** — 계좌명 옆에 작은 표식, 행 아래 안내 줄.

```
연금저축                                   350,000원 / 월
████████████████████████░░░░░░░░░░░░
└ 납입 잔여 한도의 82%              [소득세법 §59조의3 ①]
  ▍이 계좌에서 연금 수령 개시 연령 전에 인출하면 연금외수령으로
  ▍기타소득세가 적용되는 규칙이 있습니다. 그 나이까지 {m}년.
  ▍[소득세법 시행령 §40조의2 ③]  [소득세법 §129 ①6 나]
```

- **배분액이 0인 계좌에는 붙지 않는다**(계약 5.6절). 트랙만 그려진 계좌에는 안내가 없다.
- 안내 문구의 연수는 `params`(= `fund_use_horizon_boundaries`)에서 온다. **화면이 숫자를 적지 않는다.**
- `basis_rule_ids`의 규칙마다 `LawChip`을 붙이고, 누르면 `[4-F]`의 해당 항목으로 간다.

**(b) 전 계좌 안내** — `all_accounts_have_early_exit_penalty`. `[4-W]`, 즉 **헤드라인 금액과 차트 사이**에 배너로 둔다.

```
┌─────────────────────────────────────────────────────────────────┐
│ ▍세 계좌 모두 중도 인출·해지 시 적용되는 규칙이 있습니다             │
│ ▍                                                               │
│ ▍선택하신 자금 사용 시점에서는 어떤 배분으로 나누어도 이 규칙을      │
│ ▍피할 수 없습니다. 아래 배분안 비교는 세액공제액 기준이며,          │
│ ▍중도 인출 규칙은 배분안에 따라 달라지지 않습니다.                  │
│ ▍                                                               │
│ ▍[조특법 §91조의18 ⑦]  [소득세법 §129 ①6 나]                     │
└─────────────────────────────────────────────────────────────────┘
```

계약이 "화면은 배분 비교보다 이 사실을 앞세워야 한다"고 적었다. 차트 위에 두는 이유다. **이 경우에도 엔진은 배분안 순서를 바꾸지 않으므로**(어느 안도 회피 수단이 아니므로), 배너가 "그러니 다른 안을 고르라"고 말하지 않는 것이 중요하다. 위 문구의 셋째 문장이 그 오독을 직접 막는다.

**(c) 배분안 단위 표식** — C-3 스택바의 각 행 우측에 안내 개수를 작은 표식으로 단다(`▍2`). 행을 고르면 (a)가 그 배분안의 것으로 바뀐다. 배분안마다 배분액이 0인 계좌가 달라 안내 개수가 달라지므로, 이 표식이 있어야 "안을 바꾸면 안내도 바뀐다"는 것이 보인다.

#### `severity`에 따른 차이

| | `warning` (`trigger: declared_horizon`) | `info` (`trigger: horizon_unknown`) |
|---|---|---|
| 언제 | 사용자가 사용 시점을 밝혔고 구성요건이 맞다 | `fund_use_horizon`이 `unknown`이다 |
| 좌측 바 | `state-warning` 3px | `state-info` 3px |
| 바탕 | `state-warning-subtle` | `state-info-subtle` |
| 아이콘 | 주의 아이콘 16px | 정보 아이콘 16px |
| 문두 | (없음. 사실 서술로 시작) | `자금 사용 시점을 밝히지 않아 판정하지 않았습니다 — ` |
| 성격 | 이 사용자의 조건에서 걸린다 | 걸리는지 판정하지 않았고 규칙의 존재만 알린다 |

**`info`의 문두가 핵심이다.** `unknown`일 때 엔진은 구성요건을 판정하지 않고 사실만 낸다(계약 5.6절 `trigger`). 문두를 붙이지 않으면 판정된 것처럼 읽히고, 그것은 화면이 엔진보다 더 많이 아는 척하는 것이다.

**`info` 안내에는 조치 유도를 붙이지 않는다.** `자금 사용 시점을 선택하면 판정합니다` 같은 안내를 달면 정보가 미끼가 된다. 입력 패널에 이미 그 선택지가 열려 있다.

#### 안내가 하나도 없을 때

`at_or_after_pension_age`를 고르면 경고가 하나도 오지 않는다. **이때 "문제 없음" 같은 확인 문구를 띄우지 않는다.** 경고가 없다는 것은 이 두 규칙이 걸리지 않는다는 뜻이지 결과가 안전하다는 뜻이 아니고, 우리는 후자를 말할 근거가 없다. 안내 영역 자체를 그리지 않는다.

## 5. 차트 — 확정안

소유자가 두 시안을 실제 크기로 렌더링한 것을 보고 결정했다(2026-08-08). **원형 시각화는 입체 도넛으로 가고, 가로 막대는 전부 한도 트랙 방식으로 간다.** 결정 경위와 판단이 갈린 지점은 6절에 기록했다.

### 5.1 구성과 선택 근거

차트 영역 `[4-C]`는 세 층이다. **각 층이 서로 다른 질문에 답하고, 같은 것을 두 번 말하지 않는다.**

| 층 | 무엇 | 답하는 질문 | 왜 이 형태인가 |
|---|---|---|---|
| C-1 | 입체 도넛 (직접 라벨) | "내 여력이 계좌별로 어떻게 나뉘는가" | 원형 분할이 "나눈다"는 관용적 은유다. 첫인상과 이해 속도를 담당한다 |
| C-2 | 한도 트랙 막대 3개 | "각 계좌를 한도 대비 얼마나 채웠고 얼마가 남았는가" | 도넛은 100%를 나눌 뿐이라 한도를 표현할 자리가 없다. 트랙 막대는 배분액과 잔여 한도를 한 그림에 담는다. **길이가 곧 금액이므로 C-1의 원근 왜곡을 검산하는 역할도 겸한다** |
| C-3 | 스택바 3행 비교 | "다른 배분과 무엇이 다른가" | 헌장이 "결과는 선택지 비교로 제시한다"를 기능 설계 조건으로 못박았다. 정렬된 가로 막대라야 조각 경계로 동시 비교가 성립한다 (5.5절에 측정 근거) |

**세 층의 순서를 바꾸지 않는다.** 도넛이 먼저 와서 "무엇을 보는 화면인지"를 알리고, 막대가 정확한 값과 여력을 주고, 스택바가 대안을 연다. 순서를 뒤집으면 첫 화면에서 이해 비용이 올라간다.

### 5.3 C-1 — 입체 도넛과 왜곡 완화 장치

3D 원근은 앞쪽 조각을 뒤쪽보다 크게 보이게 한다. **없앨 수 없으므로 네 가지로 묶어 둔다.** 기하 파라미터는 `design-system.md` 5.20절에 고정값으로 박혀 있다.

| # | 장치 | 무엇을 막는가 |
|---|---|---|
| A1 | **기울기 15°·두께 8% 고정.** 반응형·애니메이션에서도 절대 변하지 않는다 | 기울기가 크면 왜곡이 커진다. 고정하면 왜곡량이 최소이고 일정하다 |
| A2 | **모든 조각에 금액과 비율을 직접 라벨링.** 범례만 두지 않는다 | 면적을 눈으로 재지 않아도 값을 읽을 수 있다 |
| A3 | **조각 순서와 시작각 고정.** 항상 12시에서 시계방향으로 연금저축 → IRP → ISA → 미배분. 값이 바뀌어도 순서가 바뀌지 않는다 | 시나리오를 바꿀 때 같은 계좌가 늘 같은 위치에 있어야 비교가 성립한다. **큰 조각을 앞으로 정렬하는 관행은 여기서 금지** |
| A5 | **회전·확대 애니메이션 금지.** 값 변화 시 조각 각도만 240ms로 바뀐다. 뷰 각도는 정지 | 회전 중 왜곡이 순간적으로 극대화된다 |

**A4(검산 장치)는 C-2 한도 트랙 막대가 담당한다.** 원래 설계는 도넛 아래에 같은 값을 길이로 다시 그리는 별도 스트립을 두는 것이었으나, C-2가 왜곡 없는 길이 표현이면서 잔여 한도까지 담으므로 스트립을 별도로 두지 않는다. 검산 경로는 유지되고 세로 공간은 절약된다.

**정직하게 적는다: 이 넷을 다 해도 왜곡은 남는다.** C-2가 왜곡을 보정하는 것이 아니라, 왜곡된 그림 바로 아래에 정확한 그림을 놓아 사용자가 값을 후자에서 읽게 하는 것이다. 도넛의 역할은 값 전달이 아니라 구조 전달이다.

### 5.4 C-2 — 한도 트랙 막대

`AllocationBar`(design-system 5.7절)를 세로로 3개 쌓는다.

- 트랙 전체 = 해당 계좌의 **납입 잔여 한도**(`contribution_limit_remaining_krw`). 채움 = 이번 배분액(연 환산). **세액공제 쪽 값을 트랙에 쓰지 않는다** — 5.10절.
- 세 막대는 **공통 배율**을 쓴다. 납입 잔여 한도가 가장 큰 계좌의 트랙이 가용 폭을 채우고 나머지는 그 비율만큼 짧아진다. 그래야 계좌 간 한도 크기 차이가 그림에서 보인다. 막대마다 배율을 달리하면 이 층의 존재 이유가 사라진다.
- 왼쪽 끝에 기납입액 구간을 사선 해칭으로 표시할 수 있다(선택). 표시하면 "이미 넣은 것 + 이번에 넣을 것 + 남은 것"이 한 줄에 다 들어온다.
- 각 막대 아래 캡션에 `LawChip`이 붙는다. **차트 자체가 근거를 달고 있다** — 고지 ③이 별도 블록으로만 존재하지 않는다.
- 배분액이 0인 계좌도 막대를 그린다. 트랙만 남고 채움이 없으며 캡션은 `이 배분에서는 배분하지 않음`. 계좌를 화면에서 지우면 "왜 빠졌는지"를 사용자가 알 수 없다.

### 5.5 C-3 — 스택바 3행 비교

`ScenarioStackBar`(design-system 5.21절). 같은 폭(= 월 납입 여력 100%)의 가로 막대를 시나리오 수만큼 세로로 쌓는다.

- 세로로 쌓이므로 조각 경계가 위아래로 정렬된다. "연금저축이 대안1에서 얼마나 길어졌는가"를 눈으로 잰다.
- 우측에 절감세액과 기본안 대비 차액.
- 현재 선택된 행에 `▸` + 행 바탕 `accent-subtle`. **행을 클릭하면 C-1 도넛과 C-2 막대, 그리고 계좌별 중도 불이익 안내(4.7절)가 그 배분안의 것으로 바뀐다.** 별도의 배분안 선택기를 두지 않는 이유다(4.1절).
- 행 우측에 그 배분안의 중도 불이익 안내 개수를 작은 표식으로 단다(4.7절 (c)).
- 미배분 잔액이 있는 시나리오는 `data-unallocated` 조각으로 보인다. **"여력을 다 못 쓰는 배분"이 그림에서 바로 보인다.**

**측정 근거 — 왜 소형 도넛이 아니라 스택바인가.** 폭 640px의 결과 패널에서 스택바 한 행의 유효 길이는 약 480px다. 계좌 간 5%p 차이가 24px로 나타나 육안으로 확실히 구분된다. 같은 5%p를 외경 96px 소형 도넛에서 보면 호 길이 약 15px에 원근 왜곡까지 겹쳐 구분되지 않는다. 결과 패널이 480px 아래로 내려가면 유효 길이가 320px가 되어 5%p가 16px — 아직 구분되지만 라벨이 조각 안에 못 들어간다. **이 지점이 1024px에서 단일 열로 바꾸는 근거다**(1.3절).

### 5.6 색과 라벨 규약

- 조각·채움 색은 계좌 고정 매핑(`data-pension` / `data-irp` / `data-isa`), 미배분은 `data-unallocated`, 트랙의 빈 부분은 `data-track`. **C-1·C-2·C-3와 `[4-D]` 표가 전부 같은 색을 쓴다.** 하나라도 어긋나면 넷 다 못 읽는다.
- 도넛 압출 측면은 상단면 색의 명도 −18%. 별도 토큰을 만들지 않는다.
- 도넛 지시선은 `border-strong` 1px, 라벨은 `type-body-s`(계좌명) + `type-num`(금액) + `type-caption`(비율).
- 스택바 조각 안에 라벨이 들어갈 폭이면 계좌명 축약 + 비율을 조각 안에, 안 되면 조각 위 헤더 행에 한 번만 표시한다. **행마다 라벨 유무가 달라지지 않는다** — 행마다 다르면 비교가 흔들린다.
- **개정예고 시나리오의 해칭:** 도넛은 **상단면에만** 45° 사선 해칭(측면에 얹으면 원근 때문에 패턴 간격이 왜곡된다), C-2는 채움 전체에, C-3는 해당 행 전체에 + 행 좌측 `ProposedBadge`.

### 5.8 검토했으나 채택하지 않은 것

- **도넛 아래 별도 검산 스트립(원안의 A4).** C-2 한도 트랙 막대가 같은 역할을 하면서 잔여 한도까지 담는다. 두 개를 다 두면 같은 값을 세 번 그리게 된다.
- **소형 도넛 3개 비교(원안의 대안 비교 방식).** 외경 96px에서 5%p가 구분되지 않아 "선택지 비교"가 이름만 남는다(5.5절 측정). C-3 스택바로 대체했다.
- **2D 도넛만 쓰는 안(시안 B 원안).** 입체를 버리면 왜곡이 사라지지만 소유자가 원한 첫인상도 사라진다. 6절 참조.
- **도넛 중앙에 절감세액 배치.** 금액이 도형에 종속된다. 절감세액은 `[4-B]` `AmountCard`로 도형 밖 화면 최대 요소에 두고, 도넛 중앙에는 **월 배분 총액**을 넣는다.
- **도넛/막대 전환 토글.** 두 차트를 각각 만들고 유지해야 하며, 사용자가 토글을 누르지 않으면 한쪽을 영영 못 본다. 세 층을 다 보여주는 편이 낫다.

### 5.9 배분 대상이 아닌 계좌 (3단계 구현에서 드러난 공백)

**설계가 정의하지 않았던 경우다.** 8.4(b)는 전면 차단을 다루고 4.5절은 "ISA 계좌가 없다"만 다뤘다. 그런데 **계좌는 있는데 법령 요건 때문에 한 계좌만 배분 대상에서 빠지는** 경우가 실재한다 — 금융소득종합과세 대상자의 ISA(`isa.exclusion.financial_income_taxpayer`), 연령 요건 미달의 ISA(`isa.eligibility`). 계약의 `AccountEligibility.eligible: false`가 이 상태다.

**`web-dev`의 임시 판단을 대체로 승인하고 두 가지를 바꾼다.** 바꾼 것은 C-2 트랙 표현과 통지의 색이다(아래 표시).

#### 원칙: 부정적 판정이 아니라 사실 통지

사용자가 무언가를 잘못해서 생긴 상태가 아니다. 법령 요건에 해당하지 않는다는 사실이고, 대개 사용자가 바꿀 수도 없다. **주의 색을 칠하거나 조치를 지시하면 사용자가 자기 상황을 결함으로 읽는다.**

- 색은 `state-info`. **`state-warning`을 쓰지 않는다.** ← `web-dev` 판단에서 바꾼 부분(색을 명시하지 않았던 자리를 확정)
- 문장의 주어는 법령 요건이지 사용자가 아니다.
- **조치를 지시하지 않는다.** `입력을 고쳐 주세요` 류를 붙이지 않는다 — 입력 패널에 이미 그 항목이 있다.
- 컴포넌트는 `EligibilityNote`(design-system 5.24절).

#### 네 곳에서 각각 어떻게 보이는가

| 곳 | 처리 | 근거 |
|---|---|---|
| **C-1 도넛** | 조각을 그리지 않는다. 라벨도 없다 | 도넛은 배분의 구성을 말하는 도형이다. 배분되지 않은 계좌를 0° 조각으로 넣으면 보이지 않으면서 라벨만 떠 혼란만 준다. 그 계좌의 사정은 아래 두 층이 말한다 |
| **C-2 한도 트랙 막대** | **행을 지우지 않는다.** 트랙을 실선으로 채우지 않고 **`border-subtle` 1px 점선 윤곽**만 그린다. 금액 자리에 `배분 대상 아님`, 캡션에 사유 문장 + `LawChip` | ← **`web-dev` 판단에서 바꾼 부분.** 임시 구현은 채움 노드를 그리지 않았는데, 빈 실선 트랙은 "한도는 있는데 이번에 안 채웠다"와 구분되지 않는다. 점선이 두 상태를 가른다. 행 자체를 지우면 계좌 순서가 흔들리고(A3의 정신), 사용자가 그 계좌를 왜 못 보는지 알 수 없다 |
| **C-3 스택바** | 조각을 그리지 않고 **범례에서도 뺀다.** 스택바 영역 위에 한 줄: `ISA는 이번 계산에서 배분 대상이 아니어서 아래 비교에 나타나지 않습니다` | 배제는 배분안마다 달라지지 않고 시나리오 전체에 걸린다. 행마다 반복하면 소음이고, 영역 위 한 줄이면 세 행 모두에 적용된다는 것이 분명하다 |
| **`[4-D]` 계좌별 표** | 행을 유지하고 금액 칸에 `배분 대상 아님`, 그 아래 사유 줄 + `LawChip` | 표는 차트의 텍스트 대체 경로다(4.3절). 차트에서 조각이 사라진 계좌의 사정을 여기서 반드시 읽을 수 있어야 한다 |

**사유는 C-2 캡션과 `[4-D]` 표 두 곳에 둔다** — `web-dev` 판단 그대로 승인. 두 곳 모두 그 계좌의 자리 안이라 사유와 계좌가 붙어 있다. 결과 상단 배너로 올리지 않는다: 배너는 전면 차단(8.4(b))과 전 계좌 중도 불이익(4.7(b))이 쓰는 자리이고, 한 계좌의 자격 문제를 거기 올리면 결과 전체가 문제인 것처럼 보인다.

#### 문구 표

| 사유 코드 | 문장 | `LawChip` |
|---|---|---|
| `isa_excluded_financial_income_taxpayer` | `직전 3개 과세기간 중 금융소득종합과세 대상이었던 경우 ISA 과세특례가 적용되지 않습니다. 그래서 이번 계산의 배분 대상이 아닙니다.` | `조특법 §129조의2 ①` |
| `isa_excluded_age` | `ISA 가입에 필요한 연령 요건에 해당하지 않아 이번 계산의 배분 대상이 아닙니다.` | `조특법 §91조의18 ①1·2` |

`제외되었습니다`처럼 처분받은 인상을 주는 수동태를 쓰지 않는다. `배분 대상이 아닙니다`는 상태 서술이다.

#### 세 계좌가 모두 배제되면

그때는 배분할 곳이 없으므로 8.4(b) 전면 차단으로 넘어간다. **경계는 "배분 대상 계좌가 0개인가"다.** 1개 이상이면 정상 상태이고 이 절의 처리를 쓴다.

### 5.10 `credit_eligible_limit_remaining_krw`를 "잔여 한도"로 부르지 않는다

계약 5.3절이 명시한다 — 이 값은 **"추가로 인정될 여지"이지 배분 상한이 아니다.** 개정안의 청년 IRP 우대가 적용되면 추가 IRP 납입이 이미 인정된 연금저축 기납입분을 공제 풀에서 밀어내고 그만큼이 높은 율로 갈아탄다. 그래서 **배분액이 이 값을 넘을 수 있다.**

**화면이 이 값을 "잔여 한도"로 이름 붙여 배분액 옆에 놓으면 사용자에게 모순으로 보인다.** 세 가지로 정리한다.

**(1) 트랙 기준에서 뺀다.** C-2 트랙은 `contribution_limit_remaining_krw`(납입 잔여 한도)만 쓴다. 트랙-채움 관계는 **넘을 수 없는 상한**에서만 성립하며, 채움이 트랙을 넘는 그림은 그 자체로 거짓말이다.
**3단계 확인 사항:** 구현이 연금계좌 트랙에 공제 쪽 값을 쓰고 있으면 납입 쪽으로 바꿔야 한다. ISA는 공제 값이 항상 `null`이라 이미 납입 기준일 것이므로, 두 축이 섞여 있었는지 확인이 필요하다.

**(2) 이름을 바꾼다.** 화면 명칭은 **`세액공제가 더 인정될 수 있는 금액`**. `잔여 한도`·`남은 한도`·`한도`를 단독으로 붙이지 않는다. 위치는 C-2 캡션의 둘째 줄과 `[4-D]` 표의 보조 줄이며, **배분액과 나란한 열에 놓지 않는다** — 나란히 놓는 순간 "이만큼까지 넣을 수 있다"로 읽힌다.

**(3) 넘는 경우를 감추지 않는다.** 배분액이 이 값을 넘으면 캡션에 한 줄을 덧붙인다.

```
└ 세액공제가 더 인정될 수 있는 금액 {금액} (연금저축·IRP 합산)
  이 배분은 그 금액을 넘습니다 — 추가 납입이 이미 인정된 다른 계좌의
  납입분을 공제 대상에서 밀어내고, 밀려난 만큼에 더 높은 공제율이
  적용되기 때문입니다.
  [정부안 · 국회 통과 전]  [소득세법 §59조의3 ①]
```

이 현상은 개정안 시나리오에서만 나타나므로 `ProposedBadge`가 함께 붙는다. **4단계 교차검증이 잡은 계산 버그(M1)와 같은 뿌리이므로, 화면이 이 미묘함을 감추면 같은 오해가 사용자 쪽에서 반복된다.**

**(4) 합산 금지를 캡션이 말한다.** 연금저축과 IRP는 공제 한도를 같은 풀에서 본다(계약 5.3절의 `credit_limit_shared_with`). 그래서 이 값은 **계좌별로 두 번 적지 않고 연금계좌 묶음에 한 번만** 적고, 뒤에 `(연금저축·IRP 합산)`을 붙인다. 계좌마다 적으면 사용자가 둘을 더한다.

### 5.11 ISA 비과세 한도를 보인다

설계에 없어 화면이 그리지 않던 값이다(`AccountLimit.tax_free_limit_krw`). **보인다.**

근거: 이 제품은 ISA를 배분 대상에 넣으면서 그 절세 효과를 금액으로 내지 못한다 — 미래 운용수익의 함수라 룰셋 밖 가정 없이는 계산되지 않고(게이트 2 핵심 발견), 계약도 `quantifiable: false`로 낸다. **그러면 사용자에게 ISA 배분의 근거로 남는 것은 "비과세가 적용되는 한도가 이만큼 있다"는 사실뿐이다.** 그것마저 화면에 없으면 ISA 배분은 이유 없는 숫자가 된다.

- **위치:** C-2의 ISA 막대 캡션 셋째 줄, 그리고 `[4-D]` 표의 ISA 행 보조 줄. 트랙에는 반영하지 않는다 — 납입 한도와 축이 다르다.
- **문구:** `이 계좌의 비과세 한도 {금액} — 계좌에서 생긴 수익에 적용됩니다. 수익은 계산하지 않으므로 위 절세액에 들어 있지 않습니다.` + `LawChip`(`조특법 §91조의18 ②`).
- **헤드라인 절세액에 더하지 않는다.** 이 값은 한도이지 절감액이 아니다. 둘을 같은 자리에 놓으면 헌장이 금지한 "산정 조건 없는 금액 앞세우기"가 된다.
- `tax_free_limit_krw`가 `null`이면(계좌 유형 미확정) 이 줄을 그리지 않고, `[4-E]`의 `ISA 계좌 유형을 일반형으로 두고 계산했습니다` 항목이 그 자리를 대신한다.

### 5.12 조각이 하나뿐인 도넛

`web-dev`가 실측에서 발견했다 — 한 계좌가 100%를 차지하면 시작점과 끝점이 같아져 **SVG 호가 아무것도 그리지 않는다.** 배제(5.9절)가 생기면 더 흔해지는 경로다.

**렌더링:** 360° 조각은 호가 아니라 **닫힌 고리**로 그린다(design-system 5.20절에 규약으로 박았다). 조각이 둘 이상이어도 각도가 0에 가까운 조각은 최소 2°를 보장한다 — 보이지 않는 조각보다 약간 부정확한 조각이 낫고, 정확한 값은 라벨이 말한다.

**"나눈다"는 은유가 성립하는가 — 부분적으로만.** 조각이 하나면 도넛은 나눔을 보여주지 못한다. 그럼에도 **도넛을 그린다.** 근거 셋.

1. **도넛은 "나눔"이 아니라 "전체의 구성"을 말하는 도형이다.** 구성이 한 조각인 것도 정직한 구성 표현이고, 꽉 찬 고리는 "전액이 한 곳으로 간다"를 즉시 전달한다.
2. **상태 사이에 레이아웃이 튀면 안 된다.** 배분 대상이 2개였다가 1개가 되는 순간 도넛이 사라지면 화면이 통째로 뛴다. 실시간 갱신 구조에서 그것은 사용자가 무언가를 망가뜨렸다는 인상을 준다 — 3.5절과 8.4(a)에서 반복해 경계한 문제다.
3. **정보의 무게중심은 어차피 C-2로 옮겨간다.** 그 사실을 캡션이 안내한다.

**캡션(조각이 하나일 때만):** `이번 배분은 전액이 {계좌}로 갑니다. 계좌별 한도와 남은 여력은 아래에서 볼 수 있습니다.`

중앙 값은 그대로 월 배분 총액이다. 조각 라벨은 하나만 그린다.

### 5.13 확정안에 남는 약점 (감수한 것)

숨기지 않고 적는다. 나중에 이 결정을 다시 열 사람이 알아야 한다.

1. **도넛의 원근 왜곡은 제거되지 않는다.** A1·A3·A5로 최소화하고 C-2로 검산 경로를 두었을 뿐이다.
2. **모바일에서 A2(직접 라벨)가 약해진다.** 색 + 번호 연결로 대체하지만 조각과 라벨의 거리가 멀어진다.
3. **세로가 길다.** 세 층 + 표 + 고지 블록 넷이 쌓인다. 데스크톱 첫 화면에서 고지 ③④⑤에 도달하려면 스크롤이 필요하다. 7절에서 대응했다.
4. **구현 비용이 세 층만큼 든다.** 특히 입체 도넛은 SVG 패스를 직접 작도해야 하고 접근성 대체 표현을 따로 만들어야 한다(`[4-D]` 표가 그 역할을 한다).

## 6. 결정 기록 — 차트 형태 (2026-08-08)

**판단이 갈렸다는 사실 자체가 기록으로 남아야 한다.**

| 주체 | 입장 |
|---|---|
| 소유자(최초) | 3D 파이 차트 |
| 관리자 | 3D 원근이 면적을 왜곡한다 / 비중보다 절감세액이 주인공이어야 한다 / 파이는 여러 안을 비교하기 어렵다 |
| `designer`(이 유닛) | 두 시안을 제시하고 **시안 B(2D 한도 트랙 막대)를 권고**했다 |
| 소유자(최종) | **절충안 채택** — 주 시각화는 입체 도넛, 가로 막대는 전부 시안 B 방식 |

**소유자가 이 유닛의 권고를 따르지 않았고, 그 판단에는 근거가 있다.** 이 유닛은 왜곡 위험을 가장 무겁게 봤고, 소유자는 실제 렌더링을 보고 첫인상의 가치와 왜곡 비용을 함께 저울질했다. 절충안은 이 유닛이 초안의 권고 절에 "가능하지만 두 차트를 다 만들어야 해 구현 비용 때문에 권하지 않는다"고 적었던 방향이며, 소유자가 그 비용을 감수하기로 한 것이다. 다만 확정안은 초안의 절충안(도넛/막대 토글)과 달리 **토글이 아니라 세 층을 모두 표시**하므로, 사용자가 토글을 누르지 않아 한쪽을 못 보는 문제는 없다.

**절충으로 해소된 것:** 시안 A의 단점 중 "한도 대비 여력을 못 보여준다"와 "동시 비교가 안 된다"가 사라졌다. 검산 경로도 유지된다 — C-2가 왜곡 없는 길이를 쓰므로 원안 A4의 역할을 그대로 한다.

**절충으로 해소되지 않은 것:** 도넛 자체의 원근 왜곡(5.13절 1)과 모바일에서 직접 라벨이 약해지는 문제(5.13절 2). 완화 장치 A1·A3·A5는 그대로 유지하는 조건으로 감수했다.

**이 결정을 다시 열어야 하는 때:** 사용자 테스트에서 도넛의 면적을 오독하는 사례가 관측될 때, 모바일 이탈률이 데스크톱과 유의하게 갈릴 때, 또는 구현 단계에서 입체 렌더링 비용이 일정을 압박할 때. 그때 C-1만 2D 도넛으로 낮추면 C-2·C-3는 그대로 살아남는다 — **층이 분리되어 있어 되돌리는 비용이 작다는 것이 이 구조의 부수적 이점이다.**

## 7. 결과 패널의 세로 길이와 스크롤

확정안은 세 층을 쌓으므로 결과가 길다. 고지가 스크롤 아래로 밀리는 것을 방치하면 4.2절의 배치 명세가 사실상 무력해진다.

### 7.1 도달성 기준 — 게이트 2 D11 판정에 따름

관리자가 헌장의 "같은 화면에서 함께 표시"에 선을 그었다. 네 조건이며, 이 설계가 각각을 어떻게 만족하는지 대조한다.

| D11의 선 | 이 설계 | 확인 |
|---|---|---|
| 금액과 조건 한 줄은 **같은 뷰포트** | `AmountCard`의 슬롯3이 금액 바로 아래 24px 이내. 슬롯을 비울 수 없는 컴포넌트다(design-system 5.6절) | 충족 |
| 가정·법령·한계는 스크롤 아래여도 되나 **같은 페이지에 기본 펼침** | `[4-E]` `AssumptionBlock`·`[4-F]` `BasisBlock` 모두 **기본 상태가 펼침**, `[4-G]` `LimitNote`는 접기 자체가 없음 | 충족 |
| **클릭·토글·모달·별도 페이지 뒤에 숨기면 위반** | 고지 여섯 요소 중 어느 것도 모달·별도 페이지에 없다. `LawChip`을 눌러 이동하는 곳도 같은 페이지의 `[4-F]`이고, 그 블록은 누르지 않아도 이미 펼쳐져 있다 | 충족 |
| 성격·자격 고지는 스크롤과 무관하게 **항상 노출** | `[4-A]` `DisclosureBanner`는 접기·닫기가 없고 결과 패널 안에서 sticky다(7.2절) | 충족 |

**접기 기본값 재확인(관리자 요청).** 접기가 가능한 블록은 `[4-E]`와 `[4-F]` 둘뿐이고 **둘 다 기본값이 펼침**이다. design-system 5.10·5.11절에 컴포넌트 명세로 박혀 있고, 4.2절 표의 "기본 상태" 열이 같은 값을 말한다. 접힌 상태에서도 `[4-F]` 헤더에 `적용 조항 n건 · 2026 과세연도 기준`이 남는다. **구현에서 "접힘"을 초기값으로 두면 규약 위반이며 11.3절 점검 항목이다.**

- 고지 ③④⑤의 전문은 스크롤 아래에 있다. 이를 **접혀 있는 것으로 오인하지 않게** 7.2절의 장치를 둔다.

### 7.2 장치

- **결과 패널 상단에 앵커 줄.** `[4-A]` 바로 아래에 `type-caption` 한 줄로 `이 결과의 조건 · 적용 법령 · 한계는 아래에 모두 표시됩니다`를 두고, `조건`·`법령`·`한계`가 각각 해당 블록으로 스크롤하는 링크다. **정보를 요약하지 않고 위치만 알린다** — 요약이 전문을 대신하면 각주화가 시작된다.
- **데스크톱 결과 패널은 자체 스크롤을 갖되 `[4-A]`는 패널 안에서 sticky**로 상단에 붙는다. 차트를 스크롤해도 성격·자격 고지가 화면에서 사라지지 않는다.
- **모바일 바텀시트도 같다.** 시트 상단에 `[4-A]`가 고정되고 그 아래가 스크롤된다.
- 스크롤 위치는 시나리오를 바꿔도 유지한다. C-3에서 행을 눌렀을 때 화면이 위로 튀지 않는다.

### 7.3 인쇄 · 공유 이미지에서

인쇄(`@media print`)에서는 모든 접기 블록이 펼쳐진 상태로 나오고, sticky를 해제하며, 차트는 도넛 + C-2만 남기고 C-3는 표(`[4-D]`)로 대체한다. 공유 이미지의 고지 처리는 9절에 있다.

## 8. 다섯 상태

**입력 패널과 결과 패널을 하나의 화면으로 다루되, 상태는 결과 패널이 갖는다.** 입력 패널은 항상 표시되고 사라지지 않는다 — 이것이 통합 구조의 핵심이다.

| 상태 | 언제 | 입력 패널 | 결과 패널 |

| 빈 | 초기화 직후, 또는 첫 진입 | 전부 기본값·빈값 | 8.2절 (입력 부족의 특수형) |

**설계 규칙 일곱.**

1. **결과 자리에 가짜 숫자를 놓지 않는다.** 예시 값·평균값·데모 결과를 보여주지 않는다. 사용자가 자기 결과로 오인하는 순간 헌장의 "부당한 기대" 경계를 스스로 넘는다. 자리표시자는 **무채색 도형 하나**이고 눈금·범례·숫자가 없다.
   **자리표시자가 도넛이나 막대 모양을 흉내내지 않는다.** 빈 도넛을 그리면 "배분이 0원인 결과"로, 빈 트랙 막대를 그리면 "한도를 하나도 못 채운 결과"로 읽힌다. 확정안의 세 층 어느 것과도 닮지 않은 중립 도형을 쓴다.
2. **체크리스트가 주인공이다.** "무엇을 더 넣으면 결과가 나오는가"라는 질문에 항목 단위로 답한다. 각 행은 버튼이고, 누르면 해당 필드로 스크롤 + 포커스가 간다.
3. **이미 채운 항목도 보여준다.** 남은 것만 보여주면 진행감이 없다. `2 / 4`와 진행 막대가 남은 거리를 알려준다.
4. **`자금 사용 시점`은 기본 선택이 없으므로 사용자가 고르기 전까지 항상 미충족이다.** 초판은 이 자리에 `투자 성향`을 두고 `중립형 (기본)`으로 미리 채웠으나, 게이트 2 D10으로 필드가 바뀌면서 그 처리가 사라졌다 — 계약이 기본값 생성을 금지한다. `아직 모르겠다`도 **사용자가 눌러야** 충족된다.
   그래서 첫 진입 시 남은 항목이 하나 늘었다. 이 항목의 체크리스트 행에는 다른 항목과 달리 한 줄 설명을 붙인다: `계산 금액은 바뀌지 않고, 배분안을 보여주는 순서와 안내가 달라집니다.` **필수인 이유를 묻기 전에 답한다.**
5. **진행을 막지 않는 항목은 목록에 올리지 않는다.** 초판은 기납입액을 `올해 이미 넣은 금액` 하나로 묶어 목록에 넣고 "세 필드 중 하나라도 만졌으면 충족"으로 다뤘다. 둘 다 틀렸다 — 요구사항 AC상 이 값은 진행을 막지 않으므로 애초에 목록에 있을 것이 아니었고, "만졌는가"로 충족을 판정하는 것은 **상호작용에서 확인 의사를 추론**하는 것이라 3.2절의 명시적 진술 원칙에 어긋난다. 목록에서 뺐고, 값이 전부 0인 채로 결과가 나오면 `[4-E]`가 그 사실과 영향을 적는다.
   같은 이유로 **조건부 필수 항목도 분모에 넣지 않는다.** 진행 막대가 뒤로 가는 것처럼 보이면 안 된다. 목록 아래 별도 줄로 붙인다 — 3.5절. 네 항목을 다 채웠는데 조건부 필수가 비어 있으면 `4 / 4 · 추가 항목 1개`로 표시한다.
6. **고지 ①②를 여기서도 표시한다.** 결과가 없어도 서비스의 성격 표시는 필요하다. 사용자가 소득을 입력하기 **전에** 이 서비스가 무엇이 아닌지 알아야 한다.
7. **기대 설정 블록**으로 "무엇이 나올지"를 미리 알린다. 소득 같은 값을 입력하려면 그 대가가 무엇인지 알아야 한다.

**부분 충족 시의 미리보기는 하지 않는다.** 예컨대 나이·소득만 있고 납입 여력이 없을 때 "한도만 계산해서 보여주기"를 할 수 있지만, 하지 않는다. 소유자가 확정한 갱신 시점 규칙("필수 항목이 다 채워지면 그때부터")과 어긋나고, 중간 결과가 최종 결과로 오인된다.

**예외가 하나 있고, 그것은 화면에 보이지 않는다.** 나이와 ISA 입력이 채워지면 화면은 `computeFundUseHorizonBoundaries`를 한 번 부른다(3.4절). 응답은 선택지 보조 캡션의 연수를 채우는 데만 쓰고 결과 패널에는 아무것도 표시하지 않는다. **이것은 배분을 계산하는 진입점이 아니므로 미리보기가 아니다.** 사용자가 보는 상태는 여전히 입력 부족이다.

### 8.2 빈 상태

초기화 직후 또는 첫 진입. **입력 부족 상태의 특수형**으로 다루되 셋이 다르다.

- 체크리스트가 `0 / 4`이고 진행 막대가 비어 있다. **초판은 `투자 성향`이 기본값으로 채워져 있어 `1 / 5`에서 시작했으나, 이제 네 항목 전부가 미충족이다** — 기본값 있는 항목이 사라지고(D10) 진행을 막지 않는 항목이 목록에서 빠졌다.
- 체크리스트 위에 진입 안내(2.2절) 두 문장이 펼쳐져 있다. 값이 하나라도 들어가면 접힌다.
- 첫 항목(`나이`)에 자동 포커스를 **주지 않는다.** 모바일에서 키보드가 즉시 올라와 화면 절반이 가려지고, 스크린리더 사용자가 페이지 구조를 파악하기 전에 필드로 끌려간다.

### 8.3 로딩 상태

두 종류를 구분한다.

**(a) 초기 룰셋 로드** — 페이지 진입 시 1회. 입력 패널은 즉시 상호작용 가능하게 렌더하고, 결과 패널만 `Skeleton`으로 둔다. 300ms 안에 끝나면 스켈레톤을 아예 표시하지 않는다(깜빡임 방지). 3초를 넘기면 `룰셋을 불러오는 중입니다` 캡션을 추가한다.

**(b) 재계산** — 값 변경 후 디바운스 만료. **직전 결과를 지우지 않는다.**
- 결과 영역 투명도 92%, 우상단에 `갱신 중` 인디케이터(회전 아이콘 + 텍스트).
- 계산이 120ms 안에 끝나면 인디케이터를 표시하지 않는다.
- 새 값이 들어오면 변경된 금액에 220ms 배경 하이라이트. 숫자 롤링 없음.
- **차트 세 층은 갱신 중에도 직전 형상을 유지하고, 새 값이 오면 도넛은 조각 각도만·막대는 길이만 240ms로 옮긴다.** 도넛을 지웠다가 다시 그리면 회전처럼 보여 A5(회전 금지)가 무너진다.
- `aria-live="polite"`로 `계산 결과가 갱신되었습니다`.

**(c) 경계값 호출** — `computeFundUseHorizonBoundaries` 1회(3.4절). **결과 패널에 로딩 표시를 하지 않는다.** 결과 패널은 입력 부족 상태 그대로다. 선택지의 보조 캡션 자리만 채워지며, 그전까지 그 자리는 빈 줄로 예약되어 있어 레이아웃이 흔들리지 않는다. 호출이 실패하면 캡션 없이 라벨만 남는다 — **라벨이 수치 없이도 완결되므로 선택은 그대로 가능하다.** 이것이 3.4절에서 라벨에 숫자를 넣지 않기로 한 결정의 실질적 이득이다.

**스켈레톤 안에 숫자 모양을 그리지 않는다**(design-system 5.15절).

### 8.4 오류 상태

세 층위로 나눈다.

**(a) 필드 단위 오류** — 음수, 정수 아님, 범위 초과.
- `자금 사용 시점`은 선택지가 네 개뿐이라 라디오 UI에서 잘못된 값이 나올 수 없다. 그럼에도 계약이 `invalid_enum` 오류를 정의했으므로(예: 저장된 이전 세션 값이 계약 개정으로 무효가 된 경우) 화면은 그 오류를 받으면 **값을 조용히 고르지 않고 선택을 비운 뒤 입력 부족 상태로 되돌린다.** 화면이 대신 고르는 순간 기본값 금지가 무너진다.
- 해당 필드가 오류 상태(테두리·바탕·메시지).
- 결과 패널은 **직전 결과를 유지**하고 상단에 `InlineAlert(error)`를 띄운다: `입력값에 확인이 필요한 항목이 있어 아래 결과를 갱신하지 않았습니다. → 항목 보기`. 버튼을 누르면 첫 오류 필드로 이동.
- 직전 결과가 없으면(첫 계산 전) 입력 부족 상태로 돌아가고 체크리스트의 해당 항목이 오류 표시가 된다.

**(b) 계산 불가** — 최소 가입 연령 미달 등 법령 조건에서 나온 차단. 요구사항 4절의 "오류·안내 화면"이 여기에 대응한다. **별도 페이지를 만들지 않는다.**

```
┌─────────────────────────────────────────────────────────────────┐
│ ⓘ (DisclosureBanner — 유지)                                     │
├─────────────────────────────────────────────────────────────────┤
│  ⚠ 입력한 조건에서는 배분을 계산할 수 없습니다                     │  InlineAlert(error)
│                                                                 │
│  사유: 입력한 나이가 이 계좌의 가입 가능 연령에 이르지 않았습니다.    │
│  근거: [조특법 §91조의18 ①1·2]                                   │  ← LawChip 필수
│                                                                 │
│  [ 나이 입력으로 이동 ]                                           │  secondary 버튼
│                                                                 │
│  계산할 수 있는 다른 계좌가 있으면 아래에 표시됩니다.                │
│  ─────────────────────────────────────────────────              │
│  (일부 계좌만 가능하면 그 계좌들에 대한 결과를 여기에 그린다)          │
└─────────────────────────────────────────────────────────────────┘
```

- **차단 사유에 반드시 `LawChip`을 붙인다.** 서비스가 임의로 막는 것이 아니라 법령 조건임을 보인다. 이것이 헌장의 "판단의 주체가 법령임을 화면이 스스로 보인다"의 오류 상태 판본이다.
- **부분 계산이 가능하면 부분 결과를 보여준다.** 세 계좌 중 하나만 막힌 경우 전체를 차단하지 않는다.
- 복귀 경로(해당 입력으로 이동)를 버튼으로 제공한다(요구사항 AC).

**(c) 치명 오류** — 룰셋 로드 실패, 계산 엔진 예외.
- 결과 패널 전체를 `InlineAlert(error)`로 대체: `계산에 필요한 세법 규칙을 불러오지 못했습니다. 결과를 표시하지 않습니다.` + `[ 다시 시도 ]`.
- **부분 결과나 캐시된 이전 결과를 보여주지 않는다.** 근거를 확인할 수 없는 숫자를 화면에 두지 않는다는 것이 이 제품의 원칙이다(design-system 5.9절 `LawChip` 오류 규약과 같은 판단).
- 입력 패널은 그대로 두어 사용자가 입력한 값을 잃지 않게 한다.

### 8.5 정상 상태

4절 골격 + 5절 차트 확정안(C-1 도넛 → C-2 한도 트랙 막대 → C-3 스택바 3행).

**부분 정상도 정상으로 다룬다.** 배분안이 1개여서 C-3가 그려지지 않는 경우(4.4절), 배분액이 0인 계좌가 있어 도넛 조각이 셋이 아닌 경우, **한 계좌가 배분 대상이 아닌 경우(5.9절)**, **도넛 조각이 하나뿐인 경우(5.12절)**, ISA 만기 전환 행이 없는 경우, 중도 불이익 안내가 하나도 없는 경우(4.7절) — 전부 정상 상태이며 오류 색을 쓰지 않는다.

**배제는 오류가 아니다.** 배분 대상 계좌가 1개 이상이면 결과는 정상이고, 0개일 때만 8.4(b) 전면 차단으로 넘어간다.

**중도 불이익 안내가 있는 것도 정상 상태다.** `Plan.warnings`는 계산이 잘못됐다는 신호가 아니라 결과의 일부다. 안내가 붙었다고 결과 영역을 오류 색으로 물들이지 않는다 — 물들이는 순간 4.7절이 막으려던 "겁주는 화면"이 된다.

## 9. 저장 · 공유

요구사항 유저플로우 6과 AC("생성되는 결과물에 개인 식별 가능 입력값이 포함되지 않는다")를 따른다.

- 트리거: `[4-H]`의 `공유용 이미지 만들기` 버튼(secondary).
- 모달(데스크톱) / 바텀시트(모바일)에서 **미리보기를 먼저 보여준다.** 무엇이 나가는지 확인하고 내보낸다.
- **이미지에 포함되는 것:** 계좌별 배분 금액과 비율, 절감세액, 기준 과세연도, 적용 법령 조항 목록, 고지 ①②③(요약)⑤, 개정예고 배지(해당 시), 가명칭 워터마크.
- **배분 대상이 아닌 계좌는 `0원 / 월`로 싣지 않는다.** 금액 자리에 `배분 대상 아님`을 넣고 **사유 한 줄과 `LawChip`을 함께 싣는다**(5.9절 문구 표 그대로).
  근거: `0원`은 "이 사람이 그 계좌에 넣지 않기로 했다"로 읽힌다. 실제로는 넣을 수 없는 것이고, 둘은 완전히 다른 사실이다. **이미지는 화면 밖으로 나가면 정정할 기회가 없으므로**, 화면보다 오히려 더 엄격하게 사유를 붙인다. 사유 한 줄이 들어갈 자리가 없으면 그 계좌 행을 빼는 것이 `0원`으로 싣는 것보다 낫다.
- 조각이 하나뿐인 도넛(5.12절)도 그대로 싣는다. 캡션 `전액이 {계좌}로 갑니다`가 함께 간다.
- **이미지에 포함되지 않는 것:** 나이, 총급여액, 월 납입 여력, 기납입액 — 즉 **입력값 전부.** 배분 결과 금액은 나가지만 그 근거가 된 개인 값은 나가지 않는다.
  - 주의: 배분 금액의 합이 곧 월 납입 여력이다. 미리보기 아래에 이 사실을 캡션으로 알린다: `배분 금액의 합계로 월 납입 여력이 추정될 수 있습니다.` 사용자가 알고 내보내게 한다.
- **URL에 입력값을 담지 않는다.** 쿼리스트링·해시·인코딩 어떤 형태로도 담지 않는다(designer 금지사항).
- 링크 공유를 유지한다면 그 링크가 담을 수 있는 것은 결과 없는 서비스 진입 링크뿐이다. `open_questions`에 올렸다.

## 11. 점검표 (`qa` 게이트 4용)

### 11.1 문구

- [ ] 서비스 명칭·헤더·제목에 세무/세무사/택스/TAX/절세/컨설팅/환급/상담/자문/대행이 없다
- [ ] "절세액"이 계산 결과를 가리키는 명사로만 쓰였고 서비스 제공 행위와 결합하지 않았다
- [ ] 2인칭 명령형 문장이 없다 ("넣으세요", "가입하세요", "하시면 유리합니다")
- [ ] 시나리오 라벨에 "추천"·"최적"·"권장"이 없다
- [ ] 가장 큰 금액 옆 24px 이내에 산정 조건 캡션이 있다
- [ ] 고지 ①②⑤가 접히지 않는다
- [ ] 고지 ③④의 블록이 기본 펼침이다
- [ ] 모든 금액 행에 `LawChip`이 있거나 `[4-F]`로 연결된다
- [ ] 개정예고 시나리오에 배지 + 해칭 + 캡션이 모두 있다
- [ ] 오류·차단 화면에 `LawChip`이 있다
- [ ] 공유 이미지에 고지 ①②③(요약)⑤가 포함된다
- [ ] 공유 이미지·URL에 나이·소득·납입 여력이 포함되지 않는다
- [ ] 금융사 로고·브랜드 색·상품명이 없다
- [ ] 자격자(세무사·회계사)를 연상시키는 시각 요소가 없다

### 11.2 차트 확정안 (5절)

- [ ] 세 층(C-1 도넛 → C-2 한도 트랙 막대 → C-3 스택바)이 이 순서로 모두 있다
- [ ] 도넛 기울기 15°·두께 8%·시작각 12시가 모든 뷰포트에서 동일하다 (A1)
- [ ] 도넛 조각 순서가 연금저축 → IRP → ISA → 미배분으로 고정이고 값 크기순으로 재정렬되지 않는다 (A3)
- [ ] 도넛에 회전·확대 애니메이션이 없고 값 변화 시 조각 각도만 바뀐다 (A5)
- [ ] 데스크톱·태블릿에서 도넛 조각에 금액과 비율이 직접 라벨링되어 있다 (A2)
- [ ] C-2 세 막대가 공통 배율이다 (같은 픽셀 = 같은 금액)
- [ ] C-2 각 막대 캡션에 `LawChip`이 붙어 있다
- [ ] C-3 행을 누르면 C-1·C-2가 그 시나리오로 바뀌고 스크롤 위치가 유지된다
- [ ] C-1·C-2·C-3·`[4-D]` 표의 계좌 색이 모두 같다
- [ ] 개정예고 해칭이 도넛 **상단면에만** 적용되고 측면에는 없다
- [ ] 좁은 폭에서 C-2 또는 C-3가 제거되지 않는다
- [ ] 입력 부족 상태의 자리표시자 도형이 도넛·막대 모양을 흉내내지 않는다

### 11.3 `fund_use_horizon`과 중도 불이익 안내 (게이트 2 D10 / D11)

- [ ] 선택지 라벨에 연수가 하드코딩되어 있지 않다 (숫자는 전부 `fund_use_horizon_boundaries`에서 온다)
- [ ] 보조 캡션이 없어도 라벨만으로 선택이 가능하다
- [ ] 미리 선택된 기본값이 없다. `아직 모르겠다`도 눌러야 충족된다
- [ ] `이 선택은 계산되는 금액을 바꾸지 않습니다`가 입력 옆·`[4-E]`·선택 변경 시 세 곳에 있다
- [ ] 경계 연수를 `computeFundUseHorizonBoundaries`로 얻고, `compute`의 부산물을 꺼내 쓰지 않는다
- [ ] 경계값 호출의 응답이 결과 패널에 표시되지 않는다
- [ ] 중도 불이익 안내에 금액이 없다
- [ ] 안내 문구에 "손해"·"위험"·"주의하세요"·느낌표·2인칭 지시가 없다
- [ ] 안내마다 `LawChip`이 붙어 있다
- [ ] 배분액이 0인 계좌에 안내가 붙지 않는다
- [ ] `severity: info`인 안내에 `자금 사용 시점을 밝히지 않아 판정하지 않았습니다` 문두가 있다
- [ ] `all_accounts_have_early_exit_penalty`가 차트보다 위(`[4-W]`)에 있고, "다른 안을 고르라"고 읽히지 않는다
- [ ] 안내가 없을 때 "문제 없음" 류의 확인 문구를 띄우지 않는다
- [ ] `baseline_reordered_by_fund_use_horizon`일 때 기본안이 최대 절세액이 아니라는 사실이 C-3 위에 표시된다
- [ ] `[4-E]`·`[4-F]`의 초기 상태가 **펼침**이다 (접힘으로 구현하면 D11 위반)

### 11.4 ISA 만기 전환과 조건부 입력 (게이트 1 D3 / 게이트 2)

- [ ] `ISA 만기 전환 여부 = 예`일 때 `전환한 자금을 받을 계좌`(IRP / 연금저축)가 나타난다
- [ ] 목적지 기본 선택이 `IRP`이고, 만지지 않았으면 `[4-E]`에 그 사실이 항목으로 뜬다
- [ ] `아니오`로 되돌리면 전환 관련 값이 전부 초기화되고 화면에서 사라진다 (값을 숨겨 두지 않는다)
- [ ] 조건부 필수 항목이 `RequirementChecklist`의 분모를 늘리지 않는다
- [ ] ISA 관련 항목의 노출 조건이 `ISA 계좌가 있나요 = 예`이고, 누적 납입액 값에서 추론하지 않는다
- [ ] 네 항목이 다 찼는데 조건부 필수가 비어 있으면 `4 / 4 · 추가 항목 n개`로 표시된다
- [ ] 기납입액이 `RequirementChecklist` 분모에 없다 (진행을 막지 않는 항목이다)

### 11.5 배제·한도 표기 (3단계 구현에서 드러난 공백)

- [ ] 배분 대상이 아닌 계좌가 C-2와 `[4-D]`에서 **행을 유지**하고, C-1·C-3에서는 조각이 그려지지 않는다
- [ ] 그 계좌의 C-2 트랙이 **점선 윤곽**이며 빈 실선 트랙과 구분된다
- [ ] 배제 통지가 `state-info`이고 `state-warning`이 아니다
- [ ] 배제 문구의 주어가 법령 요건이며 조치를 지시하지 않는다
- [ ] 배제 통지에 `LawChip`이 붙어 있다
- [ ] 배분 대상 계좌가 0개일 때만 전면 차단(8.4(b))으로 넘어간다
- [ ] C-2 트랙 기준이 `contribution_limit_remaining_krw`이고 공제 쪽 값이 아니다
- [ ] `credit_eligible_limit_remaining_krw`가 화면에서 `잔여 한도`로 불리지 않는다
- [ ] 그 값이 배분액과 나란한 열에 놓이지 않는다
- [ ] 배분액이 그 값을 넘는 경우 사유 한 줄이 표시되고 `ProposedBadge`가 함께 붙는다
- [ ] 그 값이 연금계좌 묶음에 한 번만 표시되고 `(연금저축·IRP 합산)`이 붙는다
- [ ] ISA 비과세 한도가 표시되고, 헤드라인 절세액에 합산되지 않는다
- [ ] 조각이 하나인 도넛이 닫힌 고리로 그려지고 폭 0이 되지 않는다
- [ ] 공유 이미지가 배제된 계좌를 `0원`으로 싣지 않고 사유와 함께 싣는다
- [ ] 전환 여부를 `예`로 바꾼 직후 직전 결과가 지워지지 않는다
- [ ] `[4-E]`의 모든 항목이 "무엇을 묻지 않았고 그래서 어떻게 계산했는가" 형태이며, 틀릴 수 있는 **방향**이 적혀 있다
