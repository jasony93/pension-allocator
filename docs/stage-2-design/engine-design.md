# 2단계 설계 — 계산 엔진

이 문서는 무엇을 어떻게 계산하는지를 정한다. 입출력 타입은 `engine-interface.md`가 정하고 그쪽이 `web-dev`와의 계약이다.

**세법 수치는 이 문서에 없다.** 한도·비율·경계값은 전부 규칙 id로만 가리킨다. 3단계 구현에서도 코드에 상수로 넣지 않고 `data/tax-rules/`에서 읽는다.

---

## 1. 이 엔진이 푸는 문제

사용자는 **월 납입 여력**이라는 하나의 예산을 갖고 있다. 이 예산을 연금저축·IRP·ISA 세 계좌에 나눠 넣을 때, **당해 과세연도에 확정적으로 계산 가능한 절세액**이 가장 커지는 배분과, 그와 비교할 수 있는 다른 배분들을 함께 산출한다.

엔진은 순수 함수다. 같은 입력이면 항상 같은 출력이다. 네트워크도 전역 상태도 시간(`Date.now`)도 읽지 않는다. 기준 과세연도는 입력으로 받는다. 그래야 4단계에서 `tax-domain`이 골든 케이스로 검증할 수 있다.

### 1.1 왜 "확정적으로 계산 가능한"이라는 단서가 붙는가

세 계좌의 세제 혜택은 성격이 다르다.

| 계좌 | 혜택의 성격 | 당해연도에 금액이 정해지는가 |
|---|---|---|
| 연금저축·IRP | 납입액에 대한 **세액공제** (`pension.credit.rate`, `pension.credit.limit.*`) | **정해진다.** 납입액과 소득만의 함수다 |
| ISA | 계좌에서 발생한 이자·배당의 **비과세와 저율 분리과세** (`isa.tax_free_limit`, `isa.excess.separate_tax_rate`) | **정해지지 않는다.** 금액이 미래 운용수익의 함수다 |

ISA의 절세액을 숫자로 내려면 수익률을 가정해야 한다. **수익률은 세법 값이 아니고 룰셋에 없다.** 엔진이 그 가정을 세우면 출처 없는 숫자가 계산에 들어가고, 제품 원칙 1·2가 우회된다. 특정 상품의 기대수익을 전제하는 순간 원칙 5(특정 금융상품 추천 금지)에도 가까워진다.

**그러므로 엔진은 ISA의 절세액을 산출하지 않는다.** 대신 ISA에 대해서는 아래 둘만 낸다.

- 그 계좌에 **얼마를 더 넣을 수 있는가**(납입 잔여 한도, `isa.contribution.annual_limit`·`isa.account.requirements`)
- 그 계좌에서 **얼마까지가 비과세 한도인가**(`isa.tax_free_limit`) — 금액이 아니라 한도로서만

이 값들은 출력에서 `non_quantified_effects`로 분리되어 나가고, "정량화하지 않은 이유"가 코드로 함께 실린다. 화면이 이 둘을 같은 축의 금액인 것처럼 더하면 안 된다.

**이 비대칭이 이 제품 설계의 뼈대다.** 목적함수가 한 축에서만 정의되므로 "유일한 최적안"이 원리적으로 존재하지 않고, 헌장이 요구하는 "기본안 + 대안 비교" 형태가 편의가 아니라 계산 구조의 귀결이 된다.

### 1.2 목적함수

한 배분안 \(x = (x_{연금저축}, x_{IRP}, x_{ISA})\)에 대해

> **최대화 대상:** 당해 과세연도의 연금계좌 세액공제액 합계(개인지방소득세 포함)

세액공제액은 `pension.credit.rate`의 공제율을 소득으로 판정해 얻고, 여기에 `tax.local.personal_income_surtax`의 부가율을 적용해 실효 절세액을 만든다. **실효율을 상수로 만들지 않는다.** 룰셋의 `derived_effective_rates` 표는 참고용이므로 읽지 않는다(룰셋 자체가 `engine_note`로 그렇게 지시한다).

### 1.3 제약

| # | 제약 | 근거 규칙 |
|---|---|---|
| C1 | 세 계좌 배분액의 합 ≤ 예산 | 입력 |
| C2 | 각 배분액 ≥ 0 (정수, 원) | 입력 |
| C3 | 연금저축 세액공제 대상액은 단독 한도 이내 | `pension.credit.limit.annuity_savings` |
| C4 | 연금저축(단독 한도 이내분) + 퇴직연금의 세액공제 대상액은 합산 한도 이내 | `pension.credit.limit.combined` |
| C5 | ISA 만기 전환이 있으면 C4 위에 추가한도가 더해진다 | `pension.credit.isa_transfer.extra_limit` |
| C6 | 연금계좌 납입 자체의 연간 한도(계좌 합산). 세액공제 한도와 별개다 | `pension.contribution.annual_limit` |
| C7 | ISA 연간 납입한도. 정액이 아니라 가입경과연수와 누적 납입액의 함수다 | `isa.contribution.annual_limit` |
| C8 | ISA 총 납입한도. 재형저축·장기집합투자증권저축 계약금액을 뺀 값이다 | `isa.account.requirements` |
| C9 | 기납입액을 뺀 잔여 한도 안에서만 배분한다 | 위 한도 규칙 전부 |
| C10 | 자격이 없는 계좌에는 배분하지 않는다 | `isa.eligibility`, `isa.exclusion.financial_income_taxpayer` |

C3와 C4의 **적용 순서를 뒤집으면 안 된다.** 단독 한도를 먼저 적용한 뒤 합산 한도를 적용한다. 룰셋이 `pension.credit.limit.combined.value.ordering`에 명시해 두었고, 뒤집으면 연금저축 단독 납입자에게 과대한 공제액이 나온다.

C7은 **상수가 아니라 산식이다.** `isa.contribution.annual_limit.value.formula`를 그대로 평가한다. 룰셋의 `engine_note`가 이 점을 경고하고 있다.

## 2. 알고리즘 선택

### 2.1 선택: 우선순위 기반 순차 충당(greedy fill)

선형계획법도 탐색도 쓰지 않는다. 계좌가 셋이고 각 계좌의 한계 절세율이 구간별 상수이며 제약이 전부 상한형이므로, **정해진 순서로 잔여 한도까지 채우는 것이 목적함수에 대해 최적**이다.

### 2.2 근거 — IRP 우선 충당이 약우월(weakly dominant)이다

세액공제 대상액은 C3·C4에 의해

```
대상액 = min( min(연금저축 납입액, 단독한도) + 퇴직연금 납입액, 합산한도 + 전환추가한도 )
```

예산 1원을 연금저축에 넣으면 **단독 한도까지만** 대상액을 늘린다. 같은 1원을 IRP에 넣으면 **합산 한도까지** 늘린다. 단독 한도는 합산 한도보다 작으므로(룰셋의 두 규칙 값 비교로 런타임에 확인한다), IRP 우선 충당은 어떤 입력에서도 연금저축 우선 충당보다 나쁘지 않고, 연금저축 납입이 단독 한도를 넘는 구간에서는 엄격히 낫다.

**주의: 이 우열은 오직 1.2절의 목적함수에 대한 것이다.** 두 계좌의 수수료·운용 제약·중도인출 규정 차이는 룰셋에 없으므로 엔진이 판단하지 않는다. 그 차이를 사용자가 반영할 수 있도록 3절의 대안 B를 함께 낸다.

한 가지 결과를 미리 적어 둔다. 위 구조 때문에 **기본안에서 연금저축 배분액은 대개 0이 된다.** 이것은 버그가 아니라 목적함수의 정직한 답이며, 정확히 그렇기 때문에 대안 B가 필요하다. 대안 B는 예산이 단독 한도 이내인 구간에서 기본안과 **절세액이 완전히 같다** — 즉 동률 대안이고, 선택은 룰셋 밖 사정을 아는 사용자의 몫이다. 결과를 개인 지시가 아니라 선택지 비교로 제시해야 한다는 헌장 제약과 계산 구조가 여기서 맞물린다.

### 2.3 채택하지 않은 대안

| 방식 | 왜 안 쓰는가 |
|---|---|
| 선형계획 솔버 | 제약이 상한형뿐이고 계수가 구간 상수라 그리디가 이미 최적이다. 외부 의존성이 늘고 결과가 솔버 버전에 따라 흔들려 결정성이 깨진다 |
| 전수 탐색·격자 탐색 | 원 단위 정수 배분에서 탐색 공간이 불필요하게 크고, 격자를 쓰면 격자 크기가 결과를 바꿔 결정성이 격자 선택에 종속된다 |
| 기대효용 최적화 | 수익률·위험 가정이 필요하고 그 값은 룰셋에 없다(1.1절) |

## 3. 배분안 세 가지

엔진은 하나의 답이 아니라 **비교 가능한 배분안 집합**을 반환한다. 각 안은 "무엇을 우선한 안인가"(`priority_basis`)를 근거 규칙 id와 함께 달고 나간다.

| id | 무엇을 우선하는가 | 충당 순서 | 근거 |
|---|---|---|---|
| `max_tax_credit` (**기본안**) | 당해연도 세액공제액 | IRP → 연금저축 → ISA | 2.2절 |
| `annuity_savings_first` | 연금저축 단독 한도를 먼저 채운다 | 연금저축 → IRP → ISA | 단독 한도 이내 구간에서는 기본안과 절세액이 같다. 두 계좌 중 어디에 둘지는 룰셋 밖 사정이다 |
| `isa_first` | ISA 납입 여력을 먼저 채운다 | ISA → IRP → 연금저축 | ISA는 `pension.withdrawal.eligibility`의 연령·기간 요건과 `pension.early_withdrawal.other_income_rate`의 연금외수령 과세가 걸리지 않는 계좌다. 두 규칙 모두 확정 룰셋에 있다 |

**세 안 모두 같은 규칙·같은 한도로 계산된다.** 다른 것은 충당 순서뿐이다.

각 안은 기본안 대비 세액공제액 차이(`delta_vs_baseline`)를 함께 낸다. 이 값은 0 이하다. 화면은 이 값으로 "무엇을 얼마만큼 포기하는 안인지"를 보일 수 있다.

**중복 제거.** 예산이 세 계좌 잔여 한도 합계 이상이면 세 안의 배분 벡터가 같아진다. 이때 엔진은 같은 벡터를 하나로 합치고 `plans` 길이가 1이 되며 `comparison_note_codes`에 사유를 담는다. 같은 숫자를 세 번 보여 비교인 척하지 않는다.

**정렬.** 항상 `max_tax_credit` → `annuity_savings_first` → `isa_first` 고정 순서다. 입력에 따라 순서가 바뀌지 않는다(3.2절).

## 4. 반드시 답해야 했던 네 가지

### 4.1 소득의 기준연도가 규칙마다 다르다

세 규칙이 서로 다른 기간의 소득을 본다.

| 규칙 | 기준 기간 |
|---|---|
| `pension.credit.rate` | **해당** 과세기간 |
| `isa.tax_free_limit` | **직전** 과세기간 |
| `isa.exclusion.financial_income_taxpayer` | **직전 3개** 과세기간 |

**결정: 소득을 하나로 받지 않는다. 필드를 나눈다. 없으면 추정하지 않는다.**

- `profile.current_year_total_salary_krw` — **필수.** `pension.credit.rate` 판정에만 쓴다.
- `profile.prior_year_total_salary_krw` — **선택(null 허용).** `isa.tax_free_limit` 교차확인에만 쓴다.
- `profile.financial_income_taxpayer_last_3_years` — **선택(null 허용).** `isa.exclusion.financial_income_taxpayer` 판정에 쓴다.

**해당 연도 소득으로 직전 연도 소득을 대신하지 않는다.** 한 값을 두 규칙에 돌려쓰면 둘 중 하나는 틀린 해의 소득으로 판정된다. 이 판정 오류는 화면에 드러나지 않으므로 사용자가 알아챌 수 없다.

**서민형/일반형은 엔진이 판정하지 않는다.** ISA 계좌 유형은 사용자가 `accounts.isa.account_type`으로 직접 선언한다(requirements.md 2절에 이미 있는 입력이다). 실제 유형은 가입·연장 시점에 금융회사가 심사해 확정한 것이고, 엔진이 소득으로 다시 판정해 사용자의 사실 진술을 덮어쓰는 것은 옳지 않다. 다만 `prior_year_total_salary_krw`가 주어지면 엔진은 `isa.tax_free_limit`의 구간 판정을 **참고로 재계산해** 사용자 선언과 어긋날 때 경고를 낸다(계산은 사용자 선언을 따른다).

`prior_year_total_salary_krw`가 null이면 교차확인을 건너뛰고 그 사실을 notice로 낸다. **추정치를 만들지 않는다.**

`financial_income_taxpayer_last_3_years`가 true면 `isa.exclusion.financial_income_taxpayer`에 따라 ISA를 배분 대상에서 제외하고 사유를 낸다. null이면 배제를 적용하지 않고 "확인되지 않음"을 notice로 낸다 — **모르는 것을 아니라고 단정하지 않는다.**

### 4.2 투자 성향은 배분 계산의 변수인가

**결정: 아니다. 배분 금액에도, 배분안의 순서에도 영향을 주지 않는다.** 입력으로는 받되 계산에 쓰지 않고 그대로 출력에 되돌린다(`echo.risk_profile`, `used_in_calculation: false`).

근거 셋.

1. **룰셋에 근거가 없다.** 확정 20건·개정예고 12건의 `conditions`를 전수로 보면 투자 성향에 대응하는 필드가 없다. 세액공제율·공제한도·납입한도·비과세 한도 어느 것도 성향의 함수가 아니다. 룰셋에 없으면 없는 것이다.
2. **성향을 금액에 반영하려면 룰셋 밖 가정이 필요하다.** 계좌별 기대수익률·변동성·자산배분 제약을 세워야 하는데 그것은 세법 값이 아니다. 그 가정을 엔진이 세우면 1.1절에서 ISA 절세액을 내지 않기로 한 이유가 그대로 무너지고, 특정 상품 성격을 전제한 추천으로 미끄러진다(제품 원칙 5).
3. **헌장의 세무사법 제약과도 어긋난다.** 개인의 성향에 따라 금액이 달라지는 결과는 "개인의 구체적 사정에 맞춘 결론"의 성격을 키운다. 헌장이 위험 요소로 지목한 방향이다.

**그럼 이 입력은 무엇에 쓰는가.** 결과 화면의 참고 정보다. 예컨대 배분안 세 가지를 나란히 놓고 "성향에 따라 사람들이 다르게 고른다"는 맥락을 designer가 줄 수 있다. 그 판단은 화면의 몫이고 계산은 중립을 지킨다. 이 결정은 requirements.md 2절의 가정("배분 우선순위에 영향을 주는 입력")과 어긋나므로 `open_questions`에 올렸다.

### 4.3 ISA 만기 전환

`pension.credit.isa_transfer.extra_limit`을 계산에 반영한다.

**전환금액은 예산이 아니다.** 월 납입 여력에서 나오는 돈이 아니라 ISA 만기 자금이므로 C1(예산 제약)에 넣지 않는다. 대신 **이미 납입된 것으로 취급해** 공제 대상액에 먼저 얹는다. 이 구분을 놓치면 사용자의 월 여력이 전환금액만큼 잠식되어 배분이 과소해진다.

계산 순서.

1. 전환 추가한도 E를 `pension.credit.isa_transfer.extra_limit.value.formula`로 산출한다. 전환금액에 규칙의 비율을 적용한 값과, 규칙의 상한에서 직전 과세기간 적용액을 뺀 값 중 작은 쪽이다. 결과가 음수면 0으로 클램프한다.
2. 세액공제 대상 총 상한을 C4의 합산 한도에 E를 더해 확장한다.
3. 전환금액을 그 목적지 계좌(`isa_transfer.destination`)의 당해연도 납입액에 선반영한다. 목적지가 연금저축이면 C3의 단독 한도 판정에 먼저 걸린다 — 이 때문에 목적지를 입력으로 받아야 한다.
4. 남은 세액공제 대상 한도를 예산으로 채운다.

전환금액은 `pension.contribution.annual_limit`(C6)의 계산에서 제외한다. 해당 규칙의 `excluded_from_limit`가 ISA 전환금액을 별도로 다룬다고 명시하고 있다.

전환 여부가 "아니오"이거나 전환금액이 0이면 E는 0이고, 출력에서 전환 관련 항목 자체가 나가지 않는다(requirements.md 수용 기준).

### 4.4 개정예고 시나리오

**결정: 시나리오를 출력의 최상위 축으로 둔다.** 요청에 `scenarios: ["current"]` 또는 `["current", "proposed"]`를 받고, 응답의 `scenarios` 배열에 시나리오별 결과가 **각각 완전한 형태로** 담긴다. 두 시나리오의 숫자를 한 배분안 안에서 섞지 않는다(제품 원칙 3).

각 시나리오 결과는 다음을 반드시 갖는다.

- `ruleset` — 어떤 룰셋 파일에서 나온 결과인지(`tax_year`, `status`, `effective_from`)
- `bill_stages` — 실제 적용된 개정예고 규칙들의 `bill_stage` 값을 룰셋에서 그대로 읽어 담는다. 확정 시나리오에서는 빈 배열이다. **문자열을 코드에 박지 않는다.** 룰셋의 값이 바뀌면 화면 표시도 따라 바뀌어야 한다(헌장 고지 요소 6).
- `is_enacted` — `ruleset.status`가 확정인지 여부. 화면이 두 시나리오를 시각적으로 구분할 최소 단서다.
- `unapplied_proposed_rules` — 개정예고 12건 중 이번 계산에 반영하지 **않은** 규칙과 그 사유 코드. 무엇을 반영하지 않았는지가 드러나지 않으면 사용자는 개정안 전부가 반영된 결과로 읽는다.

개정안 시나리오에서 **배분 결과를 실제로 바꾸는 규칙은 셋**이다.

| 규칙 | 무엇이 바뀌는가 |
|---|---|
| `proposed.isa.annual_contribution_limit` | ISA 연간 납입한도가 산식에서 정액으로 바뀌어 이월 효과가 사라진다. 기존 가입자에게도 적용된다. 잔여 한도가 줄어 배분이 달라진다 |
| `proposed.pension.credit.youth_irp_rate` | 청년의 퇴직연금 납입분에 소득 경계 없이 우대 공제율이 적용된다. 소득이 경계 위인 청년에게 IRP 우선의 이점이 커진다 |
| `proposed.productive_isa.pension_transfer.credit_extra_limit` | 전환 추가한도 상한에서 차감할 과거 적용액의 대상 기간이 넓어진다. 4.3절 1단계의 E가 달라진다 |

**청년 여부는 엔진이 판정하지 않는다.** 두 청년 관련 규칙 모두 연령 범위가 시행령 위임이고 시행령안이 공개되지 않았다. 룰셋이 `age_range: null`과 함께 "엔진이 스스로 판정해서는 안 된다"고 명시했다. 따라서 `profile.declared_youth`를 사용자 자기신고로 받고, null이면 우대를 적용하지 않은 채 그 사실을 notice로 낸다. true면 적용하되 결과에 "연령 기준이 시행령으로 정해질 예정"이라는 불확실성 표시를 함께 낸다.

## 5. 계산 순서

시나리오마다 아래를 독립적으로 수행한다. 앞 단계가 실패하면 뒤 단계를 시도하지 않는다.

1. **입력 검증** — 자료형, 정수 여부, 음수 여부, 범위, 상호 제약(전환금액 ≤ ISA 누적 납입액). 하나라도 위반이면 `ok: false`와 오류 목록을 반환하고 계산을 시작하지 않는다.
2. **룰셋 로드와 규칙 존재 확인** — 이 시나리오가 쓰는 규칙 id가 전부 있는지 먼저 확인한다. 하나라도 없으면 `rule_missing` 오류로 중단한다. **없는 규칙을 기본값으로 메우지 않는다.** 메우는 순간 룰셋이 단일 진실 원천이라는 전제가 깨지고 검증 장치 전체가 무력해진다.
3. **파생 비율 산출** — `pension.credit.rate`의 구간을 `current_year_total_salary_krw`로 판정하고, `tax.local.personal_income_surtax`의 부가율을 적용해 실효 절세율을 만든다. 개정안 시나리오에서 `declared_youth`가 true면 퇴직연금 납입분에 대해 `proposed.pension.credit.youth_irp_rate`의 비율로 대체한다.
4. **계좌 자격 판정** — `isa.eligibility`(연령 요건), `isa.exclusion.financial_income_taxpayer`. 자격이 없는 계좌는 배분 대상에서 빠지고 사유가 출력에 실린다. **연금계좌의 연령 자격은 판정하지 않는다** — 룰셋에 규칙이 없다.
5. **한도 산출** — 계좌별로 (a) 납입 자체의 잔여 한도, (b) 세액공제 대상 잔여 한도를 각각 낸다. ISA 연간 한도는 산식을 평가하고 총 납입한도와 비교해 작은 쪽을 쓴다. 기납입액을 뺀 결과가 음수면 0으로 클램프한다.
6. **전환 추가한도 반영** — 4.3절의 1~3단계.
7. **예산 산출** — `monthly_capacity_krw × months_remaining_in_tax_year`. 여기서 얻는 연간 예산이 C1이다.
8. **배분안 생성** — 3절의 세 순서로 각각 순차 충당한다. 각 계좌에서 채우는 금액은 `min(남은 예산, 그 계좌의 납입 잔여 한도, 그 계좌가 흡수할 수 있는 세액공제 대상 잔여 한도)`이되, 세액공제 대상 한도를 넘겨도 납입 한도가 남아 있으면 그 초과분은 충당하지 않고 다음 계좌로 넘긴다. 세액공제 대상 한도를 넘긴 연금계좌 납입은 목적함수를 늘리지 않으면서 인출 제약만 지기 때문이다.
9. **평가** — 각 안의 세액공제액(소득세분·지방소득세분·합계)과 미배분액을 낸다.
10. **동률·중복 처리** — 6.2절.
11. **근거 수집** — 실제로 읽은 규칙만 `legal_basis`에 담는다. 읽지 않은 규칙을 근거로 싣지 않는다.
12. **가정·고지 메타 조립** — `assumptions`, `notices`, `bill_stages`, `unapplied_proposed_rules`.

### 5.1 금액 연산 규칙

전부 **정수(원) 연산**이다. 부동소수점 누적을 쓰지 않는다.

- 비율 곱은 정수 곱 후 원 미만 **버림(floor)**. 이 버림 규칙은 룰셋 근거가 아니라 엔진의 표시 규칙이므로 `assumptions`에 담아 화면이 고지 요소 4(가정)로 쓸 수 있게 한다.
- 계산의 1차 단위는 **연간**이다. 월 표시 금액은 `floor(연간 / 개월수)`이고, 그 결과 합계가 연간 금액보다 작아지는 잔차는 삼키지 않고 `monthly_rounding_residual_krw`로 내보낸다.

### 5.2 지방소득세

`tax.local.personal_income_surtax`의 부가율을 소득세율에 적용해 산출한다. 룰셋의 `derived_effective_rates` 표는 **읽지 않는다.** 룰셋 자체가 참고용이라고 적어 두었고, 세율이 하나만 바뀌어도 그 표는 손으로 고쳐야 하기 때문이다. 출력에서 소득세분과 지방소득세분을 나눠 낸다.

### 5.3 개정안 시나리오의 룰셋 조합

개정예고 파일은 **바뀌는 규칙만** 담는다. 따라서 개정안 시나리오는 확정 룰셋을 바탕에 두고 개정예고 규칙을 덮어쓰는 방식으로 계산한다.

대응 관계(어느 개정예고 규칙이 어느 확정 규칙을 대체하는가)를 나타내는 필드가 룰셋에 없으므로, 엔진이 **규칙 id 쌍의 대응표**를 따로 갖는다. 이 표에는 세법 수치가 없고 id 문자열만 있다. 대응 관계는 룰셋이 스스로 적어 둔 상호 참조(`contrast_with_current`, `current_text`, `related_confirmed_rule`, `engine_note`)에서만 도출한다. **그 근거로 도출되지 않는 쌍은 만들지 않고 `open_questions`에 올린다.**

각 출력 숫자에는 그 값이 어느 파일의 어느 규칙에서 나왔는지가 붙는다(`basis_rule_ids`). 확정 규칙과 개정예고 규칙이 한 시나리오 안에 함께 쓰이더라도 어느 값이 어느 쪽에서 왔는지는 항상 추적된다.

### 5.4 생산적금융 ISA를 넣지 않은 이유

개정예고 12건 중 6건이 생산적금융 ISA에 관한 것이지만 **네 번째 계좌로 넣지 않았다.** 근거 셋: (a) 게이트 1 D3이 확정한 범위는 ISA·IRP·연금저축 세 계좌 배분과 ISA 만기 전환이다. (b) requirements.md의 입력 항목에 이 계좌가 없어 잔여 한도를 계산할 입력 자체가 없다. (c) 청년 소득공제의 연령 범위가 시행령 미공개이고, 소득공제의 절세액을 내려면 기본세율 구간이 필요한데 그 규칙은 룰셋에 없다.

이 6건은 `unapplied_proposed_rules`에 사유 코드와 함께 실려 나간다. 관리자 확인 사항으로 `open_questions`에 올렸다.

## 6. 동률과 경계 처리

### 6.1 계좌 간 동률

두 계좌의 한계 절세율이 같아지는 국면이 실제로 생긴다. 개정안 시나리오에서 청년의 퇴직연금 우대 공제율이 소득 구간 공제율과 같아지는 경우가 그렇다.

깨는 순서는 다음과 같고, 입력에 따라 바뀌지 않는다.

1. **약우월 규칙** — 2.2절. 합산 한도 구조상 퇴직연금이 먼저다.
2. 여전히 같으면 **고정 계좌 순서**: 퇴직연금 → 연금저축 → ISA.

무작위도, 입력 순서 의존도 없다. 결정성이 4단계 교차검증의 전제다.

### 6.2 배분안 간 동률

- **배분 벡터가 같으면** 하나로 합친다. 남는 안이 하나뿐이면 `plans` 길이가 1이 되고 사유 코드가 나간다(3절).
- **세액공제액이 같고 배분 벡터가 다르면** 둘 다 남긴다. 이것이 헌장이 요구하는 선택지 비교의 가장 좋은 형태다 — 같은 절세액을 내는 서로 다른 배분이고, 선택 기준이 룰셋 밖에 있다는 사실이 숫자로 드러난다.
- 정렬은 항상 고정 순서다(3절).

### 6.3 처리할 수 없거나 특이한 입력

| 상황 | 처리 |
|---|---|
| **월 납입 여력 0** | 오류가 아니다. 정상 계산한다. 세 안 모두 배분액 0이 되고 `zero_capacity` notice가 나간다. 잔여 한도와 기납입 현황은 그대로 산출된다 — 여력이 0인 사용자에게도 "지금 한도가 얼마나 비어 있는가"는 유효한 정보다 |
| 음수 금액, 비정수 나이 | `ok: false` 오류. 계산하지 않는다 |
| 예산이 세 계좌 잔여 한도 합계 이상 | 정상 계산. 한도까지 채우고 남는 금액은 `unallocated_*`로 명시한다. 배분 벡터가 하나로 수렴하므로 6.2절의 합치기가 일어난다 |
| 기납입액이 이미 한도를 넘음 | 잔여 한도를 0으로 클램프한다. **음수 잔여 한도를 만들지 않는다.** `existing_contribution_over_limit` 경고를 낸다 |
| 나이가 `isa.eligibility` 요건 미달 | ISA만 배분 대상에서 제외한다. 연금계좌 계산은 계속한다. 룰셋에 연금계좌 최소 가입 연령 규칙이 없기 때문이다 |
| 모든 계좌가 자격 미달 | 배분안은 전부 0이고 `plans`는 여전히 반환된다. `ok: false`로 만들지 않는다 — 자격 미달 사유를 화면이 설명해야 하는데 오류로 끊으면 그 정보가 사라진다 |
| 금융소득종합과세 대상자 | ISA를 제외하고 계산한다(`isa.exclusion.financial_income_taxpayer`) |
| ISA 계좌가 없음(`exists: false`) | 신규 가입을 전제로 잔여 한도를 산출한다. 가입경과연수는 0으로 본다. 이 취급을 `assumptions`에 담는다 |
| ISA 가입경과연수 미입력(null) | 연간 한도 산식에 필요한 값이므로 **가장 보수적인 값(0)**으로 계산하고 notice를 낸다. 추정하지 않는다 |
| 전환금액 > ISA 누적 납입액 | `ok: false` 오류(requirements.md 수용 기준) |
| 요청한 규칙이 룰셋에 없음 | `ok: false`, `rule_missing`. 대체값을 만들지 않는다 |
| 룰셋 파싱 실패 | `ok: false`, `ruleset_load_failed` |

### 6.4 designer 산출물 부재로 세운 가정

`screens.md`가 아직 없어 아래를 가정하고 진행했다(헌장 5.4절). 게이트 2에서 대조가 필요하다.

- 결과 화면은 배분안을 **셋까지** 나란히 비교할 수 있다. 엔진이 그보다 많이 내지 않는 이유이기도 하다.
- 화면은 월 금액과 연 금액을 **둘 다** 표시할 수 있다. 그래서 엔진이 두 단위를 모두 낸다.
- 근거 법령 조항은 값 옆에 붙이는 방식과 하단에 모으는 방식 둘 다 가능해야 한다. 그래서 `legal_basis`를 목록으로 내면서 각 숫자에 `basis_rule_ids`를 따로 단다.
- 사용자에게 보이는 문구는 **designer가 만든다.** 엔진은 코드와 파라미터만 낸다(`engine-interface.md` 7절).

## 7. 결정성과 검증 가능성

- 순수 함수다. 같은 입력·같은 룰셋이면 항상 같은 출력이다.
- 현재 시각을 읽지 않는다. 기준 과세연도는 입력이다.
- 난수·해시 순회·객체 키 순서에 의존하지 않는다. 계좌 순서와 배분안 순서는 코드에 고정된 상수 배열이다(세법 수치가 아니다).
- 부동소수점 누적이 없다(5.1절).
- 3단계 완료 기준: `grep`으로 코드에서 세법 수치를 찾을 수 없어야 한다. 한도·비율·경계값·상한은 전부 규칙 id로 접근한다.
