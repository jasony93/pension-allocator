# 2단계 설계 — 디자인 시스템

`[가칭] 납입배분 계산기`의 시각·상호작용 규약이다. `screens.md`가 이 문서의 토큰과 컴포넌트만으로 화면을 기술한다. 코드는 없다 — 구현은 3단계 `web-dev`의 몫이다.

---

## 0. 이 시스템이 지켜야 하는 것

이 제품의 설득력은 심미성이 아니라 **"이 숫자가 어디서 나왔는지 화면이 스스로 밝힌다"**는 데서 나온다. 헌장의 세무사법 준수 원칙이 디자인 제약으로 번역되면 다음 넷이다.

| # | 원칙 | 디자인 규약 |
|---|---|---|
| P1 | 금액을 산정 조건 없이 앞세우지 않는다 | **금액 컴포넌트는 조건 캡션 슬롯 없이 단독으로 존재할 수 없다.** 큰 금액 뒤에는 항상 같은 카드 안에 조건 한 줄이 붙는다. 6.5절 |
| P2 | 계산에 쓴 법령 조항을 결과 화면에 노출한다 | `조항 칩(LawChip)`과 `근거 블록(BasisBlock)`을 1급 컴포넌트로 둔다. 툴팁·각주가 아니다. 5.9·5.10절 |
| P3 | 개인 지시형 문장을 쓰지 않는다 | 버튼·라벨·헤딩 문구에 2인칭 명령형을 쓰지 않는다. 7.2절의 금지 패턴 목록 |
| P4 | 고지를 각주로 밀지 않는다 | 고지 텍스트는 본문과 같은 색 대비(4.5:1 이상)를 쓰고, 본문보다 두 단계 이상 작게 만들지 않는다. 캡션 최소 크기는 12.5px로 고정한다. 2.1절 |

**"작게, 회색으로, 접어서"가 고지의 기본값이 되는 것을 이 시스템이 구조적으로 막는다.** 그래서 캡션 토큰의 색이 `text-muted`가 아니라 `text-secondary`이고, `BasisBlock`과 `AssumptionBlock`의 기본 상태가 "접힘"이 아니라 "펼침"이다.

---

## 1. 기반 단위

- **기준 폰트 크기** 16px = 1rem. 사용자의 브라우저 기본 크기를 존중한다 — 루트에 `px` 고정값을 박지 않는다.
- **기준 격자** 4px. 모든 간격·크기는 4의 배수다.
- **최대 본문 폭** 결과 설명 텍스트는 68자를 넘지 않는다(한글 기준 약 34~40자).
- **최소 터치 타깃** 44×44px. 조항 칩처럼 작은 요소도 히트 영역은 44px를 확보한다.

**`type-num`의 tabular-nums는 선택이 아니다.** 시나리오 세 개의 금액이 세로로 정렬될 때 숫자 폭이 흔들리면 자릿수 비교가 불가능해진다. 결과 화면의 스택바 3행 비교(`screens.md` 5.5절)가 이 정렬에 의존한다.

### 2.2 서체 스택

```
본문/숫자 공통:
  system-ui, -apple-system, "Segoe UI", "Apple SD Gothic Neo",
  "Noto Sans KR", "Malgun Gothic", sans-serif
```

별도 웹폰트를 전제하지 않는다(`open_questions`). 어떤 서체를 쓰든 **한글과 아라비아 숫자의 기준선이 어긋나지 않을 것**과 **tabular-nums를 지원할 것** 두 가지가 채택 조건이다.

### 2.3 텍스트 규칙

- 금액은 천 단위 쉼표 + `원` 접미. 만 단위 축약(`147만원`)은 **헤드라인에서만** 허용하고, 계좌별 상세와 근거 블록에서는 항상 원 단위 전체 표기를 병기한다. 축약만 남기면 사용자가 자기 계산과 대조할 수 없다.
- 마이너스 금액은 색이 아니라 부호와 라벨로 표시한다(색맹 대응).
- 줄바꿈: 금액과 단위(`원`)는 분리되지 않는다.
- 한국어 조사 자동 결합("을/를")을 문자열 조립으로 처리하지 않는다 — 문장을 조사가 필요 없는 형태로 쓴다.

## 3. 색 — 역할 정의

색은 **역할(role)로만** 참조한다. 화면 설계 문서와 구현 어디에도 raw hex가 직접 등장하지 않는다.

hex는 **참조값**이다. 역할이 성립하는지 검증하려고 채워 넣은 값이며, 브랜드 확정 시 교체 대상이다(`open_questions`). 특정 금융사의 브랜드 색은 참고하지 않았다.

### 3.5 데이터 색 — 계좌 고정 매핑

**이 절의 값은 눈으로 고르지 않았다.** `dataviz` 스킬의 팔레트 검증기(`scripts/validate_palette.js`)가 여섯 검사를 계산으로 판정하고, 통과한 값만 여기 실린다. 검증기 출력 전문은 3.5.4절에 있다. **색을 바꾸는 사람은 바꾼 값을 같은 검증기에 라이트·다크 양쪽으로 돌리고, 그 출력을 3.5.4절에 갈아 끼운다.** 출력 없는 색 변경은 이 문서가 받지 않는다.

#### 3.5.1 왜 바꿨는가 — 진단

소유자가 "칙칙하다"고 한 것은 취향 문제가 아니라 **측정되는 결함 셋**이었다. 초판 값을 검증기에 돌린 결과다.

| 증상 | 측정값 | 원인 |
|---|---|---|
| 연금저축 색이 회색으로 보인다 | `#2E7D8A` OKLCH C = **0.078** — 채도 하한 0.10 **미달(FAIL)** | 이 색은 채도가 하한 아래라 **기술적으로 무채색 대역**에 있다. "칙칙하다"의 직접 원인이다 |
| 세 색이 다 어둡다 | OKLCH L = 0.547 / 0.618 / 0.521 (평균 0.562) | 밝기 대역의 아래쪽에 몰려 있다. 흰 카드 위에서 무겁게 보인다 |
| 연금저축과 ISA가 붙어 보인다 | 적록색각이상 ΔE **7.1**(라이트) / **5.8**(다크), 정상 시야 ΔE **13.2 / 14.0** — 정상 시야 하한 15 **미달(FAIL)** | 명도차가 0.026뿐이고 둘 다 청색 계열이라 색각이상에서 겹친다. **색각이상자만의 문제가 아니다 — 정상 시야에서도 하한 미달이었다** |

다크 값은 더 나빴다 — 셋 다 명도 대역(0.48~0.67) **밖**이었고(0.714 / 0.755 / 0.680), 연금저축 채도는 여기서도 하한 미달이었다.

**즉 "밝기"만 올리는 것은 오답이었다.** 진짜 결함은 ① 채도 하한 미달 ② 명도 대역 이탈 ③ 인접쌍 분리 실패였고, 셋 다 검증기가 잡는 것이다.

#### 3.5.2 계좌 색 (범주형)

계좌 색은 **범주형(categorical)** 이다 — 크기가 아니라 정체를 나타낸다. 순서가 고정이고 순환하지 않으며, 계좌가 넷째로 늘어나도 색을 자동 생성하지 않는다.

| 토큰 | 매핑 | 라이트 | 다크 | 색상각(H) |
|---|---|---|---|---|
| `data-pension` | 연금저축 | `#0A9A96` | `#06A19D` | 192 (틸) |
| `data-irp` | IRP | `#DA7134` | `#DF7333` | 48 (오렌지) |
| `data-isa` | ISA | `#8758C1` | `#8F5FCC` | 302 (바이올렛) |

라이트·다크의 **색상각은 같고 밝기·채도만 다르다.** 계좌의 정체는 색상각이 나르므로 테마가 바뀌어도 같은 계좌가 같은 색으로 읽힌다. 값 자체는 각 모드의 표면에 대해 **따로 뽑아 따로 검증**했다 — 3.5.4절에 두 벌의 출력이 있다.

| | 라이트 OKLCH (L / C) | 대비 (카드 `#FFFFFF` / 페이지 `#F7F8FA`) | 다크 OKLCH (L / C) | 대비 (카드 `#1E2226` / 페이지 `#14171A`) |
|---|---|---|---|---|
| `data-pension` | 0.621 / 0.105 | 3.46 / 3.25 | 0.641 / 0.109 | 5.02 / 5.65 |
| `data-irp` | 0.660 / 0.150 | 3.28 / 3.09 | 0.670 / 0.154 | 5.06 / 5.69 |
| `data-isa` | 0.560 / 0.160 | 5.00 / 4.71 | 0.586 / 0.165 | 3.56 / 4.01 |

초판 대비: 평균 채도 0.104 → **0.138**(+33%), 평균 명도 0.562 → **0.614**. 연금저축 채도는 0.078 → **0.105**로 하한을 넘었다. **이것이 "밝고 세련되게"의 실행이다** — 채도를 올리되 대비를 3:1 아래로 떨어뜨리지 않는 선에서 멈췄다.

**이 절이 피한 함정.** 색을 밝히면 흰 배경과의 대비가 떨어지고, 채도를 끝까지 올리면 형광색이 된다. 그래서 세 슬롯 모두에 대해 **대비 ≥ 3:1**(더 어두운 페이지 표면 기준으로도)을 먼저 걸고, 그 안에서 채도를 올렸다. sRGB에서 틸 계열은 이 밝기 대역의 채도 상한이 약 0.11이라 `data-pension`은 더 올릴 수 없다 — 올리면 색역을 벗어나거나 대비가 무너진다. **이것이 이 슬롯의 물리적 한계이고, 다음에 "연금저축이 아직 좀 흐리다"는 말이 나와도 같은 색상각 안에서는 답이 없다.** 그때 바꿀 것은 채도가 아니라 색상각이다.

#### 3.5.3 역할 색 — 계좌 색과 같은 팔레트, 다른 계층

미배분 조각 · 배분 대상 아님 · 자리표시자 · 트랙은 **계좌가 아니다.** 계좌 색과 섞이면 안 되므로 채도를 거의 0으로 둔 하나의 무채색 사다리(색상각 240~248, C ≈ 0.012)에서 뽑되, **표면 대비로 계층을 가른다.**

| 토큰 | 역할 | 라이트 | 대비 | 다크 | 대비 |
|---|---|---|---|---|---|
| `data-unallocated` | 미배분 잔액 — **값을 나른다** | `#5A6166` | 6.29 | `#B1B8BF` | 7.99 |
| `data-excluded` | 배분 대상 아님 윤곽 — **뜻을 나른다** | `#888F95` | 3.29 | `#6A7076` | 3.20 |
| `data-placeholder` | 결과 자리표시자 — **아무것도 나르지 않는다** | `#C0C8CE` | 1.69 | `#41474C` | 1.70 |
| `data-track` | 트랙의 빈 부분 — 배경 | `#E1E5EA` | 1.27 | `#2C3238` | 1.24 |

**대비 계층 규칙 (기계적으로 검사 가능하다).**

- **값을 나르는 색은 표면 대비 3:1 이상.** 계좌 색 셋과 `data-unallocated`가 여기 든다.
- **뜻을 나르는 비텍스트 경계는 3:1 이상.** `data-excluded`가 여기 든다(WCAG 1.4.11).
- **아무것도 나르지 않는 색은 2:1 미만.** `data-placeholder`와 `data-track`이 여기 든다.
- **2:1과 3:1 사이는 비어 있다.** 이 틈이 "이건 값이다 / 이건 아직 값이 아니다"를 눈이 아니라 수치로 가르는 장치다. 새 색을 이 대역에 넣지 않는다.

**`data-unallocated`는 라이트에서 짙고 다크에서 밝다.** 무채색이라 표면에서 멀어지는 방향이 모드마다 반대다. 이것은 팔레트 반전이 아니라 무채색의 정상 동작이다 — 계좌 색(유채색)은 두 모드에서 같은 방향(둘 다 중간 밝기)에 있다.

**초판에서 바뀐 것 둘과 그 근거.**

- `data-unallocated`가 밝은 회색(`#9AA3AB`, 대비 2.56)에서 짙은 회색으로 내려갔다. 초판 값은 **대비 3:1 미달**이었고, 동시에 `data-pension`과 적록색각이상 ΔE **3.8**로 겹쳤다 — 도넛에서 미배분 조각과 연금저축 조각이 붙어 있으면 구분되지 않았다. 새 값은 최악쌍 ΔE **13.0**(라이트) / **10.3**(다크)이다.
- `data-excluded`가 새로 생겼다. 초판은 `AllocationBar`의 배제 상태 점선에 `border-subtle`(대비 1.27)을 썼는데, 그 점선은 "이 계좌는 계산 대상이 아니다"라는 **뜻을 나르는 경계**여서 1.27:1로는 안 된다. 3:1을 넘는 전용 토큰으로 뺐다.

#### 3.5.4 검증기 출력 (이 값들의 근거)

`node scripts/validate_palette.js "<hex,…>" --mode <light|dark> --surface <표면>`

**도넛은 고리라 마지막 조각이 첫 조각과 맞닿는다. 게다가 계좌 하나가 배제되면 남은 둘이 이웃이 된다.** 그래서 계좌 색은 인접쌍이 아니라 **`--pairs all`(모든 쌍)** 으로 검사한다. 아래는 두 방식 모두의 출력이다.

```

  [PASS] Contrast vs surface    all 4 >= 3:1
```

**남은 경계 하나 — 청색각이상(tritanopia).** 네 조각 고리의 라이트 최악 tritan ΔE는 **8.3**으로 목표선(8) 바로 위다. 계좌 셋만이면 15.7이다. 검증기는 tritan을 게이트로 걸지 않고 보고만 하지만(적록에 비해 유병률이 훨씬 낮다), **여기가 이 팔레트에서 가장 얇은 자리**라는 것은 적어 둔다. 이 자리를 지키는 것은 아래 규약 2(직접 라벨)와 6.4절의 표 대체 경로다.

#### 3.5.5 규약

1. **계좌↔색 매핑은 제품 전체에서 고정이다.** 시나리오가 바뀌어도, 차트가 바뀌어도, 공유 이미지에서도, 테마가 바뀌어도 같다. 색은 **정체를 따르지 크기를 따르지 않는다** — 값이 큰 조각을 눈에 띄는 색으로 바꾸는 처리를 하지 않는다.
2. **색만으로 구분하지 않는다.** 모든 색 조각에는 직접 라벨(계좌명 + 금액)이 붙는다. 범례만 두고 라벨을 빼는 설계는 금지다. 차트 아래 `계좌별 상세 리스트`가 같은 정보를 표로 담는다(6.4절).
3. **개정예고 데이터는 색을 바꾸지 않고 패턴을 얹는다** — 45° 사선 해칭. **이 패턴은 `bill_stage` 전용이다.** 다른 어떤 상태(자리표시자·배제·미배분·로딩)에도 해칭을 쓰지 않는다 — 쓰는 순간 "국회 통과 전"이라는 뜻이 오염된다.
4. **계좌가 셋을 넘으면 색을 자동 생성하지 않는다.** 범주형 슬롯은 순환하지 않는다. 넷째 계좌가 생기면 이 절을 다시 열어 네 슬롯 전체를 검증기에 다시 돌린다.
5. **조각 사이에 2px 표면색 간격을 둔다.** 스택바의 인접 조각, 도넛의 인접 조각 모두. 색이 맞닿으면 경계에서 색이 섞여 보이고, 색각이상에서는 두 조각이 하나로 읽힌다.
6. **글자는 계좌 색을 입지 않는다.** 금액·라벨·범례 텍스트는 `text-primary`/`text-secondary`를 쓰고, 정체는 옆에 놓인 색 조각이 나른다. 계좌 색은 3:1 기준으로 뽑혔고 글자는 4.5:1이 필요하므로 애초에 자격이 없다.

### 3.6 브랜드 강조색 — 초록 (이번 개정, 소유자 지시)

**소유자 지시(2026-08-10):** "전체적인 UI가 너무 단순하다. 깔끔한 건 좋은데 색깔이 너무 없어 보인다. 밝은 초록색 색감이 들어갔으면 좋겠다." 참고 사이트 1건이 제시됐다 — JS 렌더 사이트라 정확한 색값(hex)은 확인하지 못했고, **밝은 초록 강조 + 밝은 배경 + 카드 기반 피드 + 굵은 산세리프 제목**이라는 방향만 읽었다.

#### 3.6.1 진단 — "색이 없다"의 실체

3.5.1절에서 "칙칙하다"가 검증기가 잡아내는 결함(채도 하한 미달·명도 대역 이탈·인접쌍 분리 실패)이었던 전례를 따라, 이번에도 눈으로 판단하기 전에 잰다. **다만 이번 신고는 데이터 색이 아니라 화면 전체의 인상에 대한 것이라, `dataviz` 팔레트 검증기(범주형 데이터 색 전용)가 답할 수 있는 질문이 아니다.** 그래서 이 절은 토큰 명세와 이미 구현된 `src/web/styles.css`의 실측 값을 근거로 구조적으로 잰다. **이 세션에는 개발 서버·브라우저 렌더 확인 수단이 없었으므로, 아래는 토큰·코드에서 기계적으로 읽어낸 수치이지 눈으로 본 인상이 아니다.**

**① 색 역할 수와 색상각 — "색이 없는" 것이 아니다.**

| 계열 | 역할 수(토큰) | 색상각(대략) | hex 대표값 |
|---|---|---|---|
| `accent` 계열 | 5개(accent/hover/pressed/subtle/focus-ring) | 블루 H≈225 | `#2F5D8C` |
| `state-error` 계열 | 2개 | 레드 H≈25 | `#B3261E` |
| `state-warning` 계열 | 2개 | 앰버/브라운 H≈73 | `#8A5A00` |
| `state-info` 계열 | 2개(accent와 값 공유) | 블루 | `#2F5D8C` |
| `data-pension`(+측면) | 2개 | 틸 H192 | `#0A9A96` |
| `data-irp`(+측면) | 2개 | 오렌지 H48 | `#DA7134` |
| `data-isa`(+측면) | 2개 | 바이올렛 H302 | `#8758C1` |

**이미 6개의 서로 다른 색상각이 화면 어딘가에 있다.** "색이 없다"는 인상의 원인은 색상 종류의 부족이 아니다.

**② 그 색이 차지하는 자리 — 전부 작은 요소에 갇혀 있다.** 유채색이 실제로 등장하는 자리를 전수 확인하면 전부 **선(line) · 소면적 채움 · 텍스트**다.

- `accent` — 주 버튼 배경(높이 48px)·포커스 링(2px)·선택된 세그먼트 배경(연한 톤 `accent-subtle`)·링크 텍스트.
- `state-*` — 3px 좌측 바 + 옅은 배경(`*-subtle`).
- `data-*` — 도넛 조각(압출 두께는 반지름의 8%)·`AllocationBar` 채움(높이 20px)·`LawChip` 텍스트.

**카드·페이지·입력 필드 같은 큰 표면은 전부 무채색이다.** `surface-base`(`#F7F8FA`)·`surface-raised`(`#FFFFFF`)·`surface-sunken`(`#EDEFF2`) 셋 다 회색조이고, 유채색이 "면"으로 등장하는 자리가 이 시스템 어디에도 없다. 사용자가 화면을 열자마자 보는 첫인상(페이지 배경·헤더·카드 배경)에는 색이 구조적으로 배제되어 있다.

**③ 위계(depth) 신호도 약하다 — 색과는 별개의 문제.** 카드 경계 `border-subtle`(`#E1E5EA`)과 카드 배경(`#FFFFFF`)의 대비를 WCAG 상대휘도 공식으로 직접 재면 **1.27:1**이다 — 우연이 아니라 `border-subtle`과 `data-track`이 같은 hex이고, `data-track`이 3.5.3절에 대비 1.27로 이미 실려 있다. 카드 그림자 `shadow-1`도 `rgba(16,18,20,.06)` / `.04`로 알파가 매우 낮다. **카드가 카드처럼 보이게 하는 유일한 장치가 거의 지각되지 않는 테두리와 아주 옅은 그림자뿐이다.** 이것은 색상과 무관한 밀도·위계 문제이며, 초록을 더해도 이 문제 자체는 그대로 남는다.

**결론 — 세 원인이 겹쳤다.**

| 원인 | 실체 | 이번 개정이 다루는가 |
|---|---|---|
| (a) 색상 종류 부족 | **아니다.** 이미 6개 색상각이 있다 | 해당 없음 |
| (b) 색이 "면"에 등장하지 않는다 | 맞다. 유채색이 전부 선·소면적·텍스트에만 갇혀 있다 | **다룬다** — 3.6.3절 |
| (c) 카드 위계 신호가 약하다(테두리 1.27:1, 그림자 알파 0.04~0.06) | 맞다. 색과 무관한 구조적 문제다 | **다루지 않는다** — 이번 소유자 지시(색감)의 범위 밖이라 관찰로만 남긴다. 관리자·오너 판단이 필요하다 |

**밝은 초록을 추가하는 것은 (b)를 완화하는 개입이지 (a)를 늘리는 개입이 아니다.** (c)를 함께 고치지 않으면 초록을 더해도 "평평하다"는 인상이 부분적으로만 걷힐 수 있다 — 다음에 "그래도 밋밋하다"는 말이 나오면 이번엔 (c)를 열어야 한다.

#### 3.6.2 결정 — `accent`를 초록으로 바꾸지 않는다

세 근거.

1. **`accent`는 이미 뜻을 나른다.** 주 버튼·포커스 링·선택 상태·`LawChip`/`BasisBlock` 강조가 전부 이 색에 걸려 있다(P2, 0절). 강조색 전체를 바꾸는 것은 상호작용 의미 체계를 다시 배선하는 일이고, 이번 지시("색감이 있으면 좋겠다")보다 훨씬 큰 변경이다.
2. **초록은 이 화면에서 이미 예약된 뜻이 있다.** 3.4절이 `state-success`를 의도적으로 정의하지 않은 이유를 이미 적어 두었다 — "절감세액에 초록을 붙이면 '성과가 확정됐다'는 인상을 준다... 부당한 기대 경계와 직결되므로 금액에 긍정 색을 쓰지 않는다." `accent`를 초록으로 바꾸면 주 버튼·포커스 링이 절세액 카드·도넛·막대 바로 옆에 초록으로 나타나고, 사용자가 그것을 **값의 부호(이득)** 로 읽을 위험은 이 시스템이 이미 한 번 명시적으로 피한 바로 그 위험이다.
3. **`data-pension`(연금저축, 틸 H192)과 색상각이 가깝다.** "밝은 초록"이 통상 놓이는 대역은 OKLCH H≈135~150이다. `data-pension`의 H192과의 각도 차는 약 42~57°로, 현재 계좌 팔레트의 최소 인접각(오렌지 H48↔바이올렛 H302, 약 106°, 3.5.4절)보다 훨씬 좁다. **좁은 각도 차는 낮은 ΔE의 강한 신호다** — 실측 없이는 통과를 장담할 수 없다. `accent`는 화면 전역에 반복 등장하므로, 도넛·막대가 있는 같은 화면에 초록 버튼·초록 포커스 링이 함께 있으면 "이게 연금저축 색인가 강조색인가"를 매 순간 되물어야 한다.

**이 결정의 검증 한계.** 이 유닛은 이번 세션에 `scripts/validate_palette.js` 실행 권한과 렌더 확인 수단이 없었다 — 위 3번을 각도 추정으로 논증했을 뿐 실제 ΔE는 재지 못했다. **`accent`를 초록으로 바꾸는 안을 검토한다면 실행에 앞서 반드시 검증기로 `data-pension`과의 분리를 라이트·다크 양쪽에서 재야 한다.** 경로는 3.6.4절에 열어 둔다.

#### 3.6.3 새 토큰 — `brand-tint` / `brand-tint-strong` (장식 전용, 다른 계층)

`accent`는 그대로 두고, 초록은 **상호작용·상태·데이터 어느 것도 아닌 새 계층**에 넣는다. 이 계층은 **뜻을 나르지 않는다** — 눌리지 않고, 선택되지 않고, 값을 표시하지 않는다. 순수하게 이 서비스의 "느낌"만 나르는 장식 색이다.

| 토큰 | 역할 | 라이트 | 다크 |
|---|---|---|---|
| `brand-tint` | 장식용 옅은 초록 배경(워시) | `#E9F7EC` | `#16241A` |
| `brand-tint-strong` | 장식용 초록 획·마크(가는 선·아이콘 채움) | `#1E8A3C` | `#4BC468` |

**대비 실측(WCAG 상대휘도 공식, 손계산).** 3.5.4절의 검증기는 범주형 데이터 팔레트만 판정하고(3.5.4절 scope 조항), 이 두 토큰은 정체를 나르는 데이터 색이 아니라 순수 장식이라 그 검증기의 판정 대상이 아니다. 그래도 "장식이 지각될 만큼 밝은가"는 손으로 쟀다.

| 조합 | 대비 | 판정 |
|---|---|---|
| `brand-tint-strong`(라이트) vs `surface-base`(`#F7F8FA`) | 4.15 | 장식 마크로서 충분히 지각된다. 뜻을 나르지 않으므로 WCAG 1.4.11 대상이 아니지만, 3:1을 넘겨 "있으나 마나 한 색"이 되지 않게 했다 |
| `brand-tint-strong`(다크) vs `surface-base`(다크, `#14171A`) | 8.05 | 다크에서 선명하게 지각된다 |
| `brand-tint`(라이트·다크) | — | `*-subtle` 상태 배경과 같은 밝기 대역(옅은 워시)이라 그 위에 `text-primary`/`text-secondary`를 얹어도 기존 `*-subtle` 계열과 동일하게 4.5:1 이상이 유지된다(유사 사례: `state-info-subtle` 텍스트 대비가 8.4절에 6.75~7.17로 실려 있다). **다만 이 워시 위에 고지 텍스트를 두지 않는다** — 3.6절 금지 구역이 이유다 |

**금지 구역 — 이 두 토큰을 쓸 수 없는 자리.**

1. **상호작용 요소.** 버튼·링크·포커스 링·선택 상태·토글 — 전부 `accent` 소관이다. `brand-tint*`로 대체하지 않는다.
2. **금액이 있거나 근접한 자리.** `AmountCard`, `AccountDonut`, `AllocationBar`, `[4-D]` 계좌별 표, `ScenarioStackBar`, 그리고 이번에 신설하는 `AccountBenefitStrip`(5.31절) — 전부 계좌 색·중립색만 쓴다. 절세액 옆에 초록이 있으면 "이 값이 플러스"로 읽힐 위험을 이 시스템이 이미 회피했다(3.6.2절 근거 2). **차트 영역 `[4-C]`와 그 자식 요소 전체가 이 두 토큰의 배제 구역이다.**
3. **상태색 자리.** `state-*` 어느 것도 대체하지 않는다. 장식과 상태를 같은 색으로 두면 "이게 장식인가 경고인가"가 사라진다.
4. **데이터 색 자리.** `data-pension`(틸)과 시각적으로 이웃할 수 있는 어떤 자리에도 두지 않는다 — 도넛·막대·표·범례.
5. **고지 텍스트 배경.** 고지 여섯 요소 중 어느 것도 `brand-tint` 위에 놓지 않는다. 고지는 항상 `surface-*`/`state-*-subtle` 계열 위에만 있다(design-system 8.4절 실측표가 그 조합만 보증한다).

**허용 구역은 `screens.md` 2.3절이 정한다.** 이 절은 토큰만 정의하고, 화면 어디에 실제로 나타나는지는 화면 설계 쪽 책임이다.

#### 3.6.4 대안 — `accent` 자체를 초록으로 바꾸는 안 (미실행, 오너 확인 필요)

소유자가 "브랜드 색 자체를 초록으로" 원한다면 3.6.2절의 결정을 뒤집는 것이고, 이 유닛은 그 가능성을 닫지 않는다. 다만 그 경로는 아래 넷을 반드시 거쳐야 하며, **이번 개정에서는 실행하지 않았다.**

1. `data-pension`을 초록 계열에서 최대한 먼 색상각으로 다시 뽑는다(예: 청색 계열로 이동) — 그래야 새 `accent` 초록과의 이웃 위험이 사라진다.
2. 재배치한 `data-pension`과 `data-irp`·`data-isa`를 `scripts/validate_palette.js`로 여섯 검사(명도 대역·채도 하한·CVD 분리·정상 시야 하한·표면 대비, 인접쌍/전체쌍) 전부 라이트·다크 양쪽에서 다시 통과시키고, 그 출력을 3.5.4절에 갈아 끼운다.
3. 새 `accent` 초록이 `state-warning`(H73)·`state-error`(H25)와 각각 충분히 분리되는지 같은 방식으로 확인한다.
4. `LawChip`·`BasisBlock`·포커스 링 등 P2가 걸린 모든 자리에서 새 색의 대비(텍스트 4.5:1 / 비텍스트 3:1)를 8.4절 방식으로 라이트·다크 재실측한다.

**이 넷을 건너뛰고 `accent`만 바꾸면, 지난 회차(3.5.1절)와 같은 형태의 실패가 반복된다** — 증상만 눈으로 고치고 원인(분리 실패·대비 붕괴)은 재지 않은 채 남기는 것.

## 5. 컴포넌트

각 컴포넌트의 **기본 / 호버 / 포커스 / 비활성 / 오류** 상태를 정의한다. 해당 없는 상태는 "해당 없음"으로 명시했다 — 빈칸으로 두면 구현 단계에서 임의로 채워진다.

### 5.1 `TextField` / `NumberField` / `CurrencyField`

라벨(위, `type-body-s`, `text-secondary`) → 필드 → 도움말 또는 오류(아래, `type-caption`).

| 상태 | 명세 |
|---|---|
| 기본 | 높이 48px, `surface-sunken` 바탕, `border-strong` 1px, `radius-m`, 좌우 패딩 `space-3`. 값은 `type-body` + `text-primary` |
| 호버 | 테두리 `accent` 40% 혼합. 바탕 변화 없음 |
| 포커스 | 테두리 `accent` 1px + 바깥 `focus-ring` 2px(offset 2px). 바탕 `surface-raised`로 밝아진다 |
| 비활성 | 바탕 `surface-sunken`, 텍스트·테두리 `text-muted`, 커서 `not-allowed`. **조건부 노출 필드는 비활성이 아니라 미표시로 처리한다** (요구사항 AC: ISA 누적 납입액이 0이면 전환 항목을 "표시하지 않는다") |
| 읽기전용 | 테두리 없음, 바탕 투명, 값만 표시. 계산 결과를 되비출 때만 |
| 오류 | 테두리 `state-error` 1.5px, 바탕 `state-error-subtle`, 아래에 오류 메시지(`type-caption`, `state-error`) + 경고 아이콘. `aria-invalid`, `aria-describedby` 연결 |

`CurrencyField` 추가 규약: 우측에 고정 접미 `원`(`text-secondary`), 입력 중 천 단위 쉼표 자동 삽입, 값은 `tabular-nums`. **음수 입력 자체를 막지 않고 입력은 받되 오류로 표시한다** — 요구사항 AC가 "오류를 표시한다"이지 "입력을 막는다"가 아니다.

### 5.2 `SelectField` / `RadioGroup`

ISA 계좌 유형 2택, ISA 만기 전환 여부 2택에 쓴다. 선택지가 3개 이하이면 `RadioGroup`(가로 세그먼트)을 기본으로 한다 — 드롭다운을 열지 않고 선택지를 다 보여주는 편이 "선택지 비교"라는 이 제품의 성격에 맞는다. 선택지가 4개 이상이거나 각 선택지에 설명이 붙으면 세로 목록형(`HorizonChoiceGroup`, 5.22절)을 쓴다.

| 상태 | 명세 |
|---|---|
| 기본 | 세그먼트 한 칸: 높이 44px, `surface-sunken`, 텍스트 `text-secondary` |
| 선택됨 | 바탕 `accent-subtle`, 테두리 `accent` 1.5px, 텍스트 `text-primary` + 600 |
| 호버 | 바탕 `surface-raised` |
| 포커스 | 그룹 전체가 아니라 **선택 항목 하나**에 `focus-ring` 2px. 방향키로 이동 |
| 비활성 | 전체 그룹 흐림 + `aria-disabled`. 개별 선택지만 비활성인 경우 사유를 캡션으로 함께 표시한다 |
| 오류 | 그룹 테두리 `state-error`, 아래 오류 캡션 |

### 5.3 `ConditionalGroup`

ISA 만기 전환 항목처럼 상위 값에 따라 나타나는 필드 묶음.

- 나타남: 높이 애니메이션 180ms `ease-out`, 좌측에 `border-subtle` 2px 세로선 + 좌패딩 `space-4`로 종속 관계를 시각화.
- 사라짐: 즉시 제거하고 그 안의 값을 0으로 되돌린다. **값을 남겨두고 숨기면 사용자가 모르는 값이 계산에 들어간다.** 사라질 때 결과 패널에 "ISA 만기 전환 항목이 계산에서 제외되었습니다" 한 줄을 3초간 표시한다.
- `prefers-reduced-motion`이면 애니메이션 없이 전환한다.

### 5.4 `Button`

| 변형 | 기본 | 호버 | 포커스 | 비활성 | 오류 |
|---|---|---|---|---|---|
| `primary` | `accent` 바탕, `text-on-accent`, 높이 48px, `radius-m` | `accent-hover` | `focus-ring` 2px offset 2px | `surface-sunken` 바탕 + `text-muted`. **비활성 사유를 버튼 아래 캡션으로 반드시 표시** | 해당 없음 |
| `secondary` | 투명 바탕, `border-strong`, `text-primary` | 바탕 `surface-sunken` | 동일 | 테두리·텍스트 `text-muted` | 해당 없음 |
| `text` | 텍스트만, `text-link` | 밑줄 | 동일 | `text-muted` | 해당 없음 |
| `danger` | 투명 바탕, `state-error` 테두리·텍스트 | 바탕 `state-error-subtle` | 동일 | `text-muted` | 해당 없음 |

**비활성 버튼은 사유 없이 존재할 수 없다.** "계산하기"가 비활성이면 그 아래에 남은 항목 수가 붙는다. 이 규약이 `screens.md`의 입력 부족 상태 설계와 짝을 이룬다.

### 5.5 `RequirementChecklist`

입력 부족 상태의 주인공. 결과 패널이 "무엇을 더 넣으면 결과가 나오는가"를 답하는 컴포넌트다.

- 항목: `[○] 나이` / `[●] 총급여액` 형태. 채워짐은 채운 원 + `text-secondary` + 취소선 없음(취소선은 실패의 인상을 준다), 미충족은 빈 원 + `text-primary`.
- **각 항목은 버튼이다.** 누르면 해당 입력 필드로 스크롤 + 포커스. 모바일에서는 입력 영역으로 스크롤한다.
- 상단에 진행 표시: `n / m 항목` + 가로 진행 막대(`accent`, 높이 4px, `radius-full`).
- **분모 `m`은 무조건 필수인 항목 수로 고정한다.** 조건부로 생기는 필수 항목(예: ISA 만기 전환을 선택했을 때의 전환 금액)은 분모에 넣지 않는다 — 넣으면 사용자가 값을 채우는 도중에 진행 막대가 뒤로 가는 것처럼 보인다. 대신 목록 아래에 **별도 줄**로 붙이고, 무조건 필수가 다 찼는데 조건부가 남았으면 `m / m · 추가 항목 k개`로 표시한다. 다 채웠는데 결과가 없는 상태를 설명 없이 두지 않는다.
- 상태: 기본 / 호버(바탕 `surface-sunken`) / 포커스(`focus-ring`) / 비활성(해당 없음 — 항목이 비활성이면 표시하지 않는다) / 오류(해당 항목이 오류 상태이면 원 대신 `state-error` 경고 아이콘 + 오류 요약).

### 5.6 `AmountCard` — 금액 표시의 유일한 통로

**P1의 구조적 장치.** 금액을 크게 보이려면 반드시 이 컴포넌트를 쓴다. 슬롯이 셋이고 셋 다 필수다.

```
┌────────────────────────────────────────────┐
│ 라벨          (type-body-s / text-secondary)│  ← 슬롯1 (필수)
│ {금액}        (type-display / text-primary) │  ← 슬롯2 (필수)
│ 조건 캡션     (type-caption / text-secondary)│  ← 슬롯3 (필수, 비울 수 없음)
└────────────────────────────────────────────┘
```

- 슬롯3에는 기준 과세연도 · 적용 대상(소득 구간 등) · 주요 가정이 한 줄로 들어간다. 예: `2026 과세연도 기준 · 입력한 총급여 구간 적용 · 다른 소득공제 미반영`
- 슬롯3이 비면 컴포넌트가 성립하지 않는다. 구현에서 빈 문자열을 허용하지 않는다.
- 개정예고 룰이 쓰였으면 라벨 우측에 `ProposedBadge`가 붙는다.
- 상태: 기본 / 로딩(슬롯2가 `Skeleton`, 슬롯1·3은 실제 텍스트 유지) / 오류(슬롯2에 `—` + 슬롯3에 사유) / 비활성·호버·포커스 해당 없음(비대화형).

#### 상한 변형 (`bounded`) — `screens.md` 4.8절

계산에 필요한 값을 사용자가 `모름`으로 두어 **결과가 상한으로만 성립할 때** 쓴다. 슬롯이 하나 늘어 넷이 된다.

```
┌────────────────────────────────────────────┐
│ 라벨                                        │  ← 슬롯1
│ 최대 {금액}                                 │  ← 슬롯2 + 상한 접두
│ 조건 캡션                                   │  ← 슬롯3 (필수)
│ ─────────────────────────────────────────  │
│ 방향 고지 — 임계값과 틀릴 방향 한 줄          │  ← 슬롯4 (이 변형에서만, 필수)
│ ▸ {되돌아갈 입력} 넣기                       │
└────────────────────────────────────────────┘
```

| 규약 | 내용 |
|---|---|
| 상한 접두 | `최대`. `type-display`와 같은 크기·굵기로 금액과 한 덩어리처럼 보인다. **줄바꿈으로 금액과 분리되지 않는다** |
| 슬롯4 위치 | **금액 아래 24px 이내, 같은 카드 안.** 다른 카드로 밀거나 접으면 헌장 D11 위반이다 |
| 슬롯4 내용 | **임계값**(엔진이 낸 값)과 **틀릴 방향**을 한 문장에 담는다. 방향은 한쪽으로만 열려야 한다 — 양쪽으로 열리면 상한 표기 자체가 성립하지 않는다 |
| 슬롯4를 비울 수 없다 | 슬롯3과 같은 규약. 비면 `최대`가 이유 없는 완화어가 된다 |
| 되돌아갈 경로 | `text` 변형 링크. **버튼이 아니다** — 누르지 않아도 결과는 완결되어 있고, 버튼으로 만들면 재촉으로 읽힌다 |
| 색 | 기본 변형과 같다. **`state-warning`을 쓰지 않는다** — 상한은 오류가 아니라 사용자가 정직하게 답한 결과다 |

**공유 이미지에서도 이 변형이 유지된다.** 상한 접두와 슬롯4가 함께 실린다 — 조건 없는 금액이 화면 밖으로 나가는 것이 이 제품의 가장 큰 노출 위험이기 때문이다(`screens.md` 9절).

### 5.7 `AllocationBar` — 한도 트랙 막대

계좌 하나의 배분을 나타내는 가로 막대. 결과 화면 확정안에서 입체 도넛 바로 아래에 놓이며, **도넛의 원근 왜곡을 검산할 수 있는 왜곡 없는 표현**을 겸한다(`screens.md` 5.4절).

```
연금저축                       {월 배분액} / 월        ← 라벨 행
█████████████░░░░░░░░░░░░░░░░░░░░░  ← 채움 + 트랙
└ 납입 잔여 한도 대비 {n}% · 기납입 {금액} 반영
```

- **트랙 전체 길이 = 해당 계좌의 `contribution_limit_remaining_krw`(납입 잔여 한도).** 채움 = 이번 배분액. 트랙 왼쪽 끝에 사선 해칭으로 **기납입액** 구간을 표시할 수 있다(선택).
- **`credit_eligible_limit_remaining_krw`를 트랙 기준으로 쓰지 않는다.** 그 값은 배분 상한이 아니어서 채움이 트랙을 넘는 그림이 나올 수 있다(`screens.md` 5.10절). 트랙-채움 관계는 **넘을 수 없는 상한**에만 성립한다.
- 높이 20px, `radius-full`, 트랙 `data-track`, 채움은 계좌 색.
- 계좌 세 개의 트랙 길이는 **서로 다른 스케일을 쓰지 않는다.** 같은 픽셀=같은 금액이어야 계좌 간 비교가 성립한다. 한 계좌의 한도가 화면을 넘치면 전체를 축소하지 말고 **공통 배율**을 낮춘다.
- 상태:
  - 기본 / 호버(트랙 위 툴팁으로 정확한 금액 — 단, 툴팁이 유일한 정보 전달 수단이 되면 안 된다. 금액은 라벨 행에 이미 있다) / 포커스(막대가 tabbable, `focus-ring`, 스크린리더는 `연금저축, 월 {금액}, 납입 잔여 한도의 {n}%`)
  - **배분액 0**(자격은 있으나 이 배분안에서 배분되지 않음): 채움 없이 트랙만 + `이 배분에서는 배분하지 않음` 캡션
  - **배분 대상 아님**(`eligible: false`): 트랙을 `data-track` 실선으로 채우지 않고 **`data-excluded` 1px 점선 윤곽만** 그린다. 금액 자리에 `배분 대상 아님`. 사유 문장과 `LawChip`이 캡션에 붙는다. **행 자체는 지우지 않는다** — 계좌 순서가 항상 같아야 하고, 계좌가 사라지면 사용자가 그 계좌를 왜 못 보는지 알 수 없다. **초판은 여기에 `border-subtle`(대비 1.27)을 썼다.** 이 점선은 장식이 아니라 "이 계좌는 계산 대상이 아니다"를 나르는 경계이므로 비텍스트 대비 3:1이 필요하다(3.5.3절)
  - 오류(해당 계좌 계산 실패): 트랙을 `state-error` 점선으로
- **빈 실선 트랙과 점선 윤곽은 다른 뜻이다.** 전자는 "한도는 있는데 이번에 안 채웠다", 후자는 "이 계좌는 이번 계산의 대상이 아니다". 같은 모양으로 그리면 두 상태가 구분되지 않는다.

### 5.8 배분안 이름 규약

**별도의 선택기 컴포넌트를 두지 않는다.** 배분안 전환은 `ScenarioStackBar`(5.21절)의 행 클릭이 겸한다 — 비교 그림과 선택기를 분리하면 같은 것을 두 번 말하게 된다(`screens.md` 4.1절). 여기서는 어디에 쓰이든 지켜야 할 **이름 규약**만 정한다.

- 이름은 **계산이 무엇을 우선했는지**를 그대로 부른다: `세액공제액이 가장 큰 배분` · `연금저축을 먼저 채우는 배분` · `ISA를 먼저 채우는 배분`. 엔진 계약의 배분안 종류와 1:1로 대응한다.
- 기본안에는 `기본` 표시만 단다.
- **"추천"·"최적"·"권장"을 이름에 쓰지 않는다.** 개인 지시로 읽힐 여지를 줄인다. 기본안이 최대 절세액이 아닐 수 있으므로(자금 사용 시점이 순서를 바꿀 수 있다) "최적"은 사실과도 어긋난다.
- 이름 옆에 절감세액(`type-caption`, tabular-nums)과 기본안 대비 차액을 함께 적는다.

### 5.9 `LawChip` — 법령 조항 칩

**P2의 최소 단위.** 룰셋의 `source.law` 문자열을 가공 없이 그대로 담는다.

```
[ 소득세법 §59조의3 ① ]
```

- `radius-s`, 테두리 `border-subtle`, 바탕 `surface-sunken`, `type-caption-strong`, `text-secondary`.
- 누르면 같은 화면의 `BasisBlock` 해당 항목으로 스크롤 + 하이라이트 1.2초. **새 페이지로 이동하지 않는다** — 헌장의 "같은 화면에서" 요구.
- 개정예고 룰이면 칩 좌측에 사선 해칭 4px 바 + `ProposedBadge` 인접.
- 상태: 기본 / 호버(바탕 `accent-subtle`) / 포커스(`focus-ring`) / 비활성(해당 없음) / 오류(룰셋에 `source.law`가 없으면 칩을 그리지 않고 그 자리에 `state-error` 캡션 `근거 조항 미표기 — 이 항목은 표시하지 않습니다`를 띄운다. 조항 없는 숫자를 화면에 내보내지 않는다).

### 5.10 `BasisBlock` — 근거 블록 (고지 ③)

적용된 모든 조항을 나열한다. **기본 상태가 펼침이다.**

- 각 행: `LawChip` + 규칙이 정한 내용 요약(한 문장) + 기준 과세연도 + `원문` 링크(`text-link`, 새 탭, `rel="noopener"`).
- 접기 가능하되, 접힌 상태에서도 헤더에 `적용 조항 {n}건 · 2026 과세연도 기준`이 남는다.
- 상태: 기본(펼침) / 접힘 / 로딩(행 스켈레톤 3줄) / 오류(`근거를 불러오지 못했습니다` + 결과 표시 자체를 중단) / 비활성·호버·포커스는 아코디언 헤더에만 적용.

### 5.11 `AssumptionBlock` — 가정 블록 (고지 ④)

서비스가 세운 가정을 항목으로 나열한다. 기본 펼침. 각 항목은 `type-body-s`, `text-secondary`.
`BasisBlock`과 시각적으로 같은 골격을 쓰되 아이콘·헤더 문구로 구분한다.

### 5.12 `DisclosureBanner` — 성격·자격 배너 (고지 ①②)

결과 패널 최상단. **접히지 않고, 스크롤로 밀려나도 결과 영역을 벗어날 수 없다.**

- 좌측에 정보 아이콘, 우측에 2문장. `type-caption`, `text-secondary`, 바탕 `state-info-subtle`, 좌측 3px `state-info` 바, `radius-m`.
- 상태: 기본 하나뿐. 닫기 버튼 없음. 접기 없음.

### 5.13 `LimitNote` — 한계 안내 (고지 ⑤)

결과 영역 하단 고정. `AssumptionBlock`과 같은 형태이나 접히지 않는다.

### 5.14 `ProposedBadge` — 개정예고 배지 (고지 ⑥)

```
[ 정부안 · 국회 통과 전 ]
```

- `radius-s`, 바탕 `state-info-subtle`, 텍스트 `state-info`, `type-caption-strong`, 좌측에 사선 해칭 4px 바.
- 룰셋의 `bill_stage` 값을 그대로 읽어 표시한다. 문자열을 재작성하지 않는다.
- 이 배지가 붙은 시나리오는 차트 계열에도 해칭이 적용되고, 시나리오 카드 상단에 한 줄 캡션(`이 시나리오는 아직 국회를 통과하지 않은 개정안을 반영한 계산입니다`)이 함께 붙는다. 배지 하나로 끝내지 않는다.

### 5.15 `Skeleton`

`surface-sunken` 바탕 + 1.2s 좌→우 밝기 이동. `prefers-reduced-motion`이면 정적. **스켈레톤 안에 숫자 모양을 그리지 않는다** — 실제 값으로 오인될 여지를 없앤다. 도형은 무채색 사각형뿐이다.

### 5.16 `InlineAlert`

| 변형 | 바탕 / 테두리 / 아이콘 | 쓰임 |
|---|---|---|
| `error` | `state-error-subtle` / `state-error` | 계산 불가, 필드 오류 요약 |
| `warning` | `state-warning-subtle` / `state-warning` | 미배분 잔액 발생, 한도 초과 입력 |
| `info` | `state-info-subtle` / `state-info` | 조건부 항목 제거 안내, 개정예고 |

제목(`type-body-strong`) + 본문(`type-body-s`) + 선택적 조치 버튼(`text` 변형). 상태: 기본 / 호버·포커스는 내부 버튼에만 / 비활성 해당 없음.

### 5.17 `Tooltip` / `HelpPopover`

입력 항목의 "이 값을 어디서 확인하나요" 안내에 쓴다.

- **툴팁은 보조 정보만 담는다.** 툴팁에만 존재하는 정보는 금지 — 터치 기기와 스크린리더에서 사라진다. 고지 여섯 요소 중 어느 것도 툴팁에 담지 않는다.
- 트리거는 44px 히트 영역의 아이콘 버튼. 클릭/탭으로 열고 `Esc`로 닫는다. 호버 전용 금지.

### 5.18 `Modal` / `BottomSheet`

저장·공유에 쓴다. 데스크톱은 중앙 모달(최대 폭 480px), 모바일은 바텀시트. 포커스 트랩, `Esc` 닫기, 열릴 때 배경 스크롤 잠금, 닫히면 트리거로 포커스 복귀.

### 5.19 `StickySummaryBar` (모바일 전용)

화면 하단 고정 56px 바. 입력 부족 상태면 `남은 항목 {n}개`, 결과가 있으면 `절감세액 {금액} · 결과 보기`. 탭하면 결과 시트가 올라온다.
상태: 입력 부족 / 계산 중(스켈레톤 + `계산 중`) / 결과 있음 / 오류(`state-error-subtle` 바탕 + `계산할 수 없습니다`).

### 5.20 `AccountDonut` — 입체 도넛

배분 비중을 원형으로 보여주는 주 시각화. **기하 파라미터가 고정값이고 반응형·애니메이션에서도 변하지 않는다.**

| 파라미터 | 값 | 변경 가능 여부 |
|---|---|---|
| 기울기 | 15° | **고정.** 크면 원근 왜곡이 커진다 |
| 압출 두께 | 반지름의 8% | **고정** |
| 시작각 | 12시 | **고정** |
| 조각 순서 | 연금저축 → IRP → ISA → 미배분, 시계방향 | **고정.** 값 크기순 정렬 금지 |
| 외경 | 뷰포트별 200 / 240 / 260px | 반응형으로 변함 |

- 조각 색은 계좌 고정 매핑(3.5절). **압출 측면은 전용 토큰이다.**

| 측면 토큰 | 라이트 | 다크 |
|---|---|---|
| `data-pension-side` | `#017572` | `#087C78` |
| `data-irp-side` | `#B34F03` | `#B75203` |
| `data-isa-side` | `#67369D` | `#6E3DA7` |
| `data-unallocated-side` | `#3C4247` | `#8E959C` |

  **초판은 "상단면 색의 명도 −18%"라고만 적고 토큰을 만들지 않았다. 그것은 구현할 수 없는 문장이다** — 어느 색공간의 명도인지, 곱인지 뺄셈인지가 정해지지 않으면 구현마다 다른 색이 나온다. 산식은 **OKLCH에서 L − 0.112, 색상각과 채도는 유지, 색역을 벗어나면 채도만 낮춰 클램프**이고, 그 결과를 위 표에 박아 두었다. **구현은 산식을 다시 돌리지 말고 표의 값을 쓴다.**
- **측면은 정체를 나르지 않는다 — 상단면이 나른다.** 그래서 측면은 3.5절 여섯 검사의 대상이 아니고, 두 가지만 요구한다: ① 상단면과 같은 색상각 ② 인접 측면끼리 적록색각이상 ΔE ≥ 8(측정값: 라이트 최악쌍 12.2 · 다크 12.9). 측면 대 상단면 대비는 1.57~1.62로 깊이가 보이되 다른 계좌로 읽히지 않는다.
- **다크의 `data-isa-side`는 카드 대비 2.20으로 유일하게 3:1 아래다.** 값이 아니라 실루엣만 나르는 면이라 허용하되, **다크에서 도넛 아래쪽 윤곽이 가장 약해지는 자리**이므로 3단계에서 실제 렌더를 보고 확인한다.
- 개정예고 해칭은 **상단면에만** 얹는다. 측면에 얹으면 원근 때문에 패턴 간격이 왜곡된다.
- 값 변화 시 조각 각도만 240ms로 바뀐다. **뷰 각도 회전·확대 애니메이션 금지.**
- 중앙에 **월 배분 총액**이 들어간다(`screens.md` 5.13절). 라벨 줄(`월 배분`, `type-body-s`) + 값 줄(`type-display`). **절감세액을 여기 넣지 않는다** — 그 금액은 `AmountCard`가 도형 밖에서 맡는다.
- 상태: 기본 / 호버(조각 밝기 +6%, 툴팁은 보조 정보만) / 포커스(조각이 tabbable, `focus-ring`, 스크린리더 `연금저축, 월 {금액}, 전체의 {n}%`) / 비활성(배분액 0이거나 배분 대상이 아닌 계좌는 조각을 그리지 않는다 — 그 계좌의 사정은 `AllocationBar` 행과 계좌별 표가 말한다) / 오류(도넛을 그리지 않고 그 자리에 `InlineAlert`).
- **입력 부족·빈 상태에서는 이 컴포넌트가 아니라 `ResultPlaceholder`(5.29절)가 같은 자리를 갖는다.** 조각이 0개인 `AccountDonut`을 그리지 않는다 — 그것이 "배분이 0원인 결과"로 읽히는 경로다.

**조각이 하나뿐일 때 — 반드시 지킬 렌더링 규약.**

한 계좌가 100%를 차지하면 조각의 시작각과 끝각이 같아지고, **호(arc) 하나로 그리면 아무것도 그려지지 않는다.** 배분 대상 계좌가 배제로 줄어들면 흔해지는 경로다.

- 360° 조각은 호가 아니라 **닫힌 고리**로 그린다. 두 개의 180° 호를 잇거나 원 두 개(외경·내경)의 차집합으로 만든다. 구현 방식은 자유이나 **결과가 폭 0이 되어서는 안 된다.**
- 이 규약은 조각이 2개일 때도 각도가 0에 가까운 조각에 적용된다 — 배분액이 0보다 크면 **최소 2° 이상**의 각을 보장하고, 그로 인한 각도 왜곡은 조각 라벨의 금액이 바로잡는다. 보이지 않는 조각보다 약간 부정확한 조각이 낫다.

### 5.21 `ScenarioStackBar` — 배분안 비교 스택바

같은 폭(= 월 납입 여력 100%)의 가로 막대를 배분안 수만큼 세로로 쌓는다. 조각 경계가 위아래로 정렬되는 것이 이 컴포넌트의 존재 이유다. 행 클릭이 배분안 전환을 겸한다(5.8절).

- 행 높이 28px, 행 간격 `space-2`. 조각 색은 계좌 고정 매핑 + `data-unallocated`.
- 우측에 절감세액과 기본안 대비 차액(`tabular-nums`).
- 상태: 기본 / 선택됨(좌측 `▸` + 행 바탕 `accent-subtle`) / 호버(행 바탕 `surface-sunken`) / 포커스(행이 tabbable, 방향키로 행 이동) / 비활성(성립하지 않는 배분안은 행 자체를 그리지 않는다) / 오류(해당 없음 — 계산 실패 시 결과 영역 전체가 오류 상태로 간다).
- **행마다 라벨 유무가 달라지지 않는다.** 조각 안에 라벨이 들어갈 폭이 안 되면 전 행이 범례로 통일한다.
- 행 우측에 그 배분안의 중도 불이익 안내 개수 표식(`▍n`)을 단다. 0이면 표식을 그리지 않는다.

### 5.22 `HorizonChoiceGroup` — 설명이 붙는 세로 선택지

`fund_use_horizon`(자금 사용 시점) 4택에 쓴다. 각 선택지가 라벨 + 설명 + **선택적 보조 캡션** 세 줄을 갖는 형태다.

```
┌──────────────────────────────────────┐
│ ○  라벨            (type-body-strong) │  ← 항상 있다
│    설명            (type-body-s)      │  ← 항상 있다
│    └ 보조 캡션      (type-caption)    │  ← 데이터가 오면 나타난다
└──────────────────────────────────────┘
```

- 각 항목 최소 높이 64px(터치 타깃 여유), 좌측 라디오 20px, `radius-m`, 항목 사이 `border-subtle` 1px.
- **보조 캡션 줄의 자리를 미리 예약한다.** 값이 늦게 도착해도 레이아웃이 밀리지 않아야 한다. 값이 끝내 오지 않으면 예약된 자리를 접는다.
- **보조 캡션은 라벨을 대신하지 못한다.** 캡션이 없어도 라벨 + 설명만으로 선택이 가능해야 한다 — 캡션에는 룰셋에서 온 수치가 들어가는데 그 수치가 없다고 입력이 막히면 안 된다(`screens.md` 3.4절).
- **미리 선택된 항목이 없다.** 이 컴포넌트를 쓰는 입력은 기본값을 갖지 않는다. "모르겠다"에 해당하는 선택지가 있더라도 그것 역시 사용자가 눌러야 선택된다.
- 그룹 아래에 **효과 고지 캡션**을 둔다 — 이 선택이 무엇을 바꾸고 무엇을 바꾸지 않는지. 필수 슬롯이며 비울 수 없다.
- 상태: 기본 / 선택됨(테두리 `accent` 1.5px + 바탕 `accent-subtle`) / 호버(바탕 `surface-sunken`) / 포커스(항목 하나에 `focus-ring`, 방향키 이동) / 비활성(항목 단위 비활성 시 사유 캡션 필수) / 오류(그룹 테두리 `state-error` + 아래 오류 캡션).

### 5.23 `WarningNote` — 중도 불이익 안내

계산 결과에 딸려 오는 규칙 안내를 담는다. **`InlineAlert`(5.16절)와 다르다** — `InlineAlert`는 사용자가 무언가를 고쳐야 하는 상태를 알리고, `WarningNote`는 고칠 것이 없는 사실을 알린다. 둘을 같은 컴포넌트로 만들면 결과가 오류처럼 보인다.

```
▍{문두(info일 때만)}{사실 서술 문장}
▍[법령 조항 칩]  [법령 조항 칩]
```

| 요소 | 명세 |
|---|---|
| 좌측 바 | 3px. `severity: warning`이면 `state-warning`, `info`면 `state-info` |
| 바탕 | 각각 `state-warning-subtle` / `state-info-subtle` |
| 아이콘 | 16px. 크게 키우지 않는다 |
| 본문 | `type-body-s`, `text-secondary`. **한 문장.** 여러 규칙이면 노트를 나눈다 |
| 조항 칩 | `LawChip` 1개 이상 **필수.** 칩 없는 `WarningNote`는 성립하지 않는다 |
| 금액 | **넣을 수 없다.** 금액 슬롯이 없는 컴포넌트다 |

- **제목 슬롯이 없다.** 제목을 두면 "주의"·"경고" 같은 말이 들어가고, 그것이 겁주는 화면의 시작이다.
- 문구 제약은 `screens.md` 4.7절의 표를 따른다. 느낌표·2인칭 지시·"손해"·"위험"을 쓰지 않는다.
- 상태: 기본(`warning`) / 기본(`info`) / 로딩(그리지 않는다 — 결과와 함께 온다) / 비활성·호버·포커스는 내부 `LawChip`에만 / 오류(해당 없음).

### 5.24 `EligibilityNote` — 배분 대상 아님 통지

계좌가 법령 요건 때문에 배분 대상에서 빠졌다는 **사실 통지**. `AccountEligibility.eligible: false`에 붙는다.

**`WarningNote`와 색이 다르다 — `state-info`를 쓰고 `state-warning`을 쓰지 않는다.** 근거: 배제는 사용자가 무언가를 잘못해서 생긴 상태가 아니고, 대비해야 할 위험도 아니다. 법령 요건에 해당하지 않는다는 사실일 뿐이다. 주의 색을 칠하면 사용자가 자기 상황을 결함으로 읽는다. 엔진이 이 notice를 `severity: warning`으로 내지만(`isa_excluded_*`), 그것은 **결과의 정확도에 영향을 준다는 뜻**이지 사용자에게 경고하라는 뜻이 아니다 — 화면의 색은 화면이 정한다.

| 요소 | 명세 |
|---|---|
| 좌측 바 | 3px `state-info` |
| 바탕 | `state-info-subtle` |
| 본문 | `type-body-s`. **한 문장으로 사유를 서술한다.** 주어는 법령 요건이지 사용자가 아니다 |
| 조항 칩 | `LawChip` 1개 이상 **필수** |
| 금액 | 넣지 않는다 |

- 문구는 `screens.md` 5.9절의 표를 따른다. `제외되었습니다`처럼 처분받은 인상을 주는 수동태보다 `이번 계산의 배분 대상이 아닙니다`처럼 상태를 서술한다.
- **조치를 지시하지 않는다.** `금융소득종합과세 대상이 아니라면 입력을 고쳐 주세요` 같은 문장을 붙이지 않는다 — 입력 패널에 이미 그 항목이 있다.
- 상태: 기본 하나뿐. 접기·닫기 없음.

### 5.25 `BirthDateField` — 생년월일 한 칸

`screens.md` 3.7절. **이 시스템에서 가장 민감한 값을 담는 유일한 컴포넌트**이고, 그래서 다른 필드에 없는 금지 규약이 붙는다.

```
생년월일                            ← 라벨 (type-body-s / text-secondary)
┌──────────────────────────────┐
│ 1988-03-15                   │   ← 값 (type-body / tabular-nums)
└──────────────────────────────┘
만 나이를 계산에 씁니다. 이 값은      ← 도움말 (type-caption / text-secondary)
브라우저 밖으로 나가지 않습니다.       항상 표시. 비울 수 없다
```

| 항목 | 명세 |
|---|---|
| 형태 | **한 칸.** 세 칸 분리·달력 위젯을 쓰지 않는다. 근거는 `screens.md` 3.7.2절 |
| 입력 | 숫자 8자리. 입력 중 `YYYY-MM-DD`로 자동 하이픈. `CurrencyField`의 천 단위 쉼표와 같은 마스킹 규약 |
| 키보드 | `inputmode="numeric"`. 모바일에서 숫자 키패드가 올라온다 |
| 자동완성 | **끈다.** `bday` 등 표준 토큰을 쓰지 않는다 — 값이 브라우저 프로필·동기화 계정으로 흘러 우리가 통제하지 못하는 표면이 생긴다 |
| 값 되비추기 | **하지 않는다.** 만 나이를 필드 옆에 표시하지 않는다 — 화면에 상주하는 순간 스크린샷·화면 녹화·공유 이미지에 함께 실린다 |
| 붙여넣기 | 허용한다. 하이픈이 있든 없든 8자리로 정규화한다 |
| 저장 | `localStorage`·`sessionStorage`에 **쓰지 않는다** |

| 상태 | 명세 |
|---|---|
| 기본 | `TextField`(5.1절)와 동일. 높이 48px, `surface-sunken`, `border-strong` |
| 플레이스홀더 | `YYYY-MM-DD`(`text-muted`) |
| 호버·포커스 | 5.1절과 동일 |
| 비활성 | 해당 없음 — 이 필드는 조건부가 아니고 항상 필수다 |
| 읽기전용 | 해당 없음 |
| 오류 | 5.1절 오류 상태 + **오류 문구에 사용자가 입력한 값을 되풀이하지 않는다.** 값을 되풀이하면 DOM에 한 번 더 복제되고 `aria-live`로 읽혀 나간다 |
| "모름" | **없다.** 사용자가 반드시 아는 값에 "모름"을 두면 그것은 선택지가 아니라 건너뛰기 버튼이 된다 |

- 스크린리더: 하나의 필드로 읽힌다. 라벨·도움말·오류가 `aria-describedby`로 연결된다.
- 만 나이 변환은 **컴포넌트 밖에서** 일어난다. 이 컴포넌트는 날짜 문자열만 다루고, 나이를 만드는 것은 폼 상태 계층의 일이다 — 그래야 원본이 어디까지 흐르는지가 한 곳에서 보인다.

### 5.26 `KnownOrUnknownField` — 값 또는 "모름"

`screens.md` 3.8절. **사용자가 진짜로 모를 수 있는 값**을 받되, 비어 있음과 모름을 구분해야 할 때 쓴다.

```
라벨                                  [ ? ]
┌──────────────────────────────────┐
│                              원 │   ← 값 칸 (CurrencyField 규약을 그대로)
└──────────────────────────────────┘
┌──────────────────────────────────┐
│ ○ 모르겠습니다                     │   ← 1급 선택지. 비어 있음과 다르다
└──────────────────────────────────┘
효과 고지 캡션                            ← 필수 슬롯. 비울 수 없다
▸ 이 값을 어디서 찾나요                    ← SourceGuide (선택)
```

| 규약 | 내용 |
|---|---|
| 세 상태 | `빈`(둘 다 미접촉) · `값`(0 포함) · `모름`. **셋이 서로 다른 상태이고 결과 화면이 다르다** |
| 배타 | 값을 치면 `모르겠습니다`가 풀리고, `모르겠습니다`를 누르면 값 칸이 비워진다. **값을 남겨 두고 숨기지 않는다**(5.3절 `ConditionalGroup`과 같은 판단) |
| `0` | **유효한 값이고 `모름`과 다르다.** `0`은 사실이고 `모름`은 사실의 부재다 |
| 기본 선택 | **없다.** `모르겠습니다`도 사용자가 눌러야 선택된다 — `HorizonChoiceGroup`(5.22절)과 같은 규약 |
| 효과 고지 캡션 | **필수 슬롯.** 이 값이 결과의 무엇을 바꾸는지 한 문장. 못 쓰면 이 항목을 화면에 올리지 않는다 |
| 체크리스트 | 이 컴포넌트를 쓰는 항목은 **필수 항목이고 분모에 들어간다.** "모름"이 유효한 답이므로 진행을 막지 않으면서 명시적 진술은 확보된다 |

- 상태: 기본 / 호버·포커스(값 칸과 선택지 각각, 5.1·5.2절 규약) / 비활성(해당 없음) / 오류(값 칸에만 붙는다 — `모르겠습니다`는 오류가 될 수 없다).
- **`모름`일 때 결과 쪽에서 `AmountCard`의 상한 변형(5.6절)이 짝을 이룬다.** 이 두 컴포넌트는 함께 쓰이도록 설계됐다 — 입력에서 모름을 허용하면서 결과에서 그 사실을 감추면 정직함이 깨진다.

### 5.27 `SourceGuide` — "이 값을 어디서 찾나요"

`screens.md` 3.8.4절. **찾는 것 자체가 어려운 값**을 위한 인라인 확장 블록.

| 항목 | 명세 |
|---|---|
| 위치 | 해당 필드 바로 아래. 같은 자리에서 펼쳐진다 |
| 형태 | 인라인 확장. **모달·툴팁이 아니다** — 모달은 필드를 가려 값을 보며 칠 수 없고, 툴팁은 터치·스크린리더에서 사라진다(5.17절) |
| 기본 상태 | **접힘.** 이 시스템에서 접기가 허용되는 유일한 자리다. 접히는 것이 *답*이 아니라 *설명*이기 때문이다 |
| 고지와의 관계 | **고지가 아니다.** D11의 접기 금지(고지 ③④⑤)와 무관하다. 이 블록에 고지 내용을 담지 않는다 |
| 유지 | 한 번 펼치면 그 세션 동안 펼침 상태를 유지한다 |
| 내용 | 세 줄 — 종이·PDF에서 / 온라인에서 / **지금 확인할 수 없다면**. 세 번째가 없으면 이 블록은 막다른 길이다 |
| 문자열 | 서식 항목명·기관 메뉴 경로는 **화면이 지어내지 않는다.** `LawChip`이 `source.law`를 그대로 담는 것과 같은 규약(5.9절) |
| 미확정 | 항목명이 자리표시자로 남아 있으면 **개발 빌드가 그 사실을 드러낸다**(D19 — 미설정 상태는 조용하면 안 된다) |
| 트리거 | 44px 히트 영역. `type-body-s` + 회전 삼각형 아이콘 |

- 상태: 접힘 / 펼침 / 호버(트리거 밑줄) / 포커스(`focus-ring`) / 비활성·오류 해당 없음.
- 펼침·접힘 180ms `ease-out`. `prefers-reduced-motion`이면 즉시.

### 5.28 `ProvisionalStatusNote` — 아직 법으로 정해지지 않은 상태

`screens.md` 3.9절. **정부가 발표했으나 법령으로 확정되지 않은 기준**에 사용자가 해당하는지를 다룰 때 쓴다. `EligibilityNote`(5.24절)와 골격이 같고 성격이 다르다 — 저쪽은 *확정된 법령 요건*의 사실 통지이고, 이쪽은 *아직 확정되지 않았다는 사실* 자체가 내용이다.

| 요소 | 명세 |
|---|---|
| 좌측 바 | 3px `state-info`. **`state-warning`을 쓰지 않는다** — 사용자가 잘못한 것이 아니다 |
| 바탕 | `state-info-subtle` |
| 본문 | `type-body-s`. **두 문장이 짝을 이룬다** — ① 발표된 기준으로는 어떠한가 ② 아직 법으로 정해지지 않았다. **①만 쓰면 확정된 것으로 읽히고, ②만 쓰면 사용자가 무엇을 판단해야 할지 모른다** |
| `ProposedBadge` | **필수**(5.14절). 고지 ⑥이 여기서도 걸린다 |
| `LawChip` | **1개 이상 필수.** 조항 없는 세법 서술을 화면에 두지 않는다 |
| 수치 | **본문에 세법 수치를 쓰지 않는다.** 연령 범위 같은 값은 룰셋에서 와야 하고(제품 원칙 1), 룰셋에 없으면 **이 블록 자체를 그리지 않는다** |
| 자기신고 체크 | 선택 슬롯. 있으면 **미선택이 기본이고 화면이 대신 켜지 않는다** |
| 금액 | 넣을 수 없다 |

- **주어는 발표·법령이지 사용자가 아니다.** `정부가 발표한 개정안 기준으로는 …` ○ / `고객님은 … 에 해당합니다` ✗.
- 상태: 기본 하나뿐(체크 슬롯이 있으면 그 안에서 미선택/선택). 접기·닫기 없음.
- **룰셋에 값이 없으면 나타나지 않는다.** `HorizonChoiceGroup`의 보조 캡션과 같은 처리 — 데이터가 없으면 그 줄을 그리지 않고, 그래도 입력은 성립한다.

### 5.29 `ResultPlaceholder` — 결과가 아직 없는 자리

`screens.md` 8.1절. **입력 부족 상태에서 `AccountDonut`이 들어갈 자리를 지키는 도형**이다. 소유자 지시로 신설했다(2026-08-10).

**초판은 이 자리에 "도넛을 흉내내지 않는 무채색 도형"을 두기로 했고, 그 근거는 "빈 도넛을 그리면 배분이 0원인 결과로 읽힌다"였다. 소유자가 도넛 형태를 지시했으므로 형태 금지는 해제하되, 그 근거는 그대로 살아 있다.** 그래서 이 컴포넌트의 설계 전체가 하나의 질문에 답한다 — **어떻게 하면 도넛 모양이면서도 결과로 읽히지 않는가.** 답은 넷이다.

| # | 장치 | 왜 결과로 읽히지 않는가 |
|---|---|---|
| B1 | **조각 수 12** | 결과 도넛의 조각 수는 1~4개다(계좌 셋 + 미배분). **12는 이 제품의 어떤 결과도 만들 수 없는 수다.** 세다가 다섯 번째에서 이미 결과가 아니라는 것이 확정된다 |
| B2 | **12조각 전부 같은 각(30°)** | 균등 분할은 **비율 정보가 0**이다. 그럴듯한 비율이 없으므로 읽을 값이 없다. 세 계좌가 정확히 등분되는 배분은 만들어지지 않고, 12등분은 더더욱 불가능하다 |
| B3 | **평면. 기울기 0°, 압출 0** | 결과 도넛은 기울기 15°·두께 8%가 **고정**이다(5.20절 A1). 압출이 없는 링은 결과 도넛과 같은 도형일 수 없다 |
| B4 | **`data-placeholder` 단색 — 표면 대비 1.69(라이트) / 1.70(다크)** | 값을 나르는 모든 색은 3:1 이상이다(3.5.3절 대비 계층). **자리표시자는 2:1 미만이고, 2:1과 3:1 사이는 비어 있다.** 이 도형은 값이 입는 잉크를 입을 수 없다 |

**색에서 하지 않는 것 둘.**

- **`data-unallocated`를 쓰지 않는다.** 그 회색은 "미배분 잔액 100%"라는 **실재 가능한 결과**를 뜻한다. 자리표시자가 그 색을 입으면 그 순간 결과가 된다.
- **해칭을 얹지 않는다.** 45° 사선 해칭은 `bill_stage` 전용이다(3.5.5절 규약 3). 자리표시자에 쓰면 "국회 통과 전 계산 결과"로 읽힌다 — 가장 나쁜 오독이다.

```
                ╭─────────────╮          평면 링 (기울기 0°, 압출 0)
             ╭─╯ ┆ ┆ ┆ ┆ ┆ ┆ ╰─╮        12등분 · 조각 사이 4px 표면색 간격
            │  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄  │        전부 data-placeholder 단색
            │ ┆     월 배분     ┆ │        ← 라벨 줄 (결과에서도 같은 자리)
            │ ┆        ?       ┆ │        ← 값 줄 — 물음표가 금액 자리를 맡는다
            │  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄  │
             ╰─╮ ┆ ┆ ┆ ┆ ┆ ┆ ╭─╯
                ╰─────────────╯

          값을 모두 넣으면 여기에 결과가 표시됩니다      ← type-title-s / text-primary
          계좌별 배분 · 계산된 절세액 · 적용한 법령 조항   ← type-body-s / text-secondary
```

| 항목 | 명세 |
|---|---|
| 외경 | `AccountDonut`과 **같다** — 뷰포트별 200 / 240 / 260px. 링 두께도 같은 비율. 결과가 들어올 때 자리가 밀리지 않아야 한다 |
| 조각 | 12개 × 30°. 조각 사이 4px `surface-raised` 간격(3.5.5절 규약 5의 2px보다 넓다 — 넓은 간격이 "조각"이 아니라 "눈금"으로 읽히게 한다) |
| 색 | `data-placeholder` 하나. 조각마다 다르게 칠하지 않는다 |
| 중앙 라벨 줄 | `월 배분`(`type-body-s`, `text-secondary`). **결과 상태와 같은 문자열·같은 자리.** 이 줄이 물음표가 무엇의 자리인지 스스로 말한다 |
| 중앙 값 줄 | `?` 하나. **`type-display`와 같은 크기·굵기·기준선**으로 놓는다 — 완성 시 들어올 금액과 같은 메트릭으로 자리를 예약한다. 색 `text-muted`(대비 4.06 라이트 / 5.15 다크) |
| 애니메이션 | **없다.** 회전·맥동·shimmer 전부 금지. shimmer는 `Skeleton`(5.15절)의 것이고 "요청했고 오는 중"을 뜻한다. 자리표시자는 **아직 아무것도 요청하지 않은 상태**다. 움직이면 "곧 온다"로 읽힌다 |
| 눈금·범례·지시선 | 없다 |
| 숫자 | **없다.** 예시 금액·평균 금액·`0원` 전부 금지 |
| 접근성 | 링과 `?`는 `aria-hidden="true"`(장식). 대신 결과 패널에 시각적으로 숨긴 문장 하나: `아직 계산 결과가 없습니다. 위 목록의 남은 항목을 채우면 결과가 여기에 표시됩니다.` **`aria-live`를 걸지 않는다** — 빈 상태는 갱신이 아니다 |
| 강조 문구 | 링 아래 16px. 1행 `type-title-s` + `text-primary`, 2행 `type-body-s` + `text-secondary`. **강조는 크기·굵기·색으로만 한다** — 느낌표·화살표·`accent` 색을 쓰지 않는다(`accent`는 누를 수 있는 것의 색이고 이 문구는 누를 수 없다) |

**`RequirementChecklist`(5.5절)와의 관계 — 중복이 아니라 분업이다.**

| | 답하는 질문 | 담는 것 |
|---|---|---|
| `RequirementChecklist` | **무엇을 하면 되는가** | 항목 이름, 남은 개수, 진행 막대. 각 행이 버튼 |
| `ResultPlaceholder` | **무엇이 나오는가** | 결과의 형태와 자리. 문구 두 줄 |

- **자리표시자는 "무엇이 비었는지" 말하지 않는다.** 남은 항목 수·항목명을 링 안이나 문구에 적지 않는다. 적으면 같은 말을 두 번 하게 되고, **두 곳의 수가 실제로 어긋난다** — 조건부 필수 항목은 분모에 들어가지 않기 때문이다(`screens.md` 8.1절 5번). 어긋나는 순간 사용자는 어느 쪽을 믿어야 할지 모른다. **숫자는 체크리스트에만 있다.**
- **체크리스트는 결과의 형태를 그리지 않는다.** 미리보기 도형을 체크리스트 안에 넣지 않는다.
- **자리표시자를 눌러 체크리스트로 가는 동작을 두지 않는다.** 체크리스트가 이미 자리표시자 위에 있고, 위로 되감는 링크는 방금 읽은 곳으로 돌려보낸다.

**상태 셋과 그 사이의 전환.**

| 상태 | 도형 | 중앙 |
|---|---|---|
| 입력 부족 · 빈 | 평면 12등분 링 (`ResultPlaceholder`) | `월 배분` / `?` |
| 로딩(룰셋 로드 중) | `Skeleton` 사각형 (5.15절) | 없음 |
| 정상 | 입체 도넛 (`AccountDonut`) | `월 배분` / 금액 |

셋은 **모양이 서로 다르다** — 사각형 / 평면 링 / 입체 도넛. 어느 둘도 서로로 오인되지 않는다.

**자리표시자 → 결과 전환** (첫 계산이 성공하는 순간):

1. 자리표시자 링을 120ms에 투명도 0으로 내린다.
2. **그 다음 프레임에** 결과 도넛을 그린다. 12시 시작각에서 조각 각도를 0° → 최종값으로 240ms `ease-out`. 길이(각도)만 변한다.
3. **두 도형이 겹쳐 보이는 프레임이 없다.** 크로스페이드·모프 금지 — 12등분이 결과 조각으로 변형되는 것처럼 보이면 "자리표시자가 답이었다"는 인상이 생긴다.
4. 중앙: `?`를 120ms에 투명도 0, 금액을 120ms에 투명도 1로 **교체**한다. 숫자 롤링·카운트업 금지(6.1절 5번 — 중간값이 실제 값으로 오인된다). 라벨 줄(`월 배분`)은 **움직이지 않는다.** 같은 메트릭으로 자리를 예약해 두었으므로 레이아웃이 밀리지 않는다.
5. `prefers-reduced-motion: reduce`이면 1~4 전부 0ms, 즉시 교체.

**결과 → 자리표시자(되돌아가기, 예: 사용자가 필수 값을 지움): 위 전환을 역순으로 하지 않는다.** 결과 도넛을 즉시 제거하고 자리표시자를 즉시 표시한다. 역방향 애니메이션은 "결과가 자리표시자로 줄어든다"로 읽혀 금액이 감소한 것처럼 보인다.

- 상태: 기본 하나뿐. 호버·포커스·비활성·오류 **해당 없음** — 이 컴포넌트는 대화형이 아니고, 오류는 결과 패널이 `InlineAlert`로 처리한다.

### 5.30 `ThemeControl` — 화면 밝기

`screens.md` 2.1절. 헤더 우측, `이용 안내` 버튼 왼쪽.

| 항목 | 명세 |
|---|---|
| 형태 | 44px 아이콘 버튼(접근 이름 `화면 밝기`) → 누르면 세 항목 목록이 열린다: `자동` · `밝게` · `어둡게` |
| 왜 3택인가 | 2택 토글은 **`자동`을 표현할 수 없다.** 한 번 누르면 운영체제 설정을 따르던 상태로 영영 못 돌아간다 |
| 기본 선택 | `자동`. 사용자가 고르기 전까지 이 값이다 |
| 상호작용 | 클릭·탭으로 열고 `Esc`로 닫는다. **호버 전용 금지**(5.17절과 같은 규약). 포커스 트랩 없음, 닫히면 트리거로 포커스 복귀 |
| 항목 상태 | `RadioGroup`(5.2절) 규약을 그대로 쓴다. 선택됨 = 바탕 `accent-subtle` + 테두리 `accent` 1.5px |
| 아이콘 | 단색 선형 24px. **아이콘 단독으로 뜻을 나르지 않는다**(9절) — 열린 목록에 항상 텍스트 라벨이 있다 |
| 전환 | 테마가 바뀔 때 **색 트랜지션을 걸지 않는다.** 120ms 색 전환(6.2절)을 페이지 전체에 적용하면 수십 개 요소가 제각기 다른 타이밍으로 물들어 화면이 출렁인다. 즉시 교체한다 |
| 차트 | 테마 변경으로 **도넛의 각도 애니메이션이 발동하지 않는다.** 값이 바뀐 것이 아니므로 조각은 그 자리에 있고 색만 바뀐다 |

**저장 — 하는가.** 한다. 근거와 제약을 함께 적는다.

- 제품 원칙 4가 지키는 것은 **사용자의 소득·나이 등 입력값**이다. 테마 선택은 입력값에서 파생되지 않고, 사용자의 재정에 대해 아무것도 말하지 않으며, 기기 밖으로 나가지 않는다. **원칙 4와 충돌하지 않는다.**
- 남는 우려는 "이 사이트에 왔다"는 흔적 하나인데, `screens.md` 3.7절이 적었듯 **계측 식별자가 이미 저장되고 있다.** 테마 키가 새로 만드는 흔적은 없다.
- 그래도 이 제품의 성격상 다음 넷을 못박는다.
  1. **키 하나(`theme`), 값은 `light` · `dark` · `system` 셋뿐이다.** 자유 문자열이 아니므로 입력값이 흘러들 통로가 없다.
  2. **사용자가 토글을 누르기 전에는 아무것도 쓰지 않는다.** 첫 방문자는 이 키를 남기지 않는다. `screens.md` 3.2절의 "명시적 진술" 원칙과 같은 형태다 — **상호작용에서 의사를 추론하지 않는다.**
  3. **`자동`을 고르면 키를 지운다.** 되돌릴 수 없는 저장을 만들지 않는다.
  4. **테마 값을 계측으로 보내지 않는다.** 보낼 이유가 없다. 계측 허용 판정(헌장)이 "측정 욕구와 규칙이 충돌하면 측정을 포기한다"이므로, 판정을 거칠 것도 없이 보내지 않는다.

**깜빡임(FOUC) 규약.** 저장된 테마는 첫 페인트 **이전에** 적용되어야 한다. `<head>`의 인라인 동기 스크립트가 키를 읽어 루트에 `data-theme`을 찍는다. 렌더 후에 JS로 바꾸면 어두운 화면을 기대한 사용자에게 흰 화면이 한 프레임 번쩍인다. **이 스크립트는 그 한 가지만 한다.**

### 5.31 `AccountBenefitStrip` — 계좌별 세제혜택 요약 (이번 개정, 소유자 지시)

`screens.md` 5.14절. **소유자 지시(2026-08-10):** "각 계좌에 권고 금액이 들어가면 계좌별로 얼마나 세제혜택이 있는지도 알려달라. 도넛 차트 밑이나 오른쪽 아래에 반 정도 되는 사이즈로." 이 컴포넌트가 그 답이다 — `AccountDonut`(5.20절) 바로 아래, 우측 정렬로 붙는 보조 위젯.

**새 데이터를 만들지 않는다.** 계약의 `Plan.deterministic_benefit`(연금계좌 세액공제, 현재는 연금저축·IRP 합산으로만 나온다)과 `Plan.non_quantified_effects`(ISA 등 금액으로 못 내는 효과, `NonQuantifiedEffect`)를 도넛 옆으로 끌어올려 보여줄 뿐이다(engine-interface.md 5.6절). 같은 근거가 C-2 캡션(`screens.md` 5.10·5.11절)과 `[4-D]` 표에 이미 있다 — **이 위젯은 그것을 대체하지 않고 요약만 앞으로 끌어온다.**

```
┌─────────────────────────┐
│ 계좌별 세제혜택            │  type-title-s
│ ● 연금저축 ⎫              │  계좌 색 점 + type-body-s
│ ● IRP     ⎬ 합산 세액공제  │  묶음 표시(현재 계약상 항상 합산)
│            1,4XX,XXX원   │  type-num, tabular-nums
│ ● ISA  비과세 한도 적용    │  narrative 상태
│    (세액공제 아님)         │  절세액과 구분됨을 항상 병기
└─────────────────────────┘
```

| 항목 | 명세 |
|---|---|
| 크기 | 최대 폭 = `AccountDonut` 외경의 **50%**(뷰포트별 100 / 120 / 130px). 높이는 내용에 따르되 행을 2~3개로 제한해 도넛 높이의 절반 안팎을 유지한다 |
| 위치 | 데스크톱·태블릿: 도넛 바로 아래, **우측 정렬**(도넛 카드의 오른쪽 아래 구석) — "도넛 밑"과 "오른쪽 아래"를 동시에 만족시키는 자리다(`screens.md` 5.14절에 근거). 모바일: 도넛/범례 리스트 바로 아래 전체 폭이되 행 2~3개의 컴팩트한 블록으로 유지해 "절반 크기"의 인상을 지킨다 |
| 색 | 좌측 점(●)은 계좌 고정 매핑 색(`data-pension`/`data-irp`/`data-isa`). **`brand-tint*`를 쓰지 않는다**(3.6.3절 금지 구역 2 — 이 위젯은 금액에 근접한 자리다) |
| 금액 표기 | `[4-B]`와 항상 같은 상태(정상/최대/잘림/0원, 4.8절)를 따른다. 이 위젯만의 조건 캡션 슬롯을 새로 만들지 않고, 헤더 아래 한 줄 `위 절세액과 같은 조건 — 2026 과세연도 기준`으로 짧게 참조한다 — `[4-B]`가 같은 화면 위쪽에 전체 캡션을 이미 갖고 있으므로 전문을 다시 적지 않는다. **이 참조 한 줄이 P1(금액은 조건 캡션 없이 존재할 수 없다)을 이 위젯의 좁은 폭에서 지키는 방법이다** |
| 근거(P2) | 이 위젯 자체에는 `LawChip`을 두지 않는다 — 폭이 좁아 축소하면 읽을 수 없다. 각 행을 누르면 `[4-D]`의 해당 계좌 행(법령 조항 포함)으로 스크롤 + 하이라이트한다. **근거가 없는 것이 아니라 한 단계 아래에 있다** |
| 대화형 상태 | 기본 / 호버(행 배경 `surface-sunken`) / 포커스(행 tabbable, `focus-ring`) / 비활성 해당 없음 / 오류(아래 "화면 레벨 상태" 참조 — 위젯 전체를 그리지 않는다) |

**행 상태 다섯.** 계좌마다 다섯 중 하나다.

| 상태 | 언제 | 표시 |
|---|---|---|
| `pooled` | 이 계좌의 세액공제가 다른 계좌와 합산 계산된다(현재 계약상 연금저축·IRP가 **항상** 이 상태다 — `DeterministicBenefit`이 계좌별 필드를 갖지 않는다) | 계좌명 + 묶음 표시(`⎫⎬` 또는 텍스트 `합산`) + 묶인 계좌들 아래 공유 금액 한 줄 |
| `amount` | 이 계좌 단독의 세액공제 금액을 계약이 낸다(**현재는 어느 계좌도 이 상태가 아니다** — 계약이 나중에 계좌별 분리 값을 제공하면 그 계좌만 이 상태로 승격한다) | 계좌명 + 금액(우측 정렬, `tabular-nums`) |
| `narrative` | 금액으로 낼 수 없는 효과(`NonQuantifiedEffect.quantifiable: false`, 현재 ISA가 이 상태) | 계좌명 + 짧은 서술(`비과세 한도 적용`) + `(세액공제 아님)` 괄호 — **절세액과 구분됨을 항상 병기한다.** 이 괄호를 빼면 사용자가 이 서술도 금액이라고 오독한다 |
| `excluded` | `AccountEligibility.eligible: false`(screens.md 5.9절) | 계좌명 + `배분 대상 아님`. 점 색은 `data-excluded` 윤곽만(채움 없음), `AllocationBar`의 배제 표시와 같은 규약 |
| `zero` | 배분액이 0(자격은 있으나 이번 배분에서 배분되지 않음) | 계좌명 + `이 배분에서는 배분하지 않음` |

**낼 세금 상태와 동기화한다(`[4-B]`, `screens.md` 4.8절).**

- **모름:** `pooled`/`amount` 금액 앞에 `최대`를 붙인다.
- **잘림:** 금액 아래에 축약 문구 `일부는 낼 세금 한도로 반영되지 않음`을 작게 붙인다(전문은 `[4-B]`·`[4-D]`에 있다).
- **0:** `pooled`·`amount` 행이 전부 `0원`이 되고, 그 아래 한 줄 `세액공제액으로는 계좌 간 차이가 없음`을 붙인다 — `[4-B]`·C-3와 같은 문구 계열이다(4.8절 (3)).

**이 위젯이 대체하지 않는 것.** C-2 캡션(`screens.md` 5.10·5.11절)과 `[4-D]` 표의 같은 근거는 **그대로 남는다.** 이 위젯은 요약이고, 법령 조항 전문과 상세 서술은 여전히 아래에 있다 — 이 위젯 하나로 P2(근거 노출)를 때우지 않는다.

**화면 레벨 상태.**

| 결과 패널 상태 | 이 위젯 |
|---|---|
| 입력 부족 · 빈 · 로딩(초기) | 그리지 않는다. `AccountDonut` 대신 `ResultPlaceholder`가 있는 자리이므로 이 위젯도 함께 없다 |
| 재계산 중 | `AmountCard`·도넛과 함께 투명도 92%로 낮아진다(직전 값 유지, 6.1절 4번과 동일 규약) |
| 정상 · 모름 | 위 표대로 렌더 |
| 배분 대상 계좌가 0개(전면 차단) | 그리지 않는다 — 결과 패널 전체가 `screens.md` 8.4(b) 오류 상태로 전환된다 |

**forward-compat 메모.** `pooled` 상태는 현재 계약(`DeterministicBenefit`이 연금저축·IRP의 세액공제를 합산으로만 낸다)의 반영이다. `calc-engine-dev`·`tax-domain`이 계좌별 분리 값을 나중에 제공하면 그 계좌의 행만 `amount`로 승격하면 되고, 위젯의 자리·크기·나머지 행의 규약은 바뀌지 않는다.

## 6. 상호작용 규약

### 6.1 결과 갱신 시점 (확정 사항)

1. **필수 항목이 모두 유효해지기 전에는 계산하지 않는다.** 그전까지 결과 패널은 입력 부족 상태다.
2. 모두 유효해진 뒤부터는 값 변경 시 자동 재계산하되 **디바운스 400ms**를 둔다. 타이핑 도중 매 글자 갱신하지 않는다.
3. 금액 필드는 **디바운스 + blur 우선**: 필드에서 포커스가 빠지면 디바운스를 기다리지 않고 즉시 계산한다.
4. 재계산 중에도 **직전 결과를 화면에 남긴다.** 화면을 비우고 스켈레톤으로 되돌리면 값이 깜빡여 읽을 수 없다. 대신 결과 영역 우상단에 `갱신 중` 인디케이터를 띄우고 영역 투명도를 92%로 낮춘다.
5. 새 결과가 들어오면 변경된 금액에 220ms 배경 하이라이트. 숫자 롤링 애니메이션은 쓰지 않는다 — 중간값이 실제 값으로 오인된다.

### 6.2 모션

| 용도 | 시간 / 이징 |
|---|---|
| 상태 전환(색·투명도) | 120ms `ease-out` |
| 펼침/접힘 | 180ms `ease-out` |
| 막대·차트 값 변화 | 240ms `ease-out`. **길이만 변한다. 회전·확대 없음** |
| 모달/시트 | 200ms `ease-out` |
| **테마 전환** | **0ms.** 아래 참조 |
| 자리표시자 → 결과 | 120ms 소멸 + 240ms 각도 전개 (5.29절) |

`prefers-reduced-motion: reduce`이면 전부 0ms로 처리하고 즉시 전환한다.

**테마 전환에는 트랜지션을 걸지 않는다.** 색 토큰이 한꺼번에 바뀌는데 120ms 색 전환이 페이지 전체에 걸려 있으면 수십 개 요소가 제각기 물들어 화면이 출렁이고, 그 중간 프레임에서는 글자와 배경의 대비가 4.5:1 아래로 내려간다. **고지 문구가 한순간이라도 읽히지 않는 프레임을 만들 수 없다.**

### 6.3 포커스

- 포커스 링은 어떤 경우에도 제거하지 않는다. 2px `focus-ring` + 2px offset.
- 탭 순서: 헤더 → 입력 패널(위→아래) → 결과 패널(위→아래) → 푸터. 결과가 시각적으로 오른쪽에 있어도 DOM 순서가 곧 읽기 순서다.
- 결과가 처음 생성되는 순간 포커스를 옮기지 않는다. 대신 `aria-live="polite"`로 `계산 결과가 표시되었습니다`를 알린다.

### 6.4 접근성 기준선

- 텍스트 대비 4.5:1(큰 텍스트 3:1). **고지 문구도 예외 없이 4.5:1.** 두 테마 모두에서 실측한 표가 8.4절에 있다.
- **데이터 색은 3.5절의 여섯 검사로 판정한다.** 표면 대비 3:1 이상 + 각 조각에 직접 라벨. **"인접 조각 간 3:1"이라던 초판 규정은 폐기한다** — WCAG 대비비는 명도만 보는 척도라 색상이 다르고 명도가 같은 두 조각을 통과시킨다. 조각 간 분리는 OKLab ΔE로 재고, 그 판정은 검증기가 한다.
- 색맹 시뮬레이션은 **Machado–Oliveira–Fernandes 2009 severity 1.0**으로 고정한다(검증기가 쓰는 모델). 적록(protan/deutan)은 게이트, 청색각(tritan)은 보고 항목이다. 시뮬레이션 모델을 바꾸면 임계값도 다시 잡아야 하므로 모델이 기준의 일부다.
- 흑백 인쇄에서도 조각이 구분될 것. 계좌 셋의 OKLCH 명도차는 라이트 0.040 / 0.060 / 0.100, 다크 0.029 / 0.055 / 0.084로 **완전히 안전하지는 않다.** 그래서 흑백 경로에서는 직접 라벨과 `[4-D]` 표가 유일한 식별 수단이 되며, 둘 중 하나라도 빠지면 흑백에서 차트를 읽을 수 없다.
- **`forced-colors`(고대비 모드)에서는 조각 색이 시스템 색으로 대체되어 계좌 구분이 사라진다.** 이때도 직접 라벨과 조각 사이 2px 간격은 남아야 한다. 색에 기대는 설계를 하지 않았다는 것이 여기서 시험된다.
- 모든 차트에 텍스트 대체 경로: 차트 바로 아래 `계좌별 상세 리스트`가 같은 정보를 표 형태로 담는다. **차트는 리스트의 시각화이지 유일한 정보원이 아니다.**
- 200% 확대에서 가로 스크롤 없이 동작.

### 6.5 금액 표시 규약 (P1의 실행)

- 화면에서 가장 큰 금액은 하나뿐이다(`type-display`). 그 금액은 반드시 `AmountCard` 안에 있다.
- 금액 옆·아래 24px 이내에 산정 조건 캡션이 있어야 한다. 다른 카드로 밀거나, 스크롤해야 보이거나, 접혀 있으면 위반이다.
- 헤드라인 금액에 `약`·`예상` 같은 완화어를 붙이되, 완화어가 조건 캡션을 대신하지 못한다. 둘 다 필요하다.

## 7. 문구 규약

### 7.1 어휘

헌장의 목록을 그대로 따른다. 화면에 등장할 수 있는 어휘로 한정하면 다음과 같다.

- **쓴다:** 계산 · 계산 결과 · 모의 계산 · 시뮬레이션 · 비교 · 납입 배분 · 배분 계산 · 세액공제액 · 예상 세액공제액 · 한도 · **납입 잔여 한도** · 비과세 한도 · 참고 정보 · 법령 조항 인용
- **"잔여 한도"를 수식어 없이 쓰지 않는다.** 이 제품에는 성격이 다른 한도가 둘 있다 — 넘을 수 없는 **납입 잔여 한도**와, 넘을 수 있는 **세액공제 인정 여지**다. 수식어 없는 "잔여 한도"는 둘을 뭉개고, 후자에 붙으면 사실과 어긋난다(`screens.md` 5.10절).
- **조건부로 쓴다:** `절세액`(계산 결과를 가리킬 때만) · `환급세액` · `납입 배분 최적화`(대상 명시) · `추천`(선택지 비교 맥락에서만)
- **`최대`는 상한 변형에서만 쓴다**(5.6절). 금액 앞에 붙는 유일한 완화어이고, **완화어가 조건 캡션을 대신하지 못한다**(6.5절). `약`·`예상`과 섞어 쓰지 않는다 — 셋을 다 붙이면 금액이 무엇인지 알 수 없게 된다.
- **세법 항목명은 확정된 이름을 그대로 쓴다.** `낼 세금` 같은 구어를 라벨로 쓰지 않는다 — 사용자가 서류에서 찾아야 하는 값이므로 서류에 적힌 이름과 같아야 한다. 확정 전까지 `screens.md`는 `{확정 항목명}` 자리표시자를 쓴다.
- **쓰지 않는다:** 세무/세금 상담 · 자문 · 대리 · 컨설팅 · 진단 · 점검 · 신고 대행 · 환급 신청 · 전문가 검토 · 세무사 관련 일체

**서비스 명칭:** 확정 전까지 `[가칭] 납입배분 계산기`. "세무·택스·절세·컨설팅·환급·상담·자문·대행" 계열을 쓰지 않는다.

### 7.2 금지 문장 패턴 (P3)

| 금지 | 대체 |
|---|---|
| "당신은 IRP에 ○○원을 넣으세요" | "IRP 납입 잔여 한도까지 채우는 배분: 월 ○○원" |
| "이 배분을 추천합니다" | "세액공제액이 가장 큰 배분(계산 결과)" |
| "○○하는 것이 유리합니다" | "○○일 때 세액공제액이 {금액} 더 큽니다" |
| "지금 가입하세요" | (버튼·CTA 자체를 두지 않는다. 이 제품은 가입을 연결하지 않는다) |
| "평균 ○○만원 절세" | (금지. 산정 조건 없는 금액 표시) |

| "고객님은 청년에 해당합니다" | "정부가 발표한 개정안 기준으로는 … 연령에 들어갑니다. 다만 아직 시행령으로 정해지지 않았습니다" |
| "원천징수영수증을 준비해 주세요" | "지금 확인할 수 없다면 — '모르겠습니다'를 고르면 계산은 그대로 나옵니다" |
| "더 정확한 결과를 보려면 입력하세요" | (재촉하지 않는다. 금액이 왜 상한인지 말한 문장 옆에 되돌아갈 링크만 둔다) |
| "이 값을 넣으면 더 정확한 진단이 가능합니다" | (`진단`은 쓰지 않는다) |
| "연금계좌에 넣어도 소용이 없습니다" | (근거 없는 단정. 세액공제 외의 효과를 부정할 근거가 우리에게 없다) |

**동사의 주어를 사용자에게 두지 않는다.** 결과 문장의 주어는 항상 계산 대상(배분·한도·세액공제액)이다.

**"모름"을 다룰 때의 두 규약** (`screens.md` 4.8절·8.6절).

- **모름은 결과를 막지 않는다.** 결과를 안 보여주는 것은 답이 아니다.
- **모름은 추정으로 메우지 않는다.** 대신 **틀릴 방향과 그 경계값**을 적는다. `달라질 수 있습니다`로 끝내면 사용자는 무엇을 확인해야 할지 모른다.

### 7.3 오류 메시지

- 무엇이 잘못됐는지 + 무엇을 하면 되는지, 두 조각으로만 쓴다.
- 사용자를 탓하지 않는다("잘못 입력했습니다" ✗ / "0 이상의 값이 필요합니다" ○).
- 계산 불가 사유는 법령 조건에서 나온 것이면 해당 `LawChip`을 함께 붙인다. 서비스가 임의로 막는 것이 아님을 보인다.

## 8. 다크 테마

소유자 지시로 이번에 확정했다(2026-08-10). 초판은 두 테마의 토큰만 정의하고 "3단계 범위인지 미정"으로 열어 두었는데, 그때 정하지 않은 것이 셋 있었다 — **상태 모형 · 토큰 선언 순서 · 다크 데이터 색의 재검증**이다. 이 절이 그 셋을 닫는다.

### 8.1 세 가지 상태

| 상태 | 언제 | 루트 표시 | 무엇이 결정하는가 |
|---|---|---|---|
| **지정 없음 (기본)** | 사용자가 `ThemeControl`을 건드리지 않았다 | 없음 | `prefers-color-scheme` **만** |
| **명시적 라이트** | `밝게`를 골랐다 | `data-theme="light"` | 운영체제가 다크여도 라이트 |
| **명시적 다크** | `어둡게`를 골랐다 | `data-theme="dark"` | 운영체제가 라이트여도 다크 |

**"지정 없음"이 기본이고, 그 상태에서 루트에는 아무 표시도 없다.** 이것이 이 절의 모든 규칙이 걸리는 자리다.

### 8.2 토큰 선언 순서 (구현 계약)

**색을 미디어 쿼리 안에서만 정의하면 지정 없는 상태가 깨진다.** 라이트 값을 `@media (prefers-color-scheme: light)` 안에 넣고 다크 값을 `dark` 안에 넣으면, 두 조건 중 어느 것도 참이 아닌 실행 환경에서 토큰이 비어 글자와 배경이 같은 색이 된다. 그래서 순서가 계약이다.

```css
/* 1) 맨바닥 :root — 라이트 팔레트 전체를 여기서 정의한다.
      미디어 쿼리 안이 아니다. 이것이 어떤 조건도 참이 아닐 때의 값이다. */
:root {
  color-scheme: light;
  --surface-base: #F7F8FA;   --surface-raised: #FFFFFF;   /* … 전 토큰 … */
  --data-pension: #0A9A96;   --data-irp: #DA7134;         --data-isa: #8758C1;
  --data-unallocated: #5A6166; --data-excluded: #888F95;
  --data-placeholder: #C0C8CE; --data-track: #E1E5EA;
}

/* 2) 운영체제가 다크이고, 사용자가 라이트를 명시하지 않았을 때.
      :where() 안에 넣어 이 선택자의 명시도를 :root(0,1,0)로 낮춘다 —
      그래야 3)의 [data-theme="dark"](0,2,0)가 순서와 무관하게 이긴다.
      :not(...) 가 없으면 명시적 라이트가 OS 다크에 진다. */
@media (prefers-color-scheme: dark) {
  :root:where(:not([data-theme="light"])) {
    color-scheme: dark;
    --surface-base: #14171A;   --surface-raised: #1E2226;  /* … 바뀌는 토큰만 … */
    --data-pension: #06A19D;   --data-irp: #DF7333;        --data-isa: #8F5FCC;
    --data-unallocated: #B1B8BF; --data-excluded: #6A7076;
    --data-placeholder: #41474C; --data-track: #2C3238;
  }
}

/* 3) 사용자가 어둡게를 명시했을 때. 미디어 쿼리 밖이라 OS 설정과 무관하게 이긴다.
      2)와 값이 같다. 두 곳에 같은 값을 적는 것이 이 계약의 비용이다. */
:root[data-theme="dark"] {
  color-scheme: dark;
  /* 2)와 동일한 선언 */
}
```

규칙 넷.

1. **모든 색은 맨바닥 `:root`에 값을 하나씩 갖는다.** 미디어 쿼리나 `[data-theme]` 안에만 존재하는 색은 없다. 이 규칙 하나가 "지정 없음"에서 글자가 반대쪽 배경에 얹히는 사고를 구조적으로 막는다.
2. **다크 블록은 바뀌는 토큰만 다시 선언한다.** 간격·반경·타이포 토큰은 다시 적지 않는다 — 두 벌이 되면 어긋난다.
3. **`color-scheme`을 함께 바꾼다.** 스크롤바·기본 폼 컨트롤·`::selection`이 이 값을 따른다. 빠뜨리면 다크 화면에 밝은 스크롤바가 남는다.
4. **미디어 블록의 선택자는 `:root:where(:not([data-theme="light"]))` 형태를 그대로 쓴다.** 두 부분이 각각 일한다 — `:not(...)`이 없으면 **명시적 라이트가 OS 다크를 못 이기고**, `:where()`가 없으면 2)와 3)의 명시도가 (0,2,0)로 같아져 승부가 **선언 순서에 걸린다**(지금은 3)이 뒤라 우연히 맞지만, 누가 블록을 옮기면 조용히 깨진다). `:where()`가 2)를 (0,1,0)으로 낮추면 3)이 순서와 무관하게 이긴다.

**네 조합을 다 확인한 결과.** OS 라이트 + 지정 없음 → 라이트 · OS 다크 + 지정 없음 → 다크 · OS 다크 + `밝게` → 라이트 · OS 라이트 + `어둡게` → 다크. **`qa`는 이 넷을 다 본다** — 셋만 보면 대개 세 번째가 빠지고, 그것이 이 계약이 실제로 깨지는 조합이다.

### 8.3 다크는 라이트의 반전이 아니다

- **데이터 색은 다크 표면(`#1E2226`)에 대해 따로 뽑아 따로 검증했다.** 3.5.4절에 다크 전용 검증기 출력이 있다. **라이트에서 통과한 색이 다크에서 통과한다는 보장이 없다** — 실제로 초판 다크 값은 셋 다 명도 대역 밖이었고 연금저축↔ISA가 적록색각이상 ΔE 5.8로 붕괴해 있었다. 라이트 값을 그대로 쓰거나 기계적으로 밝히는 처리로는 잡히지 않는 결함이다.
- **무채색 역할 색은 방향이 반대다.** `data-unallocated`는 라이트에서 짙고(대비 6.29) 다크에서 밝다(7.99). 표면에서 멀어지는 방향이 모드마다 반대이기 때문이다. **유채색인 계좌 색은 이 반전을 하지 않는다** — 두 모드 다 중간 밝기 대역에 있다.
- 그림자는 다크에서 절반으로 줄이고 `border-subtle`이 경계를 대신한다.
- 순수 검정(`#000`)과 순수 흰색 텍스트를 쓰지 않는다 — 명도 대비가 과해 잔상이 생긴다.
- 레이아웃·간격·타이포·모션은 두 테마가 **완전히 같다.** 다크에서만 여백을 늘리는 식의 조정을 하지 않는다.

### 8.4 고지는 다크에서도 읽힌다 (실측)

### 8.5 인쇄 · 공유 이미지 · 고대비

- **인쇄는 항상 라이트 토큰이다.** `@media print`에서 `data-theme`을 무시하고 라이트 팔레트를 강제한다. 어두운 배경은 잉크를 낭비하고 대부분의 프린터 설정에서 배경색이 빠져 글자만 남는데, 그러면 다크용 밝은 글자색이 흰 종이에 얹혀 고지가 읽히지 않는다.
- **공유 이미지도 항상 라이트로 렌더한다**(`screens.md` 9절). 수신자의 환경을 알 수 없고, 이미지에 실린 고지가 반드시 읽혀야 한다. 발신자의 테마가 수신자의 가독성을 정하게 두지 않는다.
- **`forced-colors: active`에서는 계좌 색이 시스템 색으로 대체된다.** 이때 차트의 정체 전달은 직접 라벨과 `[4-D]` 표가 전담한다(6.4절). 조각 사이 2px 간격은 `forced-colors`에서도 유지한다 — 시스템이 모든 조각을 같은 색으로 칠하면 간격만이 조각을 가른다.

## 9. 자산 제약

- **특정 금융사의 로고·브랜드 색·상품 이미지를 쓰지 않는다.** 계좌 아이콘이 필요하면 추상 도형(원·사각·삼각)으로 처리한다.
- 세무사·회계사를 연상시키는 시각 요소를 쓰지 않는다 — 가운·도장·법전·저울·배지·"전문가" 아이콘 일체 금지(`tax-rules-report.md` 2.4절이 오인 위험 요소로 명시한 유형).
- 인물 사진·일러스트를 쓰지 않는다. 사람이 개입한다는 인상을 만들지 않는다.
- 아이콘은 단색 선형 24px 격자 기준. 아이콘 단독으로 의미를 전달하지 않고 항상 텍스트 라벨과 짝을 이룬다.
