# 절세 계좌 최적화 서비스 — 에이전트 조직 설계

- 작성일: 2026-08-07
- 상태: 확정
- 산출물 종류: 조직 설계 스펙

## 1. 목적

ISA·IRP·연금저축 등 절세 계좌에 **얼마를 어떤 비중으로 납입해야 세금을 가장 많이 아끼는지** 계산해 보여주는 웹 서비스를 만들고 운영한다. 사용자는 나이, 소득 수준, 월 납입 여력, 투자 성향 등을 입력한다.

이 문서는 그 제품을 만들 **조직**을 정의한다. 조직은 Claude Code 서브에이전트로 구성되며, 사람은 승인자 한 명이다.

## 2. 범위

**이 문서가 정하는 것**

- 유닛 구성과 각 유닛의 책임
- 단계별 작업 플로우와 사람의 승인 게이트
- 유닛 간 핸드오프 규약과 산출물 경로
- 세무 정확성 보증 장치
- 수익화 결정을 유예하는 구조
- 에이전트 정의 파일의 형식과 권한 원칙
- 예외 처리와 성공 기준

**이 문서가 정하지 않는 것**

- 제품 요구사항과 화면 정의 — 1단계 기획 유닛의 산출물
- 기술 스택 — 2단계 설계에서 결정. 지금 정하면 아직 모르는 요구사항에 스택을 끼워맞추게 된다.
- 구체적인 세법 수치 — 전부 세무 도메인 유닛이 출처와 함께 조사한다. 이 문서는 어떤 수치도 사실로 단정하지 않는다.
- 수익 모델 — 출시 후 8주 실측 뒤 게이트 7에서 결정한다.

## 3. 조직 구성

**관리자는 별도 에이전트가 아니라 메인 세션이다.** 서브에이전트는 다시 서브에이전트를 호출할 수 없으므로, 조율자를 서브에이전트로 두면 팀을 부를 수 없다.

| 유닛 | 에이전트 파일 | 책임 |
|---|---|---|
| 관리자 | (메인 세션) | 단계 진행, 유닛 호출, 핸드오프 검수, 승인 요청, 반려 판정 |
| 기획 | `product-planner` | 요구사항, 유저 플로우, 화면 목록, 수용 기준(AC) |
| 세무 도메인 | `tax-domain` | 연도별 세법 룰셋 작성, 출처 명시, 개정 선행조사, 계산 결과 독립 교차검증 |
| 디자인 | `designer` | 디자인 시스템, 화면 설계, 결과 시각화 스펙 |
| 계산 엔진 | `calc-engine-dev` | 최적 납입 배분 로직(순수 함수) + 단위 테스트 |
| 웹 개발 | `web-dev` | 입력 폼·결과 화면 UI 구현 |
| QA | `qa` | 테스트 전략, E2E, 경계값·회귀 테스트, 코드 리뷰 |
| 그로스 | `growth` | 홍보 채널 조사, 랜딩 카피, SEO 구조, 분석 계측 설계, 홍보 플레이북 |
| 사업 | `biz-model` | 수익 모델 후보 비교, 수요 검증 계획, 단위경제·손익 모델, 중립성 경계선 설계, 수익 지표 정의 |

### 3.1 구성 근거

**개발을 계산 엔진과 웹으로 분리한 이유.** 계산 엔진은 UI 없이 입력→출력만 있는 순수 로직이라 테스트가 촘촘히 가능하고 세무 유닛이 검증하기 쉽다. 웹은 브라우저·상태·레이아웃 관심사다. 한 유닛에 묶으면 "UI가 도니까 계산도 맞겠지"라는 착각이 생긴다. 분리하면 두 유닛이 서로의 가정을 검사하게 되고, 각 유닛이 다뤄야 할 코드량도 작아진다.

**세무 도메인을 기획에서 분리한 이유.** 명세를 쓴 주체가 명세를 검증하면 세법 오류가 그대로 통과한다. QA는 코드가 명세대로 도는지 검증하지만, 명세 자체가 세법과 맞는지는 검증하지 못한다.

**QA가 코드 리뷰를 맡는 이유.** 개발 유닛이 자기 코드를 리뷰하면 자기 가정을 재확인할 뿐이다.

**사업을 그로스에서 분리한 이유.** 이 제품의 자연스러운 수익 모델(금융사 제휴)은 제품의 중립성 원칙과 정면으로 충돌한다. 그로스 유닛에 맡기면 성과 지표가 유입과 전환이므로 반드시 수익 쪽으로 기운다. 중립성을 지켜야 할 세무·기획 유닛과 견제가 성립하려면 수익화 판단이 별도 보고라인에 있어야 한다.

**운영 전담 유닛을 두지 않는 이유.** 브라우저 안에서 계산하는 구조라 서버 운영 부담이 거의 없다. 운영에 필요한 것은 새 유닛이 아니라 기존 유닛을 정기적으로 재소집하는 사이클(6단계)이다. 유닛을 늘리면 할 일 없는 에이전트가 회의만 만든다.

**마케팅 유닛의 범위 축소.** 광고 계정·결제수단·SNS 로그인이 필요한 실제 집행은 에이전트가 할 수 없다. 그로스 유닛은 조사·기획·문안 작성까지 담당하고, 집행은 사람이 한다.

## 4. 작업 플로우

6단계 파이프라인. 각 단계 끝에 사람의 승인 게이트가 있고, 단계 안에서는 유닛이 자율로 움직인다.

### 1단계 — 발견 (4개 유닛 동시 실행)

- **기획**: 타깃 사용자, 입력 항목, 유저 플로우, 화면 목록, 수용 기준
- **세무 도메인**: 현행 세법 룰셋 조사 + 개정 선행조사(기재부 세제개편안, 국회 계류안, 시행 예정일)
- **그로스**: 홍보 채널 조사 — 이런 서비스의 사용자가 어디에 있는지, 채널별 진입 난이도·비용·규제
- **사업**: 수익 모델 후보 비교와 **수요 검증 계획** (7절 참조)

→ **게이트 1**: 요구사항 · 룰셋 · 채널 리포트 · **수요 판정 기준** 승인

### 2단계 — 설계 (3개 유닛 동시 실행)

- **디자인**: 디자인 시스템, 화면 설계, 결과 시각화 스펙
- **계산 엔진**: 최적화 알고리즘 설계 + **엔진 인터페이스(입출력 타입) 확정**
- **그로스**: 분석 계측 설계 — 어떤 이벤트를 어느 시점에 남길 것인가

계측 설계가 여기 있는 이유는 7.3절에 있다. 무엇을 측정할지는 설계 결정이고, 화면이 다 만들어진 뒤에 이벤트를 심으려면 화면을 다시 뜯어야 한다.

→ **게이트 2**: 설계 승인. 인터페이스가 여기서 고정되므로 3단계가 병렬 가능해진다.

### 3단계 — 구현 (2개 유닛 동시 실행)

- **계산 엔진**: TDD로 로직 구현
- **웹 개발**: 확정된 인터페이스에 목(mock)을 물려 UI 선구현 → 엔진 완성 시 교체. 2단계에서 확정된 계측 이벤트를 화면을 만들면서 함께 심는다.

→ **게이트 3**: 동작하는 프로토타입 승인

### 4단계 — 검증 (순차)

- **세무 도메인**: 골든 케이스로 독립 교차검증. 불일치 시 반려하고 3단계로 되돌림.
- **QA**: E2E, 경계값·회귀 테스트, 코드 리뷰, 계측이 설계대로 구현되었고 개인 식별 값을 싣지 않는지 확인

→ **게이트 4**: 정확성·품질 승인

### 5단계 — 출시 준비

- **그로스**: 랜딩 카피, SEO 구조, 홍보 플레이북(사람이 직접 집행할 체크리스트)
- **사업**: 2단계에서 설계하고 3단계에서 심은 계측이 실제로 판정 지표를 만들어내는지 확인

→ **게이트 5**: 출시 승인

### 6단계 — 운영

출시는 끝이 아니라 루프의 시작이다. 정기 사이클로 기존 유닛을 재소집한다.

- **월간** — 그로스(채널·콘텐츠 성과), 사업(수익·수요 지표 대 목표, 가설 수정)
- **분기** — QA(회귀 전건 + 이슈 트리아지), 개발 유닛(백로그 처리)
- **세제 개편 사이클** — 개편안 발표(여름) / 국회 통과(연말) / 시행(1월)에 맞춰 세무 도메인 긴급 소집 → 룰셋 갱신 → 골든 케이스 재산출 → 교차검증 → 배포. **시행일 이전 반영이 강제 조건이다.** 시행일 이후에 이전 연도 세법으로 답을 주는 계산기는 틀린 계산기다.

→ **게이트 6**: 사이클마다 운영 리포트
→ **게이트 7**: 출시 후 8주 시점, BM 결정 게이트 (7절 참조)

## 5. 산출물과 핸드오프 규약

유닛끼리는 **오직 파일로만** 소통한다. 서브에이전트는 작업이 끝나면 컨텍스트가 사라지므로, 파일로 남기지 않은 판단은 존재하지 않는 것과 같다. 부수효과로 사람이 어느 단계든 열어볼 수 있다.

### 5.1 디렉터리 구조

```
docs/
  org/charter.md              조직 헌장 · 유닛별 R&R · 핸드오프 규약
  superpowers/specs/          설계 스펙(이 문서)
  stage-1-discovery/          requirements.md · tax-rules-report.md ·
                              channel-research.md · demand-validation-plan.md
  stage-2-design/             design-system.md · screens.md ·
                              engine-design.md · engine-interface.md ·
                              analytics-plan.md
  stage-4-verification/       golden-cases.md · verification-report.md · qa-report.md
  stage-5-launch/             landing-copy.md · seo-plan.md · promo-playbook.md
  stage-6-operations/         <YYYY-MM>-growth.md · <YYYY-MM>-biz.md ·
                              bm-decision-report.md
data/tax-rules/               2026.json … · 2027-proposed.json · sources.md
src/engine/
src/web/
.claude/agents/               product-planner.md · tax-domain.md · designer.md ·
                              calc-engine-dev.md · web-dev.md · qa.md ·
                              growth.md · biz-model.md
```

### 5.2 산출물 머리말

모든 산출물 문서는 동일한 머리말을 단다.

```yaml
unit: tax-domain
stage: 1
status: draft | approved
inputs: [docs/stage-1-discovery/requirements.md]
open_questions:
  - 공제율이 바뀌는 총급여 경계에서의 적용 기준 확인 필요
```

`open_questions`가 비어 있는 산출물은 관리자가 한 번 의심한다. 세법처럼 모호한 영역을 다루면서 질문이 하나도 없다는 것은, 대개 조사를 안 한 것이지 다 안 것이 아니다.

### 5.3 규칙

1. **쓰기 범위 제한** — 유닛은 자기 단계의 디렉터리와 자기 소스 경로에만 쓴다. 계산 엔진 유닛은 `src/web/`을 건드리지 않는다.
2. **읽기는 자유** — 이전 단계 산출물은 모두 읽는다. 단 4단계 교차검증 시 세무 유닛만 `src/engine/` 읽기 금지.
3. **남의 산출물은 고치지 않는다** — 기획서가 틀렸다고 판단해도 직접 수정하지 않고 `open_questions`에 올린다. 관리자가 게이트에서 판정한다. 유닛이 서로의 문서를 고치기 시작하면 누가 무엇을 결정했는지 추적이 불가능해진다.
4. **승인은 관리자만** — 게이트 통과 시 관리자가 `status`를 `approved`로 바꾼다. 반려 시 사유를 적은 파일을 만들어 해당 유닛을 재호출한다.

## 6. 세무 정확성 보증

이 제품의 유일한 치명적 실패는 숫자가 틀리는 것이다. 여기에만 3중 장치를 둔다.

### 6.1 룰셋은 데이터, 계산은 코드

세법 규칙은 `data/tax-rules/<연도>.json`에 선언형으로 들어가고, **엔진 코드에는 세법 숫자가 단 하나도 하드코딩되지 않는다.**

```json
{
  "id": "pension.credit.limit.combined",
  "title": "연금계좌 세액공제 납입한도(연금저축+IRP 합산)",
  "conditions": [],
  "value": {},
  "status": "확정",
  "effective_from": "2026-01-01",
  "source": {
    "law": "소득세법 해당 조항",
    "url": "",
    "verified_on": "2026-08-07",
    "verified_by": "tax-domain"
  }
}
```

**`source`가 없는 규칙은 QA가 자동으로 실패시킨다.** 세법 조항 없이 들어온 숫자는 근거 없는 숫자다.

위 예시는 필드 구조를 보이기 위한 골격이며, `conditions`와 `value`의 실제 스키마와 모든 수치는 세무 도메인 유닛이 1단계에서 법령 출처와 함께 확정한다.

### 6.2 개정 선행조사

개정 예정 규칙은 별도 파일(`2027-proposed.json`)에 `status: "개정예고"`와 `bill_stage`(정부안 / 국회 계류 / 공포)를 달아 보관한다. 확정 규칙과 절대 섞지 않는다. 이 분리 덕분에 사이트가 "현행 기준 vs 개정안 반영 시" 비교를 보여줄 수 있다.

이 조사는 세제개편안 발표(여름) · 국회 통과(연말) · 시행(1월) 주기에 맞춘 세무 유닛의 상시 업무다.

### 6.3 골든 케이스 독립 산출

세무 유닛이 **엔진 코드를 보지 않고** 프로필별 정답과 도출 과정(어느 규칙을 어떤 순서로 적용했는지)을 직접 쓴다. 코드를 보면 코드의 논리에 끌려가 같은 실수를 반복한다. 세법 원문에서 독립적으로 답을 내고 숫자만 대조해야 오류가 걸린다.

경계값은 필수로 포함한다 — 공제율이 바뀌는 총급여 경계, 납입한도 초과, 연령 기준선, ISA 만기, 중도해지. 오류는 대부분 경계에서 나온다.

### 6.4 대조와 에스컬레이션

엔진 결과와 골든 케이스가 불일치하면 세무 유닛이 근거와 계산 과정을 제출하고, 관리자가 엔진을 고칠지 룰셋을 고칠지 판정한다. **같은 케이스에서 3회 반복 불일치하면 게이트 4에서 사람에게 올린다.** 그 시점이면 세법 해석 자체가 갈리는 사안일 가능성이 높고, 그것은 사람이 판단할 일이다.

### 6.5 법적 경계선

- 결과 화면에 "세법 계산 예시이며 투자·세무 자문이 아님" 고지를 넣는다.
- 특정 금융상품·금융사를 추천하지 않는다.
- 개인 소득 정보는 서버에 저장하지 않고 브라우저 안에서만 계산한다.

이 원칙은 기획과 세무 유닛의 공동 책임이며, QA가 검사 항목으로 강제한다.

## 7. 수익화 결정 유예 구조

수익 모델은 출시 시점에 정하지 않는다. 출시 후 8주간 실제 사용 데이터를 보고 게이트 7에서 결정한다. 다만 **"미룬다"는 것 자체를 설계에 넣어야** 8주 뒤에 판단할 재료가 남는다.

### 7.1 판정 기준을 먼저 정한다

사업 유닛의 1단계 산출물은 BM 확정이 아니라 `demand-validation-plan.md`다. 게이트 1에서 승인하는 것은 수익 모델이 아니라 **판정 기준**이다.

순서가 중요하다. 데이터를 본 뒤에 기준을 정하면 어떤 숫자가 나와도 "가능성은 있다"로 읽힌다. 8주 뒤 무엇을 보면 계속하고 무엇을 보면 접을지를 미리 숫자로 적는다.

### 7.2 트래픽은 수요가 아니다

방문자 수는 홍보를 얼마나 했는지를 알려줄 뿐이다. 실제로 볼 지표는 다음과 같고, 각각의 목표치를 사업 유닛이 제안하고 게이트 1에서 확정한다.

- 계산을 끝까지 완료한 비율
- 재방문율
- 결과를 저장·공유한 비율
- 지불 의사 신호 (알림 신청 등 명시적 행동)

### 7.3 계측은 설계 단계에 속한다

그로스의 `analytics-plan.md`는 **2단계 설계 산출물**이고 게이트 2에서 승인된다. 계측 없이 출시하면 8주 뒤에 데이터가 없다.

계측을 출시 준비 단계에 두지 않는 이유가 있다. 무엇을 측정할지는 설계 결정이다. 화면이 다 만들어진 뒤에 이벤트를 심으려면 화면을 다시 뜯어야 하고, 그 시점의 압박("일단 출시하고 나중에 붙이자") 아래서 가장 먼저 잘려 나가는 것이 계측이다. 2단계에서 정하면 web-dev가 3단계에서 화면을 만들며 함께 심고, QA가 게이트 4에서 설계와 구현을 대조할 수 있다.

QA의 게이트 4 검사 항목에는 계측이 설계대로 구현되었는지, 그리고 어떤 이벤트도 개인 식별 가능 값을 싣지 않는지가 포함된다.

단, **소득·나이 등 입력값은 절대 분석 도구로 나가지 않는다.** 익명 집계 이벤트만 보낸다. 개인정보 미저장 원칙이 계측보다 우선한다.

### 7.4 출시 버전의 방침

- 출시 버전은 **수익화·광고 없음**으로 확정한다. 되돌릴 수 있는 결정이기 때문이다.
- 고지 문구는 "광고 없는 서비스입니다" 같은 영구 약속이 아니라 **"현재 제휴·광고 없음"**처럼 현재 사실만 적는다. 신뢰는 되돌릴 수 없어서, 중립을 약속한 뒤 제휴를 붙이면 배신으로 읽힌다. 지금 정하지 않은 것을 약속하지 않는 것이 나중의 선택지를 지킨다.

### 7.5 게이트 7 — BM 결정

출시 후 8주 시점에 사업 유닛이 사전 기준 대비 실측을 대조한 `bm-decision-report.md`를 낸다. 사람이 셋 중 하나를 선택한다.

1. 수익화 진행 (모델 확정)
2. 기준 미달 — 피벗 또는 중단
3. 검증 기간 연장 (연장 사유와 새 종료 시점을 명시)

금융사 제휴 여부는 이 시점에 실제 데이터를 놓고 판단한다.

## 8. 에이전트 정의 스펙

각 유닛은 `.claude/agents/<name>.md` 파일 하나이고, 동일한 골격을 쓴다.

```markdown
---
name: tax-domain
description: 언제 이 유닛을 호출하는지
tools: Read, Write, Edit, Glob, Grep, WebSearch, WebFetch
model: opus
---
## 역할        한 문단
## 입력        읽어야 할 문서 경로 목록
## 산출물      써야 할 파일 경로와 형식
## 금지사항    쓰면 안 되는 경로, 하면 안 되는 판단
## 완료 기준   무엇이 충족되면 끝인가
```

### 8.1 권한 원칙

도구 권한은 역할에 맞춰 좁힌다.

| 유닛 | 도구 | 비고 |
|---|---|---|
| `product-planner` | Read, Write, Edit, Glob, Grep, WebSearch, WebFetch | 조사가 본업, Bash 불필요 |
| `tax-domain` | Read, Write, Edit, Glob, Grep, WebSearch, WebFetch | 법령 조회 필수. 4단계에서 `src/engine/` 읽기 금지 |
| `designer` | Read, Write, Edit, Glob, Grep, WebFetch | |
| `calc-engine-dev` | Read, Write, Edit, Glob, Grep, Bash | 쓰기 범위 `src/engine/` |
| `web-dev` | Read, Write, Edit, Glob, Grep, Bash | 쓰기 범위 `src/web/` |
| `qa` | Read, Glob, Grep, Bash, Write | **쓰기는 리포트 경로만** |
| `growth` | Read, Write, Edit, Glob, Grep, WebSearch, WebFetch | |
| `biz-model` | Read, Write, Edit, Glob, Grep, WebSearch, WebFetch | |

**QA의 쓰기를 리포트로 제한하는 이유.** QA가 코드를 직접 고치기 시작하면 "테스트를 통과시키려고 테스트를 고치는" 일이 생긴다. 발견은 QA가, 수정은 개발 유닛이 한다.

### 8.2 모델 배정

세무 도메인과 계산 엔진에 가장 높은 등급을 쓴다. 이 둘이 틀리면 제품이 무의미해지고, 나머지는 틀려도 복구 가능하다.

## 9. 예외 처리

- **규약 위반** — 머리말 누락, `source` 없는 규칙, 허용 범위 밖 파일 수정. 관리자가 게이트 이전에 즉시 반려하고 재호출한다. 사람에게 올라가지 않는다.
- **게이트 반려** — 사람이 반려하면 관리자가 사유 파일을 만들어 **해당 유닛만** 재호출한다. 단계 전체를 다시 돌리지 않는다.
- **병렬 중 일부 실패** — 성공한 유닛의 산출물은 그대로 두고 실패분만 재실행한다. 파일 기반 핸드오프라 가능하다.
- **골든 케이스 3회 반복 불일치** — 게이트 4에서 사람에게 에스컬레이션 (6.4절).

## 10. 성공 기준

출시는 마일스톤이지 성공이 아니다. 조직의 성공은 출시 후 운영으로 판정한다.

1. **세법 개정이 시행일 이전에 반영됨** — 미달 시 즉시 실패로 간주한다.
2. 정기 회귀 테스트와 골든 케이스 전건 통과가 유지됨
3. 월 수익이 운영비를 넘고, 사업 유닛이 세운 궤도 위에 있음 (게이트 7에서 수익화를 진행한 경우)
4. 중립성 원칙 위반 0건 — 유료 제휴가 계산 결과 자체를 바꾼 사례가 없을 것
5. 사람의 개입이 승인 게이트와 에스컬레이션에만 국한됨
